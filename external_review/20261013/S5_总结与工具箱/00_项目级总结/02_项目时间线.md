## 2026-10-13（上线实测）· 根因锁定 = 上传协议 bug；mov 持久化成功
- 相机上线，`persist.py verify` 确认 ntsc/画质持久、mov 仍 mp4（与上一轮一致）。
- 执行影子槽实验时，**写盘前的 blob 下载失败**（原 20s 超时 < 相机 90–200s 的 68KB 响应），
  修 `download_blob` 超时 → 240s。
- 首次写入后读回仍 mp4。追查发现相机对 camsetting 返回
  `startsenddata → method=separate / bufsize=61460`，而 `persist.py` 用的是**单次 65KB POST**：
  **数据从未落地**（`senddata` 响应超时，`endsenddata` 回 ok 也无意义）。
  仓库内 oracle 日志 `camset_write_test.log` 早已记录正确分块序列（`senddata @61192`、`@65533`）。
- **重写 `persist.py::_upload_payload` 为分块协议**（chunk=61192，块间 `requestsenddata`，末 `endsenddata`），
  `flashwrite` / `flashwrite-file` / `restore` 三条路径全部改走它。
- 重跑影子槽实验：`senddata @61192 ok` → `senddata @65533 ok` → `endsenddata ok`（全程 ~2s），
  写后读回立即 = `videoformat=mov`。
- 拔电池重启 → `persist.py verify`：**`ntsc + mov + mov_60p_200mbps_c4k_10bit` 全部持久 ✓**。
- 结论更正：早先"mov 被固件重新派生为 mp4"**不成立**，H2「固件白名单」无证据支持，撤下；
  `01_成果总表.md` H1 恢复 ✓，并新增 H1b（CAMSET 分块写入协议）。

## 2026-10-13（晚）· 用户报障：机身菜单【录制质量】变灰 → 已修复

- 修复：改用 `allmenu` 已声明的同级档（用户选 `mov_60p_150mbps_c4k` = `0x92`），

  `persist.py restore` 的默认质量由 `0x8b` 改回 `0x9b`；`verify` 判决不再只认 `0x8b`。
- 拔电池重启后：菜单可选、质量保持 ✓。
- 另一条操作坑：**机身停在菜单界面时 `getinfo camsetting` 回 `err_reject`**（其它 getinfo 正常），

## 2026-10-13（晚·续）· 5.9K 片门全开解锁尝试 → 负结果
- 起点：`allmenu` 定义了 `mov_24p/25p/30p_200mbps_5_9k_10bit`（5888×3312），但 `curmenu` 全部 `enable=no`
  → 机身菜单实测 NTSC MOV 17 档 / PAL MOV 11 档，正好是 allmenu 去掉 5.9K 后的数量。
- `setsetting` **接受** 5.9K：24p→码 `0xf1`、30p→码 `0xf4`（PAL 25p 亦可）；
  但 `getsetting` 名字错报为 `mov_60p_200mbps_c4k_10bit`（S5 的"码→名"表没有这两个码）。
  `a6k` 回 ok 但静默忽略；`6k_10bit` → `err_param`。
- 写入 flash + 拔电池：码 `0xf4` **跨断电保留** ✓，但 `curmenu` 的 5.9K 仍 `enable=no`，
  且因当前值名字不在 allmenu → **机身【录制质量】再次变灰**。
- **实拍终判（解析 SD 卡文件头）**：`P1000004.MOV` = **4096×2160 @59.94fps hvc1 ~195Mbps**
  = C4K 60p，**不是 5888×3312**。请求 5.9K 30p 却出 C4K 60p → 未知码被回退到顶档。
- 结论：**S5 上 5.9K 不可用**（菜单层固件硬编码 no；设备层管线不输出 5.9K）。
  已把质量恢复为菜单可用档 `mov_60p_150mbps_c4k`(`0x92`)。
- 教训：`setsetting` 回 `ok` ≠ 格式真被执行，必须用实拍文件头（`tkhd`/`stsd` + `stts` 帧率）验证。
- 产出：`01_研究报告/08_格式对照表_NTSC-MOV_20261013.md` 第 6 节（含实测数字与逐档清单）。

## 2026-10-13（晚·续2）· 引入 S1H 交付包 → 发现 S5 的 `mp4ed` 容器
- 用户提供微信收到的 `Panasonic_hidden_format_research_20261012`（另一位研究者的 S1H 交付包）。
  微信路径被 **macOS TCC** 挡住读不了；仓库内 `01_研究报告/05_Panasonic_hidden_format_参考/`
  是同一包，自带校验 42 文件 / 0 错误。
- 该包给出跨机型关键结构：`0x5e` 首字节 = 格式编号（AVCHD=`0`、MP4=`5`、MOV=`6`、**MP4ed=`7`**、
  MP4hevc=`8`），质量记忆项按家族分（`0x122`/`0x123`/`0x124`/`0x16e`）；
  并记录两类失败：`setter=ok` 但 `getter=err_critical`、静默映射到别的格式。
- **据此在 S5 上补测 `mp4ed`（`0x07`）**：✅ 可进入，相机自动给 `mp4ed_60p_100mbps`；
  但显式写任意 `mp4ed_*` 质量 token 全部失败（44 个 NTSC 候选 0 个读回正常）。
- **实拍验证**：`P1000005.MP4` = 1920×1080@59.94fps、H.264 High 8bit、~96.6Mbps、
  **PCM 音轨**、30 帧 GOP（非 ALL-I）→ S5 的 mp4ed = 「MP4 + LPCM」1080p60 档，
  真实存在，但**不是** S1H 的 4K 4:2:2 10bit ALL-I/400Mbps。
- 另修正：S5 的 mp4ed 质量写在 `0x122`（S1H 是 `0x16e`），两机字段家族映射有差异。
- 未写入 flash（仅 RAM 验证，1080p 对本项目价值有限且会让菜单变灰）。
- 产出：`01_研究报告/09_S1H参考包分析_mp4ed_20261013.md`。

## 2026-10-13（晚·续3）· mp4ed 残留态导致菜单全灰 → 已修复；`setsetting` 会自动存盘
- 用户报障：机身【录制文件格式】多出 "(LPCM)" 条目（内部显示 AVCHD），且**格式与质量两项全灰**。
- 诊断：`live videoformat=mp4ed`，且 **flash `0x5e` byte0 也已是 `0x07`** ——
  ⇒ **修正旧假设：`setsetting` 会被相机自动写入 flash，不是"仅 RAM"**。
  之前只按 RAM 实验对待，留下了持久残留。
- 成因：`allmenu` 只声明 `mp4/mp4hevc/mov`；`avchd`/`mp4ed` 未声明 → 当前值匹配不到菜单项，
  于是**格式项与质量项一起置灰**，同时当前值被渲染成一个额外 "(LPCM)" 条目。
  **条目可见与菜单变灰是同一失配的两面，无法同时满足**；且 S5 没有 S1H 的"添加到列表（My List）"
  （全量菜单扫描无任何 list 项），故无法把隐藏档"注册"成常规入口。
- 修复：`setsetting videoformat=mov` + `videoquality=mov_60p_150mbps_c4k`，再分块回写 flash
  （`0x5e=0x06`、`vq=0x92`）。实测**两项恢复正常、"(LPCM)" 条目消失**。
- 新增工具 `04_工具与脚本/campaign2/container_switch.py`：按需切 `mov/mp4/mp4ed/avchd/mp4hevc`，
  `status` 只读查看 live+flash，`--persist` 才回写。想用 MP4(LPCM) 时切进去、用完切回来。
