# 第一部分：CAMSET 配置读写（9.2 MB 设置块）

## 1. 是什么

```
S1R2 的整份用户设置 = 一个 9,197,325 字节（约 9.2 MB）的配置块。
它同时存在于两处，内容等价：

  ① SD 卡文件  AD_LUMIX/CAMSET/CAMSET01.DAT  （9,197,325 B）
  ② USB/PTP 读到的 payload                  （9,197,337 B，多 12 字节 PTP 容器头）
```

**★ 这就是 S5 同事手里那份 "camsetting（65,533 字节）" 的 S1R2 版 —— 同一类东西，只是更大。**

## 2. 技术原理

### 2.1 双形态与头部

```
文件形态：@0x00 "Panasonic"   @0x12 "DC-S1RM2"
USB 形态：magic(4) + len1(4) + len2(4) + 同样的字符串
          ★ len2 = 9,197,325 = 文件长度
```

### 2.2 ★ 校验和算法（与 S5 是同一个算法！）

```
文件形态：   checksum = -sum(file[0 : len-1]) & 0xFF
USB payload：checksum = -sum(payload[0x0C : len-1]) & 0xFF

等价写法：   checksum = (256 - Σ(所有字节)) mod 256

★ 与 S5 的 "byte[65532] = (256 − Σ(byte[0..65531])) mod 256" 是【同一算法】
  ⇒ 证明 LUMIX 全系设置块的校验是同一套，字段定位方法可互相借鉴 ✓
```

### 2.3 配置结构（TLV 记录）

```
配置由 TLV 记录组成：group / idx / type / x / len + 数据
关键规律：改一个设置常需【同时改 3 份副本】，否则被相机内部覆盖
```

## 3. ★ 复现方式

### 读配置（零风险）

```
方式 A（USB）：PTP 0x9421 读配置 → 得到 9,197,337 字节 payload
方式 B（SD 卡）：直接读 SD 卡上的 AD_LUMIX/CAMSET/CAMSET01.DAT
```

### 写配置（已验证可生效 + 持久）

```
① 改配置里目标字段（比如照片风格名 / 快门声类型）
② 重算校验和（上面公式）
③ 写回：
   方式 A（USB）：PTP 0x9422 导入 → 相机立即生效
   方式 B（SD 卡）：写回 CAMSET01.DAT → sync → umount → 相机菜单「从卡读取设置」
④ 验证：菜单里确实变了，且断电重启后仍在（持久）✓
```

### ★ 已实测成功的字段（证明整套链路闭合）

```
· 照片风格名 → 改成 "ZZTEST"（UTF-16LE，3 份副本）→ 菜单显示 ZZTEST ✓
· 快门声类型 → 改成 3（菜单里只有 1/2）→ 出现了菜单外的隐藏音效 ✓
· 都【持久化】了（断电重启后仍在）✓
```

## 4. 已定位的关键字段偏移（供参考）

```
快门声相关（group 0x022E / 0x1022E / 0x2022E，三份）：
   0x00DE48 / 0x00DE64 / 0x00DE80   快门声【类型】(u32)
   0x01CF64 / 0x01CF90 / 0x01CFBC   音调参数
   0x002B50 / 0x00DDF4               关联标志位
照片风格名：
   0x00DE3C 起（UTF-16LE，3 份副本）
```

> ⚠️ 注意：S1R2 的 CAMSET 是 9.2MB，S5 的 camsetting 是 65,533 字节，
> 偏移【完全不同】，但【定位方法一样】：改一个设置 → dump 配置 → 差分 → 找变化字节。

## 5. ★ 与 S5 同事工作的对照（结合点）

| 维度 | S5（同事） | S1R2（我们） |
|---|---|---|
| 设置块名称 | camsetting | CAMSET |
| 大小 | 65,533 字节 | 9,197,325 字节 |
| 通道 | Wi-Fi cam.cgi | USB PTP |
| 读 | getinfo camsetting | 0x9421 / SD 卡 |
| 写 | setsetting（RAM）/ senddata（flash）| 0x9422 / SD 卡导入 |
| 校验 | byte[65532]=(256−Σ)mod256 | -sum(bytes)&0xFF（同算法）|
| 持久化 | ✅ 已验证 | ✅ 已验证 |

**⇒ 双方可以互相借鉴的是【字段差分定位法】和【校验算法】，不是具体偏移。**

# 第二部分：FunctionFS 内核越界读写（F1 / F2）

## 1. 是什么

```
S1R2 内核（Linux 4.19.124 + 松下 Milbeaut 移植）的 drivers/usb/gadget/function/f_fs.c
被松下大幅修改，新增了一个数组：

   unsigned current_alt_setting[MAX_CONFIG_INTERFACES];  // MAX_CONFIG_INTERFACES == 16

它导致了两处【可由 USB 主机触发】的内核越界读写（原生 4.19.124 没有这个数组）：
   F1 = 越界写
   F2 = 越界读
```

## 2. 技术原理（根因链）

```
攻击者发 SET_INTERFACE，wIndex 高字节非零（如 0x0100）

① composite.c：  u8 intf = w_index & 0xFF;      ← 校验用【低字节】= 0x00
②                 if (intf >= 16) break;          ← 0 < 16 通过
③                 f->set_alt(f, w_index, ...);    ← 却传【未截断的原始 w_index】✗
④ f_fs.c：       ffs_func_revmap_intf(func, u8)  ← 形参又是 u8，再截断，校验失效
⑤                 current_alt_setting[0x0100] = alt;   ← ★ 越界写（下标 256，偏移 1KB）
```

```
关键代码：
  F1 写：f_fs.c:3433  func->current_alt_setting[interface] = alt;   (SET_INTERFACE)
  F2 读：f_fs.c:3391  return func->current_alt_setting[interface];  (GET_INTERFACE)
```

## 3. ★ 复现方式（已实机验证）

### F2 越界读（安全，只读）

```
GET_INTERFACE，wIndex = 0x0100, 0x0200, …, 0xFF00
   ⇒ 读 current_alt_setting[256], [512], …, [65280]
   ⇒ 即内核堆里，数组起点之后 1KB ~ 256KB 的 1 字节快照

实测：250 点可读，泄出约 30 个非零字节（其余为 0）
      wIndex=0x0200 → 0x99；0x0a00 → 0x75；0x1000 → 0x00 …
```

### F1 越界写（危险，写内核 RAM）

```
SET_INTERFACE，wIndex = 0x1000，wValue = 0x4141
   ⇒ 写 current_alt_setting[4096] = 0x4141

实测：写前 0x00 → 写 0x4141 → 读回 0x41 → 写回 0x00 干净还原 ✓
      相机全程未崩（写的是 RAM，最坏 = 死机重启，不会变砖）
```

### 原语能力总结

```
越界读：256 个固定偏移（1KB 步长）× 每点 1 字节
越界写：256 个固定偏移（1KB 步长）× 4 字节 × 高 16 位恒为 0（低 16 位可控）
```

## 4. 可利用性判定（已做完静态分析，结论明确）

```
★ 判定：低（代码执行方向 = 死路），只能 DoS + 极弱信息泄露

原因（子代理静态分析结论）：
   · struct ffs_function = 352 字节，current_alt_setting 偏移 280（结构末尾）
   · 分配在 kmalloc-512 桶
   · 256 个偏移全部落在「第 2k 个相邻对象的固定偏移 280」处
   · 写 4 字节高 16 位恒 0 ⇒ 部分指针覆盖不可行（覆盖后指针落到 4GB 窗口头 64KB，未映射）
   · 读只泄固定偏移 1 字节 ⇒ 重建不出指针，对 ASLR 绕过无用
   · USB 主机无法在相机侧做堆喷 ⇒ 无法精确命中
```

**⇒ 结论：这是一个"入口级"内核内存破坏，但本身到不了代码执行。**
**它的价值在于：证明了 S1R2 的 USB 主机面存在"未授权内核写"，可作为 DoS / CVE 级发现归档。**

## 5. 技术路线（为什么它仍是重要的一环）

```
拿到 shell（本地代码执行）
   → 用固件里现成的【任意物理内存读写】原语提权：
       · /dev/mem（STRICT_DEVMEM 关闭）→ root 任意物理内存读写
       · uhadev（ioremap 任意物理地址）
       · /dev/exmem
       · f_fs 的 FUNCTIONFS_PHYSICAL_ADDR / PHYADDR_REMAP
   → 一步到位 root

FunctionFS OOB 是【软件侧唯一的"未授权内核写"入口】，
虽然单独到不了 root，但它证明了攻击面存在，
且是整个"USB 主机 → 内核"链路里【唯一实机确认】的一环。
```

## 6. 与 S5 的关联

```
· S5 同事现在拿到的是【设置块读写】（Wi-Fi cam.cgi，用户态/数据层）
· FunctionFS OOB 是【内核层】（USB gadget 驱动，越界写）
· 两者是【不同层级】的攻击面：
   设置块 = 改数据（解锁隐藏格式，安全）
   内核 OOB = 改内核（DoS / 潜在内存破坏，危险）

· ★ 对 S5 的启发：
   如果 S5 也用 FunctionFS（PTP 走的就是 FunctionFS），
   那【同样的 OOB 可能也在 S5 内核里存在】——
   可以对照 S5 的 f_fs.c 源码（如果拿得到 OSS）做同样的静态审计。
```
