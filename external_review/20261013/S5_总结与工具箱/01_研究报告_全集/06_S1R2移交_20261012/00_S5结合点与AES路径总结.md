# S1R2 两项成果 → S5 结合点与 AES 路径总结

> 日期：2026-10-12 · 整理：S5 逆向组

> `S1R2两项成果_移交S5同事.md`、`S1R2_已排除路线与风险备忘.md`
> 目的：① 说明 S1R2 两项成果如何落到 S5（MC801）；② 汇总"接下来破解 AES（固件解密）"的全量路径与优先级。

## 一、S1R2 两项成果 → S5 的结合点

### 1.1 CAMSET 配置读写（9.2MB 设置块）→ S5（65,533B camsetting）

| 结合点 | 结论 | 强度 |
|---|---|---|
| 同一类对象 | S1R2 `CAMSET01.DAT`（9,197,325B，SD 卡 + PTP 0x9421 双形态）与 S5 `camsetting`（65,533B，getinfo/senddata）是同一设计家族的设置块 | ✓ 双证 |
| ★ 校验算法互证 | S1R2：`checksum = (256 − Σ) mod 256`；S5：`byte[65532] = (256 − Σ(byte[0..65531])) mod 256` —— **同一算法，两组人独立反推**，证明 LUMIX 全系设置块校验同出一源 | ✓ 双证 |
| 持久化双证 | S5：直写 flash 的 senddata 持久化（mov open-gate 顶档，10-12 已闭合）；S1R2：0x9422 / SD 卡导入持久化（改照片风格名 + 隐藏快门声，已闭合） | ✓ 双证 |
| TLV「三份副本」规律 | S1R2：改一个设置常需同时改 3 份副本（group 0xNNNN / 0x1NNNN / 0x2NNNN），否则被内部覆盖 | ✓ 新信息，S5 待验证 |
| 字段定位方法论 | 改设置 → dump → 差分 → 找变化字节。S5 阶段三已实际在用（videoformat/videoquality 定位即此法） | ✓ 方法互证 |

**注意**：S1R2 偏移（如快门声 0x00DE48）与 S5（videoformat@3062 等）**完全不同，不可直接借用**，只借方法。

**对 S5 的可执行增量**：
1. 用 TLV 三份副本规律解释 S5「setsetting 只写 RAM、senddata 才落 flash」的双通道行为——下次枚举 S5 隐藏域时，先确认目标字段是否有多副本；
2. S1R2 证明了 **PTP 0x9422 写配置路径本身是闭合且持久的**——S5 安全红线暂不执行 0x9422/0x9423，但这条「PTP 配置写」路线从「未验证」升级为「同族实机已验证」，风险评级可下调（仍属只读优先红线内）。

### 1.2 FunctionFS 内核越界读写（F1/F2）→ S5

| 结合点 | 结论 | 强度 |
|---|---|---|
| S1R2 实机状态 | SC2006A + Linux 4.19.124 松下移植：`SET_INTERFACE(wIndex 高字节非零)` → `current_alt_setting[16]` 越界写（下标最大 0xFF00，偏移 255KB）/ 越界读；实测写 0x4141 生效、读 250 点非零 ~30 字节 | ✓ 实机（S1R2 侧） |
| 可利用性 | **低**：256 个固定偏移（1KB 步长）× 写 4B 且高 16 位恒 0 → 部分指针覆盖不可行、读 1B 重建不出指针、无堆喷 → **代码执行死路**，仅 DoS + 弱信息泄露 | ✓ 静态分析闭合（S1R2 侧） |
| S5 迁移性 | **不直接迁移**：S5 = MC801（32-bit A7 级），不同 SoC 家族；但 S5 的 PTP 同样走 FunctionFS | ◐ 待审计 |

**对 S5 的可执行增量**（对应总评估报告任务 6）：
1. 拿到 MC801 内核 OSS 后，审计 `drivers/usb/gadget/function/f_fs.c` 是否有同款 `current_alt_setting[MAX_CONFIG_INTERFACES]` 修改（松下是系内统一移植，命中概率不低）；
2. 若命中：S5 也获得「USB 主机 → 内核 RAM」的未授权 1B 读 / 4B 写原语——价值 = CVE 级发现 + DoS + 辅助信息泄露，**单独仍到不了 AES/明文**；
3. 不命中也不改变主路线（JTAG 仍是主线），仅少一条支线。

## 二、S1R2 侧「已排除路线」对 S5 的交叉校验

S1R2 风险备忘（SC2006A 实测 / OSS 源码确认）中的排除结论，**不能直接搬到 S5（MC801）**，逐条标注适用性：

| S1R2 结论 | S1R2 依据 | 对 S5 的适用性 |
|---|---|---|
| ❌ UART 是死路 | U-Boot `BOOTDELAY=-2` + 内核 `console=null loglevel=0` + `ENV_IS_NOWHERE`（接了也是黑的） | **⚠️ 不可直接套用**：S5 的 U-Boot 配置未读（rootfs 加密，离线看不到 env）。**先做离线核验**（见 §三 P3）：在 48 分区表的 type=2 明文分区里找 env / BOOTDELAY / console 痕迹；若同样关闭 → S5 UART 判死路；若开启 → UART 复活为只读 bootlog 通道 |
| ⚠️ SD.DAT / ROM-flashing 高风险别碰 | 无只读/RAM-boot 模式，跑代码必须写 flash；写错 `pardata.par` = 不可逆毁出厂标定；S1R2 是 **NAND**，GoPro 的 eMMC 路径从未在 NAND 上验证成功 | **⚠️ 保守处理**：S5 存储类型（eMMC/NAND）需拆机确认（P1）。若同为 NAND → 风险同级，**SD.DAT 降级为 JTAG 之后的备胎**，不做第一动作 |
| ⚠️ legacyboot（U-Boot 从 SD 引导自核） | 命令存在但默认 bootcmd 不用，且需 U-Boot 控制台（被 console=null 堵死） | 同 UART 结论，取决于 P3 核验结果 |
| ⚠️ 服务模式组合键 | 松下有传统：GX85 = 回放+AF/AE LOCK+右键 开机；ZS30 = 录像+MENU/SET 开机 → SERVICE MODE；S1R2 组合键无公开资料 | **✅ 零风险直接试 S5**：多键组合开机盲试（参考上述两例 + 快门/电源/拨盘变体），命中即可能进维护菜单 |
| ✓ UVC 零长度控制请求 → 持久 DoS | 网络摄像头模式 VS probe `SET_CUR(wLength=0)` → 守护进程挂死，跨断电不恢复，须出厂重置 | S5 漏洞档案补充项：UVC probe 零长度测试（低优先，属 DoS 归档） |
| ✅ JTAG 是唯一"确定能到终点"的路 | 不需控制台；halt CPU 后 dump RAM = 解密后明文 | **✅ 完全适用**：S5 的 A7 核有完整 CoreSight（同平台 GoPro 公开先例，OpenOCD 现成配置）——**维持本包 §5 路线排序第一名** |
| 零风险探针：SD 根目录固件文件名匹配 | 相机开机/进菜单时枚举 SD 根目录做固件文件名匹配（官方"卡里 2 个固件文件会导致不识别"可证） | **✅ 零风险可做 S5 版**：放命名文件进 SD，观察是否被枚举（判断 bootrom 侧行为窗口） |
| MDR 寄存器读引导来源（0xd150000） | `STRICT_DEVMEM` 关闭，有代码执行即可 `/dev/mem` 只读反推引导/strap 状态 | 依赖先有代码执行（JTAG 后自然具备），非独立路径 |

## 三、★ 接下来破解 AES（固件解密）的可能路径 —— 汇总优先级

**目标重述**：AES 密钥本身固化在 MC801 芯片内（OTP/eFuse/Crypto Engine/TrustZone），软件侧已终局否定。
因此"破解 AES"的现实目标 = **拿到开机后 DDR 里的运行时明文**（或等价的可写自编代码入口），**不需要那把密钥本身**。

### 3.1 已排除（✗ 不要再走）

| 路线 | 否定依据 |
|---|---|
| 离线密钥提取（XOR/RC4/AES 全模式，130k+ 探测，含 loader1/0x220 块及派生） | 10-10 终局否定 |
| 转接环 EF-L 取 S5 密钥 | 总线拓扑 + SoC 安全域隔离 + `.ecp` 是标定数据无代码（三重论证） |
| Wi-Fi / 网络取密钥或 RCE | ~70 mode 枚举全 err_param；仅 3 个验证型预言机（版本门/签名/CAMSET 校验和）；GoAhead 溢出、LD_PRELOAD、file-op/exec 全失败 |
| 改 `comm_proto_ver` 绕版本门 | 字段方向 + 无比较逻辑 |
| 旧机型 PTool 密钥切片移植（GH2 法） | 120 组合全失败，S5 是硬件密钥 |

### 3.2 活路径（按优先级排序，P1→P8）

| 优先 | 路径 | 前置 | 风险 | 预期收益 | 状态 |
|---|---|---|---|---|---|
| **P1** | **拆机只读取证**：SoC 丝印（定 die/代际）、JTAG/SWD 与 UART 测试点、Wi-Fi 模块型号、**存储类型 eMMC/NAND**、主板正反面高清图 | 拆机（接 AC、备拔电池恢复） | 零（只读） | 全部硬件路径的先决条件；信息量最大 | 未做 |
| **P2** | **服务模式组合键盲试**：多键同时按下开机（GX85/ZS30 式），试 S5 的 SERVICE MODE | 无 | 零 | 若命中 → 维护菜单/读入口（或至少排除） | 未做 |
| **P3** | **S5 U-Boot 控制台离线核验**：在 48 分区表 type=2 明文分区中找 U-Boot env / BOOTDELAY / console= / loglevel 痕迹 | 离线（`s5_layout.json` + `S5___V29.bin.parts.json` 已在包内） | 零 | 判定 UART 生死（S1R2 先例：console=null → 死路）；顺带看 Stubby 是否 ENFORCING | 未做（**本次新增**） |
| **P4** | **JTAG / CoreSight dump RAM**：OpenOCD（A7，3 看门点/5 断点）halt → dump loader/program/zimage/rootfs 运行态 | P1 确认焊点 + 时序 | 低（只读 halt，不写 flash） | **★ 解密后运行时明文 = 目标达成** | 未做（主线） |
| **P5** | **UART bootlog**（仅当 P3 判活）：115200 8N1 抓 Stubby 告警/验签/分区表/cmdline | P3 | 零 | 启动链实证 + 验签时机 | 未做 |
| **P6** | **SD.DAT / ROM-flashing**：BootROM 跑 SD 卡自编 `DATA.BIN`，绕 loader2/3 与验签链，可写可 dump | P1（确认存储类型）+ 全量备份 + 验证过的 `pardata.par` | **高**（S1R2 NAND 教训：写错标定数据 = 不可逆砖） | 彻底绕过验签链的写入口（JTAG 受阻时的备胎） | 未做（降级为备胎） |
| **P7** | **S5 内核 f_fs OOB 离线审计**：MC801 内核 OSS 对照 `f_fs.c` 的 `current_alt_setting` 修改（S1R2 报告 §2 代码位置） | 拿到 MC801 内核 OSS | 零 | 若命中 = USB 主机→内核 未授权写原语（CVE 归档/DoS/辅助泄露），单独不解密 | 未做 |
| **P8** | **芯片级**：chip-off / 故障注入 / 侧信道（Crypto Engine） | 芯片级设备与资金 | 高 / 高成本 | 直接提取密钥本身 | 最后手段 |

### 3.3 策略一句话

**P1 拆机取证 + P2/P3/P7 零风险项并行启动 → JTAG（P4）做主线 → SD.DAT（P6）仅在 JTAG 受阻且完成 S1R2 NAND 风险功课后备用。**
软件面（Wi-Fi/PTP/设置块）对 AES 的贡献已封顶：设置块读写 = 改数据（已吃尽收益），内核 OOB = 改内核（DoS 级），都不出明文。

### 3.4 与既有结论的关系（无冲突声明）

- 本总结**不推翻** 10-10 总评估报告的 §5 路线排序（UART/JTAG > SD.DAT > Stubby > Wi-Fi 芯片），而是用 S1R2 实机教训做了三处修正：
  1. **UART 从"默认首选"改为"先核验 console 配置再决定"**（S1R2 已实测 console=null 死路，S5 待 P3 核验）；
  2. **SD.DAT 从"排名 2"降为"JTAG 之后备胎"**（S1R2 NAND 实测教训 + 无只读模式）；
  3. **新增 P2 服务模式组合键 与 P3 离线 console 核验** 两个零风险先行项。
