# S5 隐藏录像格式持久化 — 成果报告

日期：2026-10-12　固件：VD4.30（MC801，研究版）　IP：192.168.1.131

## 一句话结论
相机现在**每次开机都直接处于隐藏的最高档**：`MOV C4K 60p 200Mbps 10-bit` + NTSC 帧率门常开。
该状态已写入 **flash，跨断电重启持久**，无需重启后重新设置。
（最终轮已按要求**放弃 HEVC 容器**，改用 mov 容器——一次性把「常规录制 + open-gate 隐藏档」都拿到手。）

## 核心机制（本次破解的关键）
相机对外只暴露设置的 **RAM 副本**（`getinfo camsetting` 读到的就是它）。两个写入路径行为不同：

| 写入方式 | ntsc_pal | videoformat | videoquality | 是否跨重启持久 |
|---|---|---|---|---|
| `setsetting`（CGI 命令） | 写入 flash ✓ | 只写 RAM ✗ | 只写 RAM ✗ | 部分 |
| **直接 flash 写入**（startsenddata/senddata/endsenddata 上传 65533 字节 blob） | ✓ | ✓ | ✓ | **全部持久** |

即：`setsetting` 对录制容器/画质只改运行时（RAM），一断电回落默认 mp4/30p；
而把整块设置 blob 通过 senddata 上传到 flash 后，三项都真正落到 flash，开机即生效。
（ntsc_pal 用 setsetting 也能持久，属固件对"系统设置"与"录制设置"的不对称处理。）

## 关键字段偏移（camsetting 65533 字节 blob）
| 偏移 | 字段 | 取值 |
|---|---|---|
| `65230` | ntsc_pal | `0x00`=NTSC，`0x01`=PAL |
| `3062` | videoformat | `0x05`=mp4，`0x06`=mov，`0x08`=mp4hevc（最终弃用） |
| `6986` | videoquality | `0x8b`=mov_60p_200mbps_**c4k**_10bit（open-gate 顶档，最终默认），`0x9b`=mov_60p_200mbps_4k_10bit，`0xc1`=mp4_30p_20mbps（mp4 默认） |

校验和：整块 65533 字节求和 mod 256 = 0，即 `byte[65532] = (256 - Σ(byte[0..65531])) mod 256`。
改任意字段后必须重算该字节，否则相机会拒收/回滚。

## 当前相机的持久状态（已复读 + 已断电验证）

ntsc_pal   = ntsc
videoformat= mov
videoquality = mov_60p_200mbps_4k_10bit   (blob 65230=0x00 / 3062=0x06 / 6986=0x9b, 校验和有效)

## 工具（工作目录 campaign2/）
- `persist.py` — 主工具，四种模式：
  - `verify`（只读，安全）：健康 + 实时 + blob 三字段，给结论。**重启后跑这个验证。**
  - `flashwrite`（危险，需 `--confirm`）：下载当前 blob → 仅设 ntsc → 重算校验和 → 上传。
  - `flashwrite-file <blob> --confirm`：上传指定的 65533 字节 blob（自动备份）。
  - `restore --confirm`：**一键恢复**。下载当前健康 blob，只强制改那 3 个字段，重算校验和，备份后上传。
    （比整包覆盖更安全：其余字段保持相机当前健康值，适合出厂重置/升级后恢复。）
- `out/GOLDEN_S5_hidden_format_payload.bin` — 黄金 payload（ntsc+m mov+mov_60p，校验和有效）。

## 常用命令
```bash
# 验证（只读，随时跑）
python3 persist.py verify

# 一键恢复隐藏格式（危险，先确认相机健康，AC 供电）
python3 persist.py restore --confirm
```

## 安全与约束
- UA 必须 `LUMIX Sync`；建议 AC 供电；相机极易卡死，写后健康守护（getstate=ok），非 ok 立即停手。
- flash 写回务必用**严格 65533 字节**、校验和有效；每次写前已自动备份（`out/backup_*.bin`）。
- 不要：刷固件 / resetDevice / fw_update_mode / PTP 配置写 / 超长包。
- 若相机异常，用最近一次备份 blob 通过 `flashwrite-file <备份> --confirm` 回滚。

## 追加：HEVC (H.265) 容器持久化 —— 2026-10-12

### 新发现：mp4hevc 的 blob 容器码 = 0x08
`camsetting` blob 偏移 `3062`（videoformat）取值补充：
- `0x05` = mp4
- `0x06` = mov
- **`0x08` = mp4hevc**  ← 本次确认（之前文档只列了 mp4/mov）

### HEVC 的画质不单独存在 blob 里
切到 `videoformat=mp4hevc` 后，画质由固件按"容器+帧率"**派生**（NTSC→`mp4hevc_30p_72mbps_4k_10bit`）。
blob 的 `6986`（videoquality 码）在切容器时**不更新**为 HEVC 专属码，仍保留上一个 MOV 值；
`16558`/`57762` 同理。所以**不要手动改 6986 去"造"HEVC**，只要把容器码 `3062=0x08` 落地即可，
画质会自动派生稳定。

### 持久化方法（已断电验证成功）
把相机**当前健康的 mp4hevc 活体 blob**（`3062=0x08`、校验和有效）整块回写 flash 即可：
```
python3 persist.py verify                      # 只读，随时可跑
# 回写用 out/blob_hevc_active_*.bin（当前活体、已校验），走 startsenddata/senddata/endsenddata
```
断电（拔电池）重启后 `getsetting videoformat` 仍 = `mp4hevc`，证明持久成功。

### 当前相机持久状态（已断电验证）
```

videoformat= mp4hevc              (flash 持久，本次新落地)
videoquality = mp4hevc_30p_72mbps_4k_10bit  (固件派生)
```
开机即 HEVC 4K 10bit，无需重启后手动补。回滚底：`GOLDEN_S5_hidden_format_payload.bin`
（mov_60p 态）与 `backup_pre_hevcflash_*.bin`。

## 最终轮：放弃 HEVC，锁定 mov + open-gate（2026-10-12 终版）

按用户优先级调整：**放弃 HEVC**（`mp4hevc` 容器），优先保证「常规录制模式 + 隐藏格式都可用」，
并把 open-gate 的 MOV 高档（60p 200M 4K/C4K）一并持久。最终用 **mov 容器** 落地。

### 关键结论 1：videoformat 是单一容器门，mp4 / mov 互斥
`videoformat`（blob `3062`）是**唯一门控字段**，决定整条画质菜单的可见性，mp4 与 mov 二选一、互斥：

| 容器态 | 可见/可选的画质 | 隐藏的画质 |
|---|---|---|
| `mov`（0x06） | 17 个 `mov_*` open-gate 档（24p/30p/60p × 100/150/200Mbps × 4K/C4K/10bit 变体） | 16 个 `mp4_*` 常规档 |
| `mp4`（0x05） | 16 个 `mp4_*` 常规档 | 17 个 `mov_*` 全部隐藏 |

**重要澄清**：mov 态下「常规录制」并没有丢——17 个 mov 档里最低就是 100Mbps
（`mov_30p_100mbps` 等），日常拍摄完全够用，且码率比 mp4 的 20/28Mbps 还高。
所以 **mov + open-gate = 常规 + 隐藏都拿到，是最优解**，不需要在 mp4/mov 之间来回切。

17 个可选的 mov 档（mov 态实测 enable=yes）：
`mov_24p_100mbps / _10bit / _4k / _c4k`、`mov_24p_150mbps_4k_10bit / _c4k_10bit`、
`mov_30p_100mbps / _10bit / _4k / _c4k`、`mov_30p_150mbps_4k_10bit / _c4k_10bit`、
`mov_60p_100mbps / _10bit`、`mov_60p_150mbps_4k / _c4k`、`mov_60p_200mbps_4k_10bit`。
（5.9K / 6K / 100p / 120p / 400mbps 等为其他机型占位，本机恒隐藏。）

### 关键结论 2：`mov_60p_200mbps_c4k_10bit` 真实码 = 0x8b（更正旧文档）
open-gate 顶档 `mov_60p_200mbps_c4k_10bit` 在 blob `6986` 的真实编码是 **`0x8b`**，
不是旧文档/旧摘要写的 `0xf4`（那是错的）。对照：
- `0x8b` = `mov_60p_200mbps_c4k_10bit`（C4K 顶档，最终默认）
- `0x9b` = `mov_60p_200mbps_4k_10bit`（4K 档）
- `0xc1` = `mp4_30p_20mbps`（mp4 容器默认）

### 关键结论 3：senddata 时序陷阱 + endsenddata 恢复套路（踩坑记录）
相机对 `senddata` 可能**长期不返回响应**（它在等 `endsenddata`），导致 `KA.send()` 的
`recv()` 卡死（进程 S 态 / CPU 0%）。`timeout=120` 反而卡了 6 分钟。**这不是失败**：
- 数据由 `sendall` 发出即已送达相机；`send()` 的响应超时/卡死**不代表失败**。
- 恢复套路：`kill` 卡死进程 → 健康检查 → **用一条新的短超时连接直接发 `endsenddata`**
  （相机不绑 keep-alive，新连接即可）→ 健康 + 复核。这就是本轮救回相机的做法。
- 更省事：参考 `/tmp/flash_hevc.py` 用 `timeout=20`，send 超时后直接走 `endsenddata`（双发无害）。
