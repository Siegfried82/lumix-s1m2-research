# 固件上传「解密/校验预言机」测试

> 目标：确定相机在 `endsenddata` 时的校验顺序与错误区分能力，
> 判断软件层面（非拆机）能否反推固件解密密钥。
> 工具：`upload_test.py`（纯标准库，流式上传，边传边改字节，不额外占 90MB 磁盘）

## 背景（为什么这是最后一条纯软件路线）

- 静态穷举已排除：XOR / RC4* / AES-ECB/CBC/CTR（全部候选密钥含 loader1 24B+64B、0x220 64B 块及派生）、SHA-384 标签。
  （*RC4 本轮补测，仍未命中，见下）
- 48 字节分区校验块不是任何无密钥哈希（SHA-384/256/1/MD5/CRC 的组合全部试过）→ 极可能是带芯片内密钥的 HMAC/CMAC。
- 结论：密钥大概率在 MC801 boot ROM 内。软件路线只剩「上传时相机对固件做解密+校验」这一行为可利用。

## 校验顺序假设（待实测）

```
endsenddata 收到全文件后：
  [1] 版本检查      → err_fw_same / err_fw_old
  [2] CRC32 检查    → 0x40 字段 = crc32(data[0x200:])（已本地验证公式）
  [3] RSA-4096 签名 → 文件末尾 512B
  [4] 分区解密+48B 校验块比对
  [5] 写 flash → 重启
```
预言机是否成立取决于：
- [3] 是否先于 [4] 且不可绕过 → 若先于，则任何改动都被 `err_reject` 挡掉，预言机死路（除非有免签名的恢复模式）。
- [4] 失败时返回的错误是否与 [3] 不同 → 若不同，可逐字节翻转密文试探，反推明文/密钥流。

## 各阶段（风险递增）

| 阶段 | 内容 | 风险 | 预期信息量 |
|---|---|---|---|
| 0 | getstate / req_acc / req_acc_g 握手探测 / 端口扫描 / 上传**原始 V29** | 无 | 基线响应（预期 `err_fw_same`）；2401 热点上是否有隐藏端口；加密握手是否可用 |
| 1 | 翻转头部某 4 字节字段 +1（如 0x24，CRC 不受影响）后上传 | 无 | 若响应从 `err_fw_same` 变化 → 找到版本字段；不变 → 换下一个字段 |
| 2 | 版本字段 +1 后上传 | **中**：若相机回 `ok` 会写入并重启（内容是原版 V29 代码，应能正常开机） | 关键问题：签名检查在上传时还是启动时？`ok`=上传时不验签；`err_reject`=验签挡住 |
| 3 | 版本 +1 + 改 1 字节（默认改 zboot 分区 48B 校验块首字节；或 `--data-flip` 指定数据位） | **高**：若相机接受，写入的是被破坏的固件，可能无法启动 | 若 [2] 已 `err_reject` 则本阶段无意义。若 [2] 是 `ok`：本阶段区分「签名只覆盖头部」与「覆盖全文件」 |

每次上传 90MB ≈ 1470+ 分片，Wi-Fi 下约 5–20 分钟。

**重试语义（与官方 app 一致，2026-10-10 补上）**：相机在缓冲区未排空时会对
`senddata`/`startsenddata` 回 `err_busy`、对 `requestsenddata`/`endsenddata`/
`abortsenddata` 回 `err_busy` 或 `wait`。官方 app（`p168v5/a.java` 的
`J()`/`I()`/`u()`）对同一分片/命令重试 5 次、每次间隔 1s，`senddata` 的
`wifi_reset` 也视为成功。`upload_test.py` 已按此实现（`--retries N`，默认 5；
连接超时同样重试）。此前第 4 次运行在**最后一个分片**收到一次 `err_busy`
即中止，属脚本缺陷，非相机行为。

## 运行（在你的终端，相机已连 2401 热点 / 192.168.1.131）

```bash
cd <LOCAL_USER>/Downloads/com.panasonic.jp.lumixsync_b0834c31/oracle

# 阶段 0（安全，先跑）
python3 upload_test.py --ip 192.168.1.131 --bin ../fw_fetch/S5___V29.bin --phase 0
# 相机离线时可等它上线后自动跑（每 15s 探测，30 分钟上限；相机弹出连接提示时按 OK）
bash wait_cam_and_run.sh


# 阶段 1（安全，逐字段试版本字段；先试 0x24）
python3 upload_test.py --ip 192.168.1.131 --bin ../fw_fetch/S5___V29.bin --phase 1 --field 0x24
# 若响应与阶段 0 相同，再试: --field 0x1C  /  0x20  /  0x2C  /  0x34

# 阶段 2（风险：相机可能写入并重启；确认后再跑）
python3 upload_test.py --ip 192.168.1.131 --bin ../fw_fetch/S5___V29.bin --phase 2 --field 0x24 --confirm-risky
# 若回 ok：等 60–120s 相机重启完成，再跑阶段 0 确认相机活着

# 阶段 3（高风险，仅在阶段 2 回 ok 后）
python3 upload_test.py --ip 192.168.1.131 --bin ../fw_fetch/S5___V29.bin --phase 3 --field 0x24 --partition zboot --confirm-risky
```

结果自动追加到 `oracle_results.md` + `oracle_results.jsonl`（含每步精确响应与耗时，
耗时本身也是信息：RSA-4096 验签要数百毫秒，可区分「验签失败」与「数据校验失败」）。

## 阶段 0 实测结论（2026-10-10 已完整跑通，勿重复浪费上传）

`phase 0` 已跑 4 次，最后一次（02:51）在会话门打开（`req_acc` 弹窗确认 + `fw_update_mode(V3.00)=ok`）后
把**原封不动的 V2.9** 完整上传：`startsenddata=ok,method=separate,bufsize=61460`，1474 个分片全 `ok`，
**最后一个分片**回 `err_busy`→重试→`err_critical`，`abortsenddata=error`；相机仍在 VD4.30，未变砖。

由此得到三条硬结论：

1. **降级保护实证**：正确签名的旧固件 V2.9 被拒（`err_critical`），且发生在**收完全文件之后**、
   写 flash 之前。相机始终没刷，说明版本/签名门先于写 flash——这就是安全底线。
2. **无预言机**：相机对「旧版本固件」只给一个粗粒度 `err_critical`，不是 `err_fw_old/err_fw_same`
   （那是 app 端下载前自检的文案，不是相机上传响应的区分）。没有逐字节/逐分片的错误反馈，
   也没有可用的时序差（Wi-Fi HTTP 下 RSA 耗时被网络抖动淹没）。
3. **阶段 1 的前提已失效**：README 原假设「原始旧固件→`err_fw_same`」，实测是 `err_critical`，
   因此「翻转字段看响应是否从 err_fw_same 变化」无从谈起，逐字段找版本位已无判别信号。

结论：上传路径不是解密预言机，继续跑 phase 1/2/3 要么无信号、要么（phase 2/3 版本+1）
有真实变砖风险且换不到密钥。建议**停止上传预言机这条线**，转向恢复模式（见下）或硬件提取。

## 相机变砖后的恢复（阶段 2/3 前必读）

1. 先查电池（阶段 0 的 getstate 会打印），电量低先充电。
2. S5 的官方恢复方式：USB 线连电脑，进入恢复模式（官方文档搜索词：
   `LUMIX S5 firmware update failed recovery USB` / 松下支持页
   `panasonic.com/support/global/cs/products/cameras/dsc/s5`），
   恢复模式下的固件写入通常**跳过签名检查**——这本身就是预言机的另一条入口。
3. 恢复模式进入的按键组合以官方文档为准（S5 多为「按住 FUNC 键同时开机电源」，
   实测前务必先查文档，不要盲试）。
4. 相机重启后若 `getstate` 不通：先重启相机一次；仍不通再走恢复模式。

## 判定表（阶段 2 结果 → 下一步）

| 阶段 2 响应 | 含义 | 下一步 |
|---|---|---|
| `err_reject`（快，<1s） | 上传时验签，签名先于数据检查 | 预言机死路 → 转「恢复模式是否免签名」验证 + 社区调研 |
| `err_reject`（慢，>1s） | 先做了别的工作（解密/CRC）再拒 | 看耗时分解，可再测 CRC 破坏变体定位顺序 |
| `ok` + 相机正常回来 | 上传时不验签（或签名不覆盖版本字段） | 跑阶段 3 定签名覆盖范围；若数据区改动也被接受 → 预言机成立，可逐字节反推密钥流 |
| `ok` + 相机没回来 | 启动时验签失败 → 变砖 | 走恢复模式；若恢复模式接受无签名固件 → 预言机从恢复模式入口打开 |
| `err_fw_same` | 版本字段猜错（没生效） | 回阶段 1 换字段 |

## 已排除算法清单（本地实测，供后续参考）

- 单字节 XOR、重复密钥 XOR（密钥：`panasonic`、0x220 64B、48B 校验块、loader1 24B/64B、SHA/MD5 派生）
- RC4（密钥：loader1 24B/64B、0x220 64B、24+64 拼接、SHA256/SHA1/MD5 派生，dtb/zimage/rootfs 目标）
- AES-128/192/256 ECB/CBC/CTR（全部候选密钥 × IV=0/前16B/后16B/12B-nonce+4B-counter）
- 48B 校验块 = SHA-384/256/1/MD5/CRC32 的 19 种输入组合（含 name+data、entry92+data、header+data、panasonic 块+data 等）
