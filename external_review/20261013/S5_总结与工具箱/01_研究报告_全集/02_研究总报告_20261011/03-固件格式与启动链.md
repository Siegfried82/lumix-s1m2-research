# 03 · 固件格式与启动链

> 对象 `S5___V29.bin`（90,238,464 B = 0x560EE00，SoC MC801）。本章给出 UPD 容器结构、版本字段精确定位、三重签名、48 分区表与启动链倒推。全部数值脚本可复现（见 `scripts/` 与 `research/FIRMWARE_FORMAT.md`、`research/BOOT_FLOW.md`）。

## 3.1 容器总体布局

| 偏移 | 大小 | 内容 |
|---|---|---|
| 0x000000 | 0x200 (512) | 外层 UPD 头 |
| 0x000200 | 0xA0 | `"panasonic"` 标记 + 64B **ECDSA P-256** 签名（32B r + 32B s）+ 填充 |
| 0x0002A0 | 0x40 (64) | 内层 UPD 头（字段与外层一致） |
| 0x0002E0 | 0x0C (12) | 目录头（数据起点 / 总长 / 每条目校验尺寸） |
| 0x0002EC | 0x1140 | 分区表：**48 条 × 92 字节**（物理至 0x142C，与数据起点 0x1400 重叠 44B） |
| 0x001400 | 0x560D800 | 分区数据（多数加密；前 44B 被分区表尾覆盖） |
| 0x560EC00 | 0x200 (512) | **RSA-4096 签名**（= `S5___V29.sig` 内容） |

## 3.2 UPD 头字段

```
0x00  u32  0x00445055  "UPD\0" 魔数
0x04  u32  0x200       头部大小
0x08  u32  0x200       （重复）
0x0C  char[8]          芯片型号 "MC801"（S5M2=MC8223 / S1M2=MC8243）
0x14  u32  0
0x18  u32  0
0x1C  u32  0x02900290  ★ 版本字段（外层）
0x20  u32  0x00010004
0x24  u32  0x07101450  时间戳/版本
0x2C  u32  3           （引导段数 = loader 数量）
0x34  u32  3
0x38  u32  0x200       数据起始偏移
0x3C  u32  0x0560EC00  数据总长（= 文件长 - 0x200）
0x40  u32  CRC32       zlib.crc32(data[0x200:]) 实测 = 0x8E73AAC0
```

## 3.3 ★ 版本字段精确定位（决定"改版本号绕过版本门"是否成立）

版本字段以 **BCD 4 字节 `[sub][major][sub][major]`** 编码，**同时出现在两处**：

| 位置 | 偏移 | 是否在 CRC 覆盖内 | V29 实测值 |
|---|---|---|---|
| 外层头 | **0x1C** | **否**（CRC 从 0x200 起，0x1C 在外） | `90 02 90 02` |
| 内层头 | **0x2BC** | **是**（在 0x200..end 内） | `90 02 90 02` |

解读：
- `90 02 90 02` = 两个 u16 `0x0290, 0x0290`，即 **V2.90 / V2.90**（`[major=02][sub=90]` 重复两次）。
- 改**外层 0x1C** 不改 CRC（在覆盖外），但改**内层 0x2BC** 会破 CRC，且两处都在签名覆盖域内。
- **结论**：版本号可以写大（`camctrl type=fw_update_mode value=V3.00` 就放行版本门，见 §08.1），但**真正的关卡在签名**（ECDSA P-256 + RSA-4096）。改版本号**不能**绕过签名 → "改版本号绕过版本门"这条线**不成立**，版本门只是防回滚，不是安全边界。

## 3.4 三重签名（容器内无公钥）

| 工件 | 位置 | 大小 | 验证方 |
|---|---|---|---|
| CRC32 | 0x40 | 4 B | BootROM（完整性，非安全） |
| **ECDSA P-256** | 0x220（`"panasonic"`@0x200 之后） | 64 B (r+s) | 片内 BootROM 公钥（**公钥不在文件内**） |
| **RSA-4096** | 0x560EC00（尾块） | 512 B | 片内 BootROM 公钥（非 PKCS#1 v1.5，疑似 PSS/裸 RSA） |

**含义**：容器内无公钥、无"禁验签"开关、无回退标志 → 纯软件无法让相机接受自编 / 篡改固件。唯一"签名 oracle"是相机 `endsenddata` 时的真实验签（当前尚未触达，见 §04）。

## 3.5 目录头（0x2E0）

```
0x2E0  u32  0x1400      分区数据起点
0x2E4  u32  0x560D800   分区数据总长（起点+总长 = 签名前）
0x2E8  u32  0x30        每条目校验块尺寸 = 48 字节
```

## 3.6 分区表条目（92 = 0x5C B / 条，共 48 条）

```
0x00  char[12]  名称（'\0' 填充）
0x0C  u32       数据偏移（文件内绝对偏移）
0x10  u32       大小
0x14  u32       目的加载地址（RAM）；loader1/2/3 上=数据区相对偏移
0x18  u32       类型（2=明文数据区，3=加密区）
0x1C  char[32]  SHA-256(明文) 摘要
0x3C  char[16]  每分区独立 IV（加密分区非零且唯一；数据分区全 0）
0x4C  char[16]  填充（全 0）
```

- **type ↔ IV 关系（48/48 完全吻合）**：`type=2` ⟺ IV 全零（明文，相机可读写）；`type=3` ⟺ IV 非零（加密）。7 个数据分区明文，41 个加密分区。
- 相邻条目 tiling 连续：`偏移[i] + 大小[i] == 偏移[i+1]`。
- 分区表物理终点 0x142C（48×92=0x1140）与数据起点 0x1400 **重叠 44B**（末项 `hr_c_ddr` 的 sha 尾 12B + IV 16B + 零填充 16B），这解释了旧文档"loader1 有 28 字节随机数"的由来。

## 3.7 关键分区

| 名称 | 偏移 | 大小 | 类型 | 说明 |
|---|---|---|---|---|
| loader1 | 0x1400 | 4 KB | 3 | 512B 零头 + 3584B 加密载荷（熵 7.948，真实 BL1） |
| loader2 | 0x2400 | 38 KB | 3 | 加密（BL2/bootstrap） |
| loader3 | 0xBC00 | 48 KB | 3 | 加密（Stubby 类 / RTOS bring-up） |
| program | 0x17C00 | 16 MB | 3 | 加密主固件（相机 OS） |
| zboot | 0x385D400 | 2 KB | 3 | 512B 0xFF 头 + 1536B 加密（zImage 引导 stub） |
| dtb | 0x385DC00 | 4 KB | 3 | 加密设备树 |
| zimage | 0x385EC00 | 2.5 MB | 3 | 加密 Linux 内核 |
| rootfs1 | 0x3ADEC00 | 3 MB | 3 | 加密根文件系统（只读） |
| rootfs2 | 0x3DDEC00 | 10 MB | 3 | 加密（数据 / overlay） |
| history / lens_hist / music / osd* / fileinfo / ninsho_db / koutei_kao / wifi_info / menu_save | … | … | 2 | 明文数据区（相机可读写出厂默认值） |

代码 / 数据 / DSP 分区（loader2 起、zimage、rootfs1/2、dtb、program、ipu/rc/nr/hm/hr_*）均为高熵随机数据（熵 ≈7.8–7.999），**加密**，无 ELF/gzip/squashfs 明文魔数。反编译前必须先解密。

## 3.8 启动链（倒推）

```
上电
 └─ [1] MC801 BootROM（片内固化，公钥在 BootROM/OTP，不可改）
     └─ [2] 容器验证：UPD\0 魔数 + 头 512B + CRC32@0x40 + ECDSA@0x220 + RSA-4096 尾块
            + 版本字段在签名覆盖内 → 降级/改版本必破签名
     └─ [3] 解析 48 分区表；引导段数=3
     └─ [4] 搬运数据区前 90KB（loader1|2|3 连续块）到 RAM 基址，跳 0x0
 [5] loader1(4K, RAM 0x0)  → [6] loader2(38K, 0x1000) → [7] loader3(48K, 0xA800)
 [8] program(16M, RAM 0x80000) —— 主相机固件（相机 OS）
 [9] 运行时按分区表装载：
     ├─ postboot1-5 / eep_* / 数据区（history/lens_hist/music/osd*/fileinfo/ninsho_db/…）
     └─ Linux 子系统：zboot(2K)→zimage(2.5M)+dtb(4K)→rootfs1(3M,只读)+rootfs2(10M,overlay)
[10] 外设固件：usbcharge / ipu / rc / nr（ISP/DSP）/ hm_* / hr_*（DDR 训练）
```

- 90KB 连续引导块（0x1400–0x17C00）：loader1/2/3 的 load 字段正好等于其数据区相对偏移（0x0/0x1000/0xA800），`program` 的 load(0x80000) ≠ 数据区偏移，说明 program 起由 loader 链另址装载。
- 与 Milbeaut（Socionext SC2000a/GP1、SC2006A）参考链映射：loader1≈CM0 supervisor（**推测**），zboot+dtb+zimage+rootfs≈Linux 子系统（**较确定**，命名/布局直证）。
- **关键含义**：验证链最前两级（BootROM→loader1 明文头→加密载荷）不在可改写用户区明文里；明文容器内无公钥、无回退标志，纯软件无法绕过验签。

## 3.9 对旧文档的更正（本轮确证）

| 旧结论 | 更正 |
|---|---|
| "loader1 有 28B 随机 + 全 0 填充 / 本体为空" | 28B 是分区表尾 44B 重叠的一部分；loader1 实为 **512B 零头 + 3584B 加密载荷**（熵 7.948） |
| "zboot 全 0xFF（空）" | 实为 **512B 0xFF 头 + 1536B 加密载荷**（熵 7.865） |
| "load = flash 地址，128KB 对齐" | = **目的地址（RAM）**，不 128KB 对齐；loader1/2/3 该值=数据区相对偏移 |
| 48×92B 表"结束于 0x1400" | 物理结束于 **0x142C**，与数据起点 0x1400 重叠 44B |
