# S5 隐藏录像格式持久化 · 追查与结论（mov 已跨断电持久）

日期：2026-10-13　固件：VD4.30（MC801，研究版）　IP：192.168.1.131（MAC `00:00:00:00:00:00`）

## 一句话结论（已定案）
**mov 容器现在跨断电持久。** 本轮把"mov 开机回落 mp4"的根因查清并当场修复：既不是固件白名单，
也不是影子槽，而是**上一轮的 flash 上传用错了协议**——`persist.py` 用一次 65KB 的 POST 发整个 blob，
而相机对 `type=camsetting` 要求的是**分块 `method=separate` 协议**。那次写入**从未落地**，所以
"重启后 mov 消失"其实只是"mov 从未写进 flash"。改用正确协议（并把 `0x005e` 的 13 个槽一并写 mov）
后，写后立即读回 = mov，拔电池重启后仍 = mov，NTSC 与画质码同样持久。

## 最终实测状态（断电重启后读回）
```
live  ntsc_pal=ntsc   videoformat=mov   videoquality=mov_60p_150mbps_c4k
blob  0x005e payload = 06 06 06 06 06 06 06 06 06 06 06 06 06 00
      ntsc[65230]=0x00(ntsc)  videoquality[6986]=0x92  checksum sum%256==0 ✓
```
容器/null 的 golden 样本（质量仍是 `0x8b` 时抓的）：
`out/blob_GOLD_mov_persisted_20261013_020600.bin`，sha256 `13b59254…`；
质量已按用户选择改为 `0x92`（原因见文末附录：`0x8b` 会让机身菜单变灰）。

## 根因：上传协议用错（决定性发现）
- 相机对 `GET /cam.cgi?mode=startsenddata&type=camsetting&value=65533` 返回
  `<method>separate</method><bufsize>61460</bufsize>`。
- 正确写入必须：按 `chunk = bufsize − multipart 开销 = 61460 − 268 = 61192` 分成
  **61192 + 4341** 两块，逐块 `POST /cam.cgi?mode=senddata`（multipart），块间
  `GET /cam.cgi?mode=requestsenddata`，最后 `GET /cam.cgi?mode=endsenddata`。
- 旧 `persist.py::_upload_payload` 是**单次 POST 全部 65533 字节** → `senddata` 响应超时
  （客户端干等数分钟），`endsenddata` 虽回 `ok`，但数据从未提交。
- 该正确序列在仓库内本来就有实证：`01_研究报告/01_固件AES绕过_调研_20261010/03-离线破解与上传
  预言机/oracle/camset_write_test.py` 的日志（A/C valid-ck → `endsenddata ok`；B 错校验和 →
  `err_reject`）记录了 `senddata @61192`、`senddata @65533` 的分块过程。
- 改用分块后：`senddata @61192 -> ok`、`senddata @65533 -> ok`、`endsenddata -> ok`，全程 ~2s。

**推论修正**：上一轮"flash 写进三项、开机被固件重新派生为 mp4"的推断**不成立**（写入从未发生）。
因此 **H2「固件白名单」没有任何证据支持**，可以撤下。

## 影子槽实验（已执行）
`experiment_mov_shadow.py --confirm` 把偏移 3062..3074 共 13 字节全写 `0x06`、保留 3075=`0x00`、
重算校验和；确认只改这 13 字节 + 校验和。写入 → 拔电池 → 重启后 13 个槽与活动值**全部保持 mov**。

诚实边界：本次 13 个槽（含活动槽 slot0）是一起写的，因此**"是否必须同时写影子槽"未被单独隔离**。
但既然固件在重启后没有改动任何一个槽，此前"活动槽被派生/回退"的现象已由上传 bug 完全解释；
单写 slot0 是否同样足够，属未做的可选项，不影响当前可用结论。

## camsetting blob 结构（本轮解析成果）
65533 字节：44 字节头（`"Panasonic"`+`"DC-S5"`）+ 8 字节前导（offset 44..51，含 `0xffcc`）
+ TLV 记录流（offset 52 起，`[field_id u16 LE][len u16 LE][flag u16 LE][payload: len-6]`），
共 **831** 条记录，记录流止于 65528，尾部 `ff ff 00 00` + 校验和字节 65532。

| 字段 | record | 文件偏移 | 说明 |
|---|---|---|---|
| videoformat（容器） | `0x005e` | 3062（活动值） | 14 字节 payload：byte[0]=活动容器，byte[1..12]=12 个记忆/影子槽，byte[13]=`0x00` |
| videoquality | `0x0124` | 6986 | 13 槽 u16 数组，槽 0 = 选中码，其余 `0x00c0` |
| ntsc_pal | `0x0495` | 65230 | 0x00=ntsc / 0x01=pal |
| 校验和 | — | 65532 | `(256 − Σ(byte[0..65531])) mod 256` |

容器取值：`0x05`=mp4，`0x06`=mov，`0x08`=mp4hevc（已弃用）。
运行时 `setsetting videoformat=mov` 只改 byte[3062] + 校验和（已实测复现）。

## 同族交叉证据（S5II / S5IIX，见 `out/S5II_slot_crosscheck_20261013.md`）
- S5II：slot0=`05`(mp4) 而 **slot1=`06`(mov)**；S5IIX：slot0=`06`、slot1=`06`。
- 说明 slot0 之外是**真实的记忆槽**，可被固件写入并跨导出保留；也说明"任一槽=mov ⇒ 开机活动槽=mov"
  并不成立（S5II 有 mov 槽仍活动 mp4）。
- S5 槽数 13（8-bit 字段尾部多一个 `0x00`），S5II/S5IIX 为 14；引用 JSON 的 `data_head_hex` 是
  **截断到 17 字节**的头，不是完整 payload。

排除项：blob 内**没有**独立的「默认容器 / 白名单 / 注册格式表」字段（全量 831 字段扫描），
也没有第二个随 mov↔mp4 变动的字段。PTP 侧（S1M2）亦无录制容器字段——容器只存在于非易失设置流里。

## 附：机身菜单「录制质量」变灰的根因与修复（10-13 用户报障）
**现象**：NTSC + MOV 下，机身菜单的【录制质量】整项是灰的、选不了。（App/接口侧一切正常。）

**根因**：flash 里 `videoquality` 的代码 `0x8b = mov_60p_200mbps_c4k_10bit` **不在机身菜单定义
`allmenu` 里**。把 `getinfo allmenu`（机身菜单）与 `getinfo curmenu`（App 看到的可用项）做集合差：
`curmenu` 有、`allmenu` 缺的 mov 质量档**恰好只有这一个**。机身菜单找不到与"当前值"匹配的条目，
于是把整项置灰。
> 注意：`allmenu` 的 mov 列表里**有** `mov_60p_200mbps_4k_10bit`（3840×2160），只是没有
> `..._c4k_10bit`（4096×2160）。这是 S5 机身菜单未声明 C4K 顶档，不是我们改坏了菜单。

**修复**：把持久化的质量换成 `allmenu` 已声明的同级档——
`mov_60p_200mbps_4k_10bit`(`0x9b`) 或机身菜单里任选一档。用户最终选定
`mov_60p_150mbps_c4k`(`0x92`)，写入 flash 后**拔电池重启仍可选、值保持**。
新增一键工具 `persist_quality.py`：先校验名字在 `allmenu` 中已声明，再 `setsetting` 生效，
最后把当前 blob 分块写入 flash。

**部分代码表（实测）**：`0x8b`=mov_60p_200mbps_c4k_10bit（机身菜单无）、
`0x92`=mov_60p_150mbps_c4k、`0x94`=mov_30p_150mbps_c4k_10bit、`0x96`=mov_24p_150mbps_c4k_10bit、
`0x97`=mov_24p_100mbps_c4k、`0x9b`=mov_60p_200mbps_4k_10bit、`0xc1`=mp4_30p_20mbps。

**操作坑（重要）**：机身**停在菜单界面时**，`getinfo camsetting` 一律回 `err_reject`（86 字节），
而 capability/allmenu/curmenu 正常。退出菜单回到普通拍摄画面后立刻恢复（连续 3 次成功）。
`download_blob` 已加显式提示。

**工具同步**：`persist.py restore` 的默认质量由 `0x8b` 改回 `0x9b`（避免把机身菜单搞灰）；
`verify` 判决不再只认 `0x8b`，现按代码表报出质量名。新增 `persist_quality.py`。

## 结论更正史
- 2026-10-13 早先：把"随机断电后 mov 回落"判为格式字段不可持久，`01_成果总表.md` H1 降至 ◐。

  **mov 已跨断电持久**，H1 恢复 ✓。教训：**在断言"固件不持久某字段"之前，先独立验证写入确实落地**
