# S1H 隐藏格式交付包分析 + S5 的 `mp4ed` 容器发现（2026-10-13）

## 0. 来源与可读性

用户从微信收到 `Panasonic_hidden_format_research_20261012/`（另一研究者的 S1H 交付包）。
微信路径 `<LOCAL_USER>/Library/Containers/com.tencent.xinWeChat/Data/...` **被 macOS 隐私保护
（TCC）挡住**（`Operation not permitted`，非 DSH 沙箱），当前进程无法读取。
仓库内 `01_研究报告/05_Panasonic_hidden_format_参考/` 是**同一交付包**，且已用其自带
`programs/check_package.py` 校验：**42 个文件、0 错误**，完整无损。本文件基于仓库这份副本分析。

## 1. 交付包讲了什么（要点）

- 对象：**DC-S1H**（V2.8，PAL）。S5 明确标注"未由本研究实机复现"。
- 方法论与我们一致：`allmenu`（完整菜单声明集）与 `curmenu`（当前启用集）**做集合差**，
  再对候选做**单项 `setsetting` + 连续精确读回**。
- 证据分级 E1–E5：原始菜单 → setter+读回 → 机身菜单显示 → **实际媒体完整解码** → 重启保留。
  它强调 **E2（setter ok + 读回准）≠ 能录制**，必须实拍解码（E4）。
- S1H 唯一取得实际媒体的隐藏档：**`mp4ed_25p_400mbps_4k_10bit`**
  → 3840×2160 25p、H.264 **4:2:2 10bit ALL-I**、**LPCM**、400Mbps 标称；
  机身菜单显示 **MP4(LPCM)**，一次正常重启后保留。另有 `mp4_25p_10mbps`（720p）对照。
- 16 个候选中 14 个"读回准确"但**只有 2 个录出真媒体**；并记录两类失败：
  `setter=ok 但 getter=err_critical`（无效）、**静默映射到别的格式**（如 mp4ed_50p_150mbps_4k → avchd_50p_28mbps）。
- 关键结构信息（S1H）：CAMSET 66,933 B / 848 记录 / 记录起点 0x34 / 终止 `ffff 0000`；
  **`0x5e` 首字节 = 格式编号**：AVCHD=`0`、MP4=`5`、MOV=`6`、**MP4ed=`7`**；
  质量记忆项 `0x122`=AVCHD、`0x123`=MP4、`0x124`=MOV、**`0x16e`=MP4ed**。

## 2. 对我们最有用的三条（已用于 S5）

1. **格式编号表** → 我们此前只试过 `0x05/0x06/0x08`，据此补测 **`mp4ed = 0x07`**。
2. **分家族质量 tag** → 纠正了"质量只看 0x124"的错误；S5 上 mp4ed 的质量实际写在 `0x122`。
3. **失败模式目录** → 我们 5.9K 遇到的"setter ok 但无效"在 S1H 报告中早有记录，可直接对照定性。

## 3. S5 实测：`mp4ed` 容器

| 测试 | 结果 |
|---|---|
| `setsetting videoformat=mp4ed` | ✅ `ok`，读回 `mp4ed`，blob `0x5e` byte0 = **`0x07`** |
| 进入 mp4ed 后的自动质量 | **`mp4ed_60p_100mbps`**（`getsetting` 正常） |
| 显式写任意 `mp4ed_*` 质量 token | ❌ 掉回 `mp4_60p_28mbps` 或 `err_critical`；**44 个 NTSC 候选 0 个读回正常** |
| `videoformat=avchd` / `mp4hevc` | ✅ 分别得 `0x00` / `0x08`，与 S1H 编号表一致 |

其他容器字节（S5 实测）：`0x00`=avchd、`0x05`=mp4、`0x06`=mov、`0x07`=mp4ed、`0x08`=mp4hevc。

### 3.1 实拍验证（E4）

`mp4ed_60p_100mbps` 实拍文件 `DCIM/100_PANA/P1000005.MP4`：

```
1920×1080 @59.94fps · H.264 High(8bit 4:2:0) level 5.0 · ~96.6 Mbps
音轨 PCM('twos') · 300 帧 / 5.006s · GOP: stss=10 个关键帧 → 30 帧 GOP（非 ALL-I）
```

结论：**S5 的 `mp4ed` = "MP4 + LPCM" 1080p60 高码率档**，是真实的隐藏格式
（普通 S5 MP4 用 AAC，这里换成 PCM），但**不是** S1H 那种 4K 4:2:2 10bit ALL-I/400Mbps。

## 4. 结论

- 这份包**有用**：提供了跨机型对照的格式编号表与质量 tag 布局，直接让我们发现了 S5 的
  `mp4ed` 容器（此前完全没试过），并拿到了一个真实的隐藏档 `mp4ed_60p_100mbps`（MP4+LPCM 1080p60）。
- 但它**不能**把 S1H 的 400Mbps ALL-I 4K 移植到 S5：S5 的 mp4ed 质量 token 全部读回失败。
- 同 S1H 报告的经验一致：**setter 返回 ok 毫无意义，必须实拍解码**。本包对有疑问的
  `err_critical` / 静默映射两类失败给出的判据，与我们 5.9K 的结论互相印证。
- 代价提醒：进入 `mp4ed` 同样会让机身【录制文件格式/质量】变灰（它不在 `allmenu` 里），
  且 1080p 码率档对本项目价值有限，故**未写入 flash**，仅做了 RAM 验证后恢复。

## 5. 追加：`mp4ed` 残留态、"（LPCM）"条目的成因，与恢复

用户随后观察到：机身【录制文件格式】里多出一个 **"(LPCM)"** 条目（内部显示 AVCHD），
且【录制文件格式】与【录制质量】**双双变灰、无法修改**。诊断结果：

```
live  videoformat = mp4ed        quality = mp4ed_60p_100mbps
flash 0x5e byte0  = 0x07 (mp4ed)  ← 已写入 flash
```

**两个重要结论：**

1. **`setsetting` 会被相机自动存盘（纠正我们此前的"RAM-only"假设）。**
   我们只在 RAM 里切过 `mp4ed`，但 flash 已被写成 `0x07`，所以重启后仍是灰的。
   ⇒ 以后做容器/质量实验后，**必须显式回写一个声明值**，否则会留下持久残留。
2. **"(LPCM)" 条目 = 当前"未声明容器"在格式选择器里的渲染，它和变灰是同一件事的两面。**
   `allmenu` 只声明 `mp4 / mp4hevc / mov`；`avchd`/`mp4ed` 不在其中 → 当前值匹配不到菜单项
   → 格式项与质量项一起置灰，同时当前值被当作一个"额外条目"显示出来。
   **两者无法同时成立**：让条目显示的条件，正是让菜单变灰的条件。
   且 **S5 没有 S1H 的"添加到列表（My List）"机制**（全量扫描菜单项，无任何 list 项），
   所以 S1H 报告里"注册进列表后长期进入"的路子在本机不存在。

**恢复**：把容器与质量换回声明值并回写 flash 即可（已执行）：

```bash
python3 container_switch.py mov --persist     # 0x5e=0x06（声明档），菜单恢复
```

实测：写回后**两项均可正常修改，"(LPCM)" 条目消失**。

**想要 MP4(LPCM) 时**：用新增的 `container_switch.py` 随时切进去，用完切回来：

```bash
python3 container_switch.py mp4ed     # 进入 MP4(LPCM) 1080p60（菜单会变灰，属预期）
python3 container_switch.py mov       # 切回声明档，菜单恢复
python3 container_switch.py status    # 只读查看 live + flash
```

## 6. 未做 / 可继续

- `mp4ed` 与普通 MP4 在画质/宽容度上的实际差异（同一场景 A/B 实拍）未做。
- S5 的 `0x16e`（S1H 的 MP4ed 质量项）在 S5 上似乎未被使用（改质量动的是 `0x122`），
  字段家族映射 S5 与 S1H 存在差异，尚未完全厘清。
