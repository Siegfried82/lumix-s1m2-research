# 版本门证伪 + 握手卡死根因与修复

> 本文是本研究**最核心的成果**：一条看似可走的"改版本号绕过版本门"路线被证伪；
> 而真正反复卡死相机的"invalid login / 需要重启"根因被定位，并给出了**可稳定复现的修复**。

---

## A. "改版本号绕过版本门"—— 不成立（已证伪）

**假设**：相机要求"更新 App"，是不是因为它比对了客户端版本号？若把版本号改高就能绕过？

**结论：不成立。** 三个独立证据互相印证：

1. **字段方向**：`comm_proto_ver=10.0` 只出现在 `getinfo&type=capability`（**相机→App** 单向），
   是相机告诉 App"我支持协议版本 10.0"，**不是**校验 App 的版本。

2. **握手不带版本**：`accctrl&type=req_acc` 的握手请求**不携带任何客户端版本字段**，
   只有 `value=<UUID>` 和 `value2=<设备名>`（App 用的是 `Build.MODEL`，S5 并不校验它）。
   也就是说，**相机在握手阶段根本没有"App 版本"可以比对**。

3. **反编译无比较逻辑**：反编译 LUMIX Sync 后，App 侧把 `protoVer` 存成一个**普通 getter**，
   **没有版本比较 / 拒绝分支**。"请更新此应用程序"对应的是**通用连接失败文案**
   （`msg_error_connect_app_need_update`），只要连接态异常就会弹，**与版本无关**。

**推论**：想"改版本号"绕过，根本没有可改的字段，也没有比对逻辑可绕。此路**彻底关闭**。

---

## B. 反复"invalid login / 需要重启"的真正根因

**现象**：多次出现相机提示 "an invalid login occurred"，要求重启相机；
伴随 `getstate` 返回 `err_unsuitable_app`（App 界面显示"需要更新"）。

**根因**：相机端 `accctrl` 模块只有**一个"待批复(pending)"槽位**。
一次**没有被正确清理**的 `req_acc` 请求会**残留在该槽**，成为【陈旧 pending 请求】。
下一次 `req_acc` 撞上这个残留 → 会话态被污染 → 相机报 "invalid login / 需要重启"。

> 这就是为什么"相机时好时坏、一急就崩"：问题不在你发了什么"坏包"，
> 而在于**上一次连接没有干净收尾**，把毒留给了下一次。

**正确做法（来自反编译 LUMIX Sync）**

参考 `service/a.java:270-296` + `service/c.java:668`：

- 一整个握手尝试**只用同一个 uuid**（`ok_under_research` 时用同一 uuid 温和重发）；
- 在**每一个终止路径**（成功、失败、用户取消、超时）都用**同一个 uuid** 发一次 `req_acc_can`，
  把那次 pending 请求清理掉；
- **绝不**用 `req_acc_can` 去打断一个已经 `ok` 的会话；
- **绝不**快速连发 `req_acc`（会撞满 pending 槽）。

---

## C. 修复实现（safe_handshake.py v2）

`scripts/safe_handshake.py` 已按上述规则实现 v2：

- 只读预检 `getstate`（单次，绝不重试）。
- 一次干净 `req_acc`（同一 uuid）；`ok_under_research` 时按 `--poll-delay` 温和重发**同一 uuid**
  （保持相机"允许连接"提示存活），请用户在相机上按 OK。
- 相机一旦掉线立即停手、温和探活，绝不连发。
- 结束若非 `ok`：用**同一 uuid** 发一次 `req_acc_can` 清理陈旧 pending（`--no-cleanup` 可关），再 `getstate` 复查。

**用法**
```bash
python3 safe_handshake.py --ip 192.168.1.131
python3 safe_handshake.py --ip 192.168.1.131 --polls 6 --poll-delay 2.5
python3 safe_handshake.py --ip 192.168.1.131 --verify   # 成功后只读回读确认
```

**效果**：按此修复后，**可稳定获得干净的会话**（`getstate` 持续 `ok`），不再触发
"invalid login / 需要重启"。

## D. 附：协议 / 字段参考

- 端点：`http://<ip>:80/cam.cgi?mode=<m>&type=<t>&value=<v>&value2=<v2>`
- `req_acc` 的 `value` = UUID `4D454930-0100-1000-8001-<12hex>`；`value2` = 设备名（App 用 `Build.MODEL`，S5 不校验）。
- `req_acc` 结果：`ok` / `ok_under_research` / `ok_under_research_no_msg` / `err_user_refused` /
  `err_others_requesting` / `err_reject` / `err_busy` / `err_param`。
  - `ok` 返回 4 字段 `ok,S5-70E253,remote,encrypted`，**无 token** → **不存在 X-SESSION_ID**（无 cookie 会话）。
  - `err_others_requesting` = 另一客户端（多为手机 App）正持有该 IP 的会话。
- `getstate` 结果：`ok`（健康）/ `err_unsuitable_app`（连接态被污染）/ `err_reject`。
- `getsetting` 响应格式：`<camrply><result>ok</result><settingvalue <key>="<value>"/></camrply>`
  （**值是属性 attribute**，不是子节点）。
- `setsetting`：`mode=setsetting&type=<cmd_type>&value=<value>` → `<result>ok</result>` 表示接受。
