# 固件验证逻辑漏洞分析笔记（公钥来源 / 回退路径 / 降级字段）

对象：`fw_fetch/S5___V29.bin`（90,238,464 B = 0x560EE00，MC801）
扫描器：`fw_fetch/scan_verify.py`（只读，不改动固件文件）
对比样本：`fw_fetch/fw_sample.bin`（S5m2_V31.zip 前 64 KiB，解压得 S5m2_V31.bin 前
0x10ADD 字节；完整 205 MB `S5m2_V31.bin` **不在本地磁盘**，故 S5m2 的末尾 RSA 签名块
与完整分区表无法对比，仅能对比头部/安全头区域——该区域恰好落在样本内）。

本任务结论用证据编号 E1..E8 引用，每条含偏移+十六进制+文件名。

## 三个核心问题的答案

### 问题 1：容器明文里是否内嵌任何公钥？→ 否。

Phison 式「公钥在镜像内、可同时替换公钥+签名」攻击**不可行**：RSA-4096 与 ECDSA
P-256 的验签公钥都不在容器里，只能来自芯片 BootROM / OTP / 硬件。

证据：
- **E1 无 PEM**：全 90 MB 中 `-----BEGIN`（含 PUBLIC KEY / RSA PUBLIC KEY /
  CERTIFICATE / EC PUBLIC KEY / PRIVATE KEY 各变体）出现 **0 次**。
  `scan_verify.py` 输出全部 `none`。
- **E2 无 DER 结构**：明文区（0x0-0x1400 头+分区表、0x1400-0x2400 loader1、
  0x560EC00-0x560EE00 尾部）中，以下 ASN.1 结构全部 `none`：
  - X.509 v3 版本块 `A0 03 02 01 02`
  - RSA SPKI OID `06 09 2a 86 48 86 f7 0d 01 01 01`（rsaEncryption）
  - RSA SPKI 全头 `30 82 02 22 30 0d 06 09 2a 86 48 86 f7 0d 01 01 01`
  - RSAPublicKey 4096-bit 模数 INTEGER 长度 `02 82 02 01 00`
  - RSA 指数 65537 `02 03 01 00 01`
  - EC SPKI OID `06 07 2a 86 48 ce 3d 02 01` / P-256 曲线 OID
    `06 08 2a 86 48 ce 3d 03 01 07`
  - EC 未压缩点 BIT STRING `03 42 00 04`
- **E3 无在曲线上的 EC 点**：对全文件做「04 || 32B X || 32B Y」扫描并校验
  `y² ≡ x³−3x+b (mod p)`（用生成元 G 自检通过），明文区**0 个在曲线上**；全文件
  343,474 个 0x04 字节中也 **0 个**在曲线上（随机 64 字节落在 P-256 曲线上的概率
  ≈2^-255，该检测几乎零误报）。即没有任何可当作 EC 公钥的点。
- **E4 `0x30 0x82` 全部在密文区**：全文件 1370 处 `30 82`（长 SEQUENCE），第一处
  @0xDBDA（loader2 加密区，>0x2400），全部为加密载荷随机噪声；明文头+分区表
  （0x0-0x1400）内**0 处**。
- 旁证：`research_repos/*_notes.md` 已记录「头部保留区无 key blob / 无 PKCS#7-CMS
  包裹块」，与本扫描一致。

### 问题 2：是否存在明文回退标志或次级验证路径？→ 未见。

明文容器里只有一条验证链，没有任何「跳过验证/回退」标志或第二条签名路径。

- **E5 保留区全零**：外层头 0x44-0x1FF、安全头 0x209-0x21F、安全头 0x260-0x29F
  全部为 0x00（`scan_verify.py` hexdump 可查）。这些是唯一能放「disable-verify」
  标志的位置，全零 = 无标志。
- **E6 标记唯一**：`panasonic` 全文件只出现 1 次 @0x200（无第二/回退安全头）；
  `UPD\0` 出现 2 次 @0x0、@0x2A0（外层/内层头，非回退）；`MC801` 出现 2 次
  @0x0C、@0x2AC。
- 验证相关工件恰为三件，无更多：
  1. `0x40` u32 CRC32 = `zlib.crc32(data[0x200:])`（**仅完整性，无密钥**，攻击者可
     重算）；S5 实测 0x8E73AAC0 吻合。
  2. `0x220` 64 字节 ECDSA P-256（r=0x9ACF…C7A、s=0xDC0E…510E，r,s ∈ [1,n-1]
     合法标量——支持「P-256 签名」判定，但不证明验签内容）。
  3. 文件末尾 `0x560EC00` 512 字节 RSA-4096（= `fw_fetch/S5___V29.sig` 内容，
     byte 级相等）。分区表内还有每分区 32 字节 SHA-256（明文内容完整性），属被签名
     覆盖的数据而非独立验证路径。

### 问题 3：版本字段位置，以及是否被签名覆盖？→ 0x24（外层）/0x2C4（内层重复），被签名覆盖。

**降级攻击不能只改版本字段而不破坏签名。**

- **E7 版本字段 = 0x24（u32），内层头 0x2C4 重复同一值**：
  - 外层 `0x24` = `50 14 10 07`（LE）= 0x07101450；内层 `0x2C4` = 相同。
  - 字节 07 10 14 50 是合法 BCD → 判为 **MMDDHHMM 构建时间戳**（07/10 14:50），
    不是明文版本号 "2.9"。S5m2 的 `0x24` = 0x09241744（09/24 17:44）同为 BCD，
    支持该判读。头部**没有**明文 "2.9"/"3.1" 字符串。
- **覆盖关系**：
  - CRC32 @0x40 覆盖 `data[0x200:]`（从 0x200 到文件尾，含内层头、分区表、密文、
    尾部 RSA 签名）。**外层 0x24 不在 CRC 覆盖内**（0x24 < 0x200），但**内层 0x2C4
    在 CRC 覆盖内**。
  - RSA-4096 尾部签名按结构应覆盖 `data[0x200:0x560EC00]`（其之前的全部载荷），
    故**内层 0x2C4 也在 RSA 覆盖内**；0x200 之前的 0x24 只可能由 ECDSA 覆盖。
  - ECDSA @0x220 覆盖范围无公钥无法实测，但按结构最可能是外层头（0x0-0x200），
    即**外层 0x24 被 ECDSA 覆盖**（判定为强假设，未验签）。
- **攻击代价**：改版本需同时改 0x24 与 0x2C4（两处须一致）；改内层 0x2C4 会破坏
  CRC（可重算，无秘密）但**必然破坏 ECDSA 与 RSA-4096（无密钥无法重签）**。故
  「只改版本字段」的降级在文件层面被签名阻断。**未定**：设备开机是否真验
  ECDSA/RSA、是否做单调版本比较——这些逻辑在加密的 loader2/loader3/BootROM 里，
  仅从明文容器无法判定。

## 其他有价值的发现

- **E8「loader1 的 28 个非零字节」其实是分区表尾部，不是 loader 内容**：
  0x1400-0x141B 的 28 字节 = 第 48 条目录项（`hr_c_ddr`，0x13D0 起）的
  SHA-256 后 12 字节（`45c07d280ba270b9996963c6`）+ 该条目 16 字节 IV
  （`ff0bebb956078576a4678df1ea86c71b`）。48 条 × 92B = 0x1140，目录物理结束于
  0x142C，与目录头声明的数据起点 0x1400 有 **0x2C 字节重叠**；loader1 自身载荷
  （0x1400-0x2400）除表尾外**全 0**。这说明「loader1 是 28 字节随机数」的旧描述
  实为目录项尾字段，loader1 内容为空。
- **E9 RSA 尾块不是 PKCS#1 v1.5**：首字节 `89 a1`（v1.5 应为 `00 01`），512 字节中
  511 个非零 → 更可能 RSA-PSS 或裸 RSA 签名；4096-bit 模数对应的验签公钥不在
  容器内（见问题 1）。
- **E10 跨机型字段变化**（S5/MC801 vs S5m2/MC8223，样本内逐 u32 对比）：
  随机型/版本变化：0x0C 芯片（`MC801`/`MC8223`）、0x1C 机型 id（`0x02900290`/
  `0x15031503`）、0x24 时间戳、0x3C 数据长度（`0x560EC00`/`0xC427A00`）、0x40
  CRC、0x220 ECDSA（64B 完全不同）。
  跨机型**不变**：0x00/0x04/0x08 魔数与头大小、0x14/0x18/0x28/0x30（全 0）、0x20
  板号 `0x00040001`、0x2C/0x34（=3）、0x38（=0x200）、0x200 `panasonic` 标记
  （32B 完全一致）。→ 结构与板号共享，芯片/机型/版本/签名逐构建变化。

## 方法说明（供复核）

`python3 fw_fetch/scan_verify.py` 会：
1. 打印 0x00-0x40 外层头、0x200-0x2A0 安全头、0x2A0-0x2EC 内层头+目录头、
   0x1400 起 loader1 区、0x560EC00 起 RSA 尾块的十六进制；
2. 打印 0x220 的 r/s 与 P-256 标量合法性、CRC32 重算吻合性、tail==sig 相等性；
3. 扫描 PEM / DER SPKI / RSAPublicKey / X.509 / EC 点并标注明文区 vs 密文区；
4. 对比 S5 vs S5m2（取自 fw_sample.bin 解压）。

未做/限制：无公钥 → 无法实测 ECDSA/RSA 的覆盖范围与验签结果；完整 S5m2_V31.bin
不在本地 → 无法对比 S5m2 尾部 RSA 签名块与完整分区表；不涉及解密、不碰相机。
