# VILTROX EF-L / EF-L Pro 转接环固件（Ver 2.4）解包与密钥访问攻击面分析

> 分析对象：VILTROX EF-L / EF-L Pro 卡口转接环固件镜像（`EF-L 2.4.ecp`，Ver 2.4 / 2023.9.25）
> 关联研究：Panasonic LUMIX DC-S1RM2 (S1R II) FunctionFS 内核越界读写（OOB）+ `pvc_mass_storage` 用户态 CDB 执行
> 分析方式：纯静态（无实机转接环 / 无厂商烧录工具）
> 语言：简体中文

---

## 0. 摘要（TL;DR）

1. **解包成功**：`EF-L 2.4.ecp`（59392 B）是一个 **VILTROX 私有烧录包容器**，内部由 1 个版权头块 + 115 个 `_Best->` 帧（每帧 512 B = 8 B 魔数 + 4 B 序号 + 500 B 载荷）组成。有效固件 = 序号 0..112 共 113 帧的 500 B 载荷拼接 = **56500 B**（约 64 KB MCU 的 86%）。
2. **固件性质：这是一张"标定 / 校准数据镜像"，不是可反汇编的常规可执行文件。** 证据充分：
   - 内部布局 = 96 B 头 + 904 B 全 `0xFF` 擦除区 + 稀疏 4 字节记录表 + 约 55 KB 密集记录区；
   - **未压缩**（zlib/deflate/lzma 在多个偏移均失败，无魔数）；
   - **未加密**（全文件最大 64 B 滑动窗口熵仅 5.84，真实随机 ≈ 7.9；字节直方图强偏斜，256 个取值全出现 → 真实数据而非密文）；
   - **不是 ARM/Thumb/RISC-V 代码**（整体反汇编得垃圾指令；56 KB 内仅 ~20 处"像函数序言"的巧合匹配，无成簇的函数体）。
   - 密集区高频 u16 值可解读为 **Q1.15 定点的 AF / 光圈电机控制系数**（增益、行程、加速度曲线）。
3. **密钥材料评估：镜像内没有任何明文密钥 / 证书 / 签名。** 两个附加帧（序号 113/114）不是代码签名，而是小段标定数据（其中序号 114 恰为 128 B 数据 + `0xFF` 填充，但内容是重复的 `0x86/0x4d/0x06` 记录模式，熵 5.9，非高熵签名）。
4. **最关键的结论（密钥如何被访问）**：`.ecp` 文件本身**就是该转接环 MCU 的闪存内容**——也就是说"标定密钥"（电机标定数据）**已经被解出来了**。真正有价值、且**不在**这张公开镜像里的密钥（OTP/fuse 唯一 ID、镜头认证密钥、安全区数据），必须通过**设备侧攻击面**去访问，共四条路径：
   - **A. I2C 命令处理面**（相机 = I2C 主机 → 可借 S1RM2 OOB 让相机发畸形 I2C 打转接环 MCU 的 I2C 处理器）——与本研究链最契合，但需实机动态验证；
   - **B. 固件更新协议**（`.ecp` 烧录；容器内**未见签名** → 更新协议可能未鉴权，可回植带 dump 功能的镜像）；
   - **C. 调试接口**（SWD/JTAG；若 MCU 未锁 SWD，物理接触即可直接读走整片闪存，包括 OTP 外的所有数据）；
   - **D. USB-C 更新口**（多数 VILTROX 环带 USB-C 升级口，主机侧可控）。
5. **诚实的边界**：因为拿到的镜像是"数据分区"，**无法静态定位 I2C 处理器里的具体越界写 / 命令注入 bug**。确认 A 路径需要：拿到 MCU 的**代码镜像**（可能是另一个 `.ecp` 或厂商烧录工具的 flash 转储）做反汇编审计，或用可控相机对实机做 I2C fuzz。

## 2. 容器格式与解包

### 2.1 整体布局

```
0x0000 ┌──────────────────────────────────────────────┐
       │ 帧0：版权头块（512 B，非 _Best-> 帧）          │
       │   [0x00..0x28] "Copyright of VILTROX          │
       │                 Technology Co., Ltd.\0"        │
       │   [0x64] u32 LE = 0x0000E800 (总长 59392)     │
       │   [0x68] u32 LE = 0x0000DCB4 (载荷 56500)     │
       │   [0x6C] u32 LE = 0x00000017 (23, 含义未定)    │
       └──────────────────────────────────────────────┘
0x0200 ┌──────────────────────────────────────────────┐
       │ 帧1..帧115：_Best-> 载荷帧（115 个，各 512 B）  │
       │   每帧 = [0:8]"_Best->\0"                      │
       │          [8:12] u32 LE 序号 (0,1,2,...,114)    │
       │          [12:512] 500 B 载荷                    │
       └──────────────────────────────────────────────┘
```

- **115 个 `_Best->` 帧**，序号严格为 `0..114`（已逐帧校验，无缺号）。
- **有效固件 = 序号 0..112 的 500 B 载荷拼接** = 113 × 500 = **56500 B**，与头内 `[0x68]=0xDCB4` 完全一致（解包自洽）。
- **序号 113、114 两个帧不并入固件**，是容器附加的 2 个小数据块（见 §5）。
- 全部 116 块 × 512 B = 59392 B = 文件总长，与 `[0x64]=0xE800` 一致。

### 2.2 解包脚本（可复现）

```python
import struct
ecp = open("EF-L 2.4.ecp","rb").read()
sig = b"_Best->\0"
offs = [i for i in range(len(ecp)) if ecp[i:i+8] == sig]   # 115 帧
fw   = b"".join(ecp[o+12:o+512] for o in offs[:113])       # 序号0..112
open("efl_firmware.bin","wb").write(fw)                      # 56500 B
# 校验：len(fw) == struct.unpack("<I", ecp[0x68:0x6c])[0]  # 0xDCB4 == 56500 ✓
```

产物：`efl_firmware.bin`（SHA256 `2bf111a286496dfb2b037c7c40e8c6c0e222ce26aec576bbbd95b33634799f8f`）。

## 3. 固件镜像内部结构

对 56500 B 做字节密度剖面（每 256 B 统计非 `0xFF`/非 `0x00` 占比与不同字节数），得到稳定分段的内部布局：

| 偏移区间 | 大小 | 内容 |
|---|---|---|
| `0x0000 – 0x005F` | 96 B | **结构化头**（魔数 + 参数）。前 8 个 u32 LE：`0xa0ab0022, 0x00290010, 0x80190007, 0x00309700, 0x1a001700, 0x3a003c00, 0x3a000000, 0x80007fff`；其后为小整数（如 `0x0e d1`=3793、`0x0d a9`=3529，疑似计数 / 偏移） |
| `0x0060 – 0x03E7` | 904 B | **全 `0xFF` 擦除区**（未用闪存） |
| `0x03E8 – ~0x0600` | ~500 B | **稀疏 4 字节记录表**：大量 `0x00`/`0xFF` 间隔中散布 `04 01 83 4X`（LE 字节 `04 01 83 4X`，XX 从 0x42 递增到 0x4f 后重复）、少量 `04 01 b0 70`、`04 01 b1 1c`；疑似表项索引 / 寄存器映射 |
| `~0x0600 – 0xDCB4` | ~55 KB | **密集记录区**（主体）：4 字节结构化记录连续排布，非随机、非压缩、非加密，是 AF / 光圈**电机标定表**（增益 / 行程 / 加速度曲线） |

密集区高频 u16（按出现次数，可解读为 Q1.15 有符号定点）：

| u16 | 次数 | Q1.15 解释 |
|---|---|---|
| `0x3F50` | 高 | +0.79（增益 / 比例系数） |
| `0x3B50` | 高 | +0.72 |
| `0x5E08` | 高 | +1.37 |
| `0x5F80` | 48 | +1.98 |
| `0x0E20` | 高 | +0.22 |
| `0x1080` | 高 | +0.40 |
| `0x3FD0` | 高 | +0.99 |
| `0x8010`/`0x8104` | 数百 | −1.00 / −0.99（表区 `04 01 83 4X` 的字节碎片） |

这些取值（0~2.0 区间的定点数，且成对 / 成簇出现）与**电机闭环控制的增益、位置、速度、加速度参数表**高度吻合。

## 4. 固件性质判定：标定数据镜像，非可执行代码

| 判定项 | 证据 | 结论 |
|---|---|---|
| 是否压缩 | zlib / raw-deflate / lzma 在 `0x0000 / 0x0060 / 0x03E8 / 0x0600 / 0x0B20` 等多偏移均解压失败；无压缩魔数（`78 9C`、`FD 37`、`5D 00` 等） | **否** |
| 是否加密 | 全文件最大 64 B 滑动窗口熵 = **5.84**（真实随机 ≈ 7.9）；字节直方图强偏斜（`0x00`=8.8%、`0x80`=6.4%、`0x10`=2.7%、`0x01`=2.3%、`0x04`=1.9%…），256 个取值全部出现 | **否**（真实数据） |
| 是否代码 | 整体按 ARM / Thumb 反汇编得垃圾（`0x0000` 处 ARM=`adcge r0,fp,r2,lsr #32`、Thumb=`movs r2,r4`）；全文件 Thumb"函数序言"式匹配仅 ~20 处、ARM 仅 1 处，无成簇函数体 / 调用图 / 常量池 | **否**（非 ARM/Thumb/RISC-V 可执行形态） |
| 是否含密钥 | 无 64 B 高熵块（最大 5.84）；无 `30 82`（DER 证书 / RSA 签名）、无 `-----BEGIN` 等密钥头；长 ASCII 串仅 `MDM`、`w3333`、`ELKJ` 等巧合片段 | **否** |

**结论**：这张 56500 B 镜像是转接环 MCU 里"**标定 / 校准数据分区**"（或整片小闪存中占绝大多数的数据区），承载 AF / 光圈电机的标定参数与查找表。它不是可以直接反汇编找 buffer overflow 的代码镜像。

## 5. 两个附加帧（序号 113 / 114）—— 不是签名，是数据

| 帧 | 内容 | 熵 | 判定 |
|---|---|---|---|
| 序号 113（500 B 满） | 密集数据，开头 `9f 5a 5b da 5e 62 00 40 1d 44 2a 07 …`，内含大量 `0x86/0x4d/0x06` 记录；`0x1F0` 附近出现连续 `4d 44 4d`（"MDM"）夹在 `86 12` 与 `86 15` 之间 | 6.70 | 第二段标定 / 参数块；"MDM" 是记录模式（`0x4d` 高频）中的**巧合 ASCII**，非标记 |
| 序号 114（500 B） | **128 B 数据 + 0xFF 填充**。数据内容为重复的 `86 1e 4d 06 4d 86 21 4d 27 4d …`（同族记录） | 5.91 | 小段标定表，恰 128 B 自然结束；**非高熵签名**（真 128 B RSA 签名熵应 ≈ 7.9 且常以 `0x30 0x82` 开头） |

> 重要推论：**`.ecp` 容器内未见任何代码签名 / 证书块。** 若 VILTROX 的烧录协议依赖"整包校验"而非"签名"，则更新路径的鉴权强度存疑（见 §6.2）。这一点需拿到厂商升级工具 / 抓包才能最终确认。

## 6. 密钥访问攻击面（核心）

先厘清"密钥"在转接环语境下指什么：

1. **标定数据密钥**（AF / 光圈电机标定）——**就在本镜像里，已解出**，非机密。
2. **设备唯一 ID / 序列号**——常存于闪存固定区或 OTP，用于固件绑定 / 防伪。
3. **镜头 / 机身认证密钥**——部分转接环需与机身做握手认证（让机身"认"这是一颗可用镜头），密钥存于安全区 / OTP。
4. **安全区 / OTP / fuse**——一次性烧录，**不在闪存、不在本镜像**，只能靠设备侧手段读取。

因此"访问密钥"的实质问题是：**能否绕过公开镜像，读走设备上 OTP / 安全区 / 运行时的机密数据**。可行路径有四条，按与研究链的契合度排序：

### 6.1 路径 A：I2C 命令处理面（与 S1RM2 OOB 研究链直接相连）

**拓扑**：转接环 MCU 通过相机卡口的 **I2C** 与机身通信，**相机是 I2C 主机**，转接环是**从机**。转接环上没有任何对外 USB / 网络接口能直接打它的 I2C 处理器——**唯一能驱动它 I2C 事务的就是相机**。

**攻击链（需实机动态验证）**：

```
恶意 USB 主机 ──USB──> S1RM2 相机
   │  (1) S1RM2 ffs OOB 越界写/读：控制 / 泄露相机内核内存
   │  (2) pvc_mass_storage：CBW/CSW 状态机把 16B CDB 交给用户态/固件执行
   │  → 攻击者在相机侧获得"写受控字节 + 读回内存 / 执行受控逻辑"的原语
   ▼
相机固件（I2C 主机控制器驱动）
   │  (3) 攻击者改写相机 I2C 主机控制器的寄存器 / 缓冲，
   │      向转接环从机发出【畸形 I2C 事务】（超长数据、越界寄存器写、异常命令字）
   ▼
转接环 MCU 的 I2C 命令处理器
   │  (4) 若处理器存在：
   │      - 数据长度未校验 → 越界写（破坏 MCU 栈 / 全局 / 函数指针）
   │      - 寄存器索引未校验 → 越界写任意地址
   │      - 命令字分派存在注入 / 未处理分支
   │      → 控制 MCU 执行流 / 改内存
   ▼
读走 MCU 闪存 +（若可访问）OTP / 安全区 → 拿到设备唯一 ID / 认证密钥
```

**为什么这是"入口级"而不是"已证实"**：
- 本研究已把 (1)(2) 做实（POC 可复现），(3) 依赖"相机 I2C 主机控制器能否被内存原语重编程"——需确认相机 I2C 驱动 / 寄存器映射（松下 OSS 可查），属**高可行但需实机**的一步。
- (4) 是**未证实假设**：因为拿到的 `.ecp` 是**数据分区**，I2C 处理器的**代码**不在其中，**无法静态定位具体 bug**。要坐实必须：
  - 拿到转接环 MCU 的**代码镜像**（可能是另一份 `.ecp` / 厂商烧录工具的 flash 全量转储），反汇编审计 I2C 中断服务 / 命令分派 / 缓冲拷贝；**或**
  - 用可控相机对实机做 **I2C fuzz**（畸形长度 / 越界寄存器 / 异常命令字），观察转接环是否崩溃、挂起、或回吐数据。

**严重性（条件性）**：高。前提是 (1)(2) 已实机成立，且转接环 I2C 处理器确无长度 / 索引校验。一旦成立，攻击者以"一根 USB 线 + 一台被控相机"即可读走转接环的机密数据，且可持久篡改其标定 / 认证行为。

### 6.2 路径 B：固件更新协议（`.ecp` 烧录，可能未鉴权）

- §5 已确认**容器内无签名 / 证书**。若 VILTROX 升级工具仅做"整包 CRC / 尺寸校验"，则：
  - 攻击者可**回植**一份"原版 + 注入 dump 后门"的镜像，让转接环在下次被相机 / USB-C 升级时，把 OTP / 安全区 / 闪存内容经 I2C 或 USB 回吐；
  - 或回植"恒过认证"的固件，直接读取认证密钥。
- **验证方式**：抓 VILTROX 官方升级工具的 USB-C / 相机侧升级流量，确认是否存在签名验证、CRC 算法、镜像对齐要求；再据 §2 的容器格式构造回植包。
- **严重性**：高（若未鉴权）/ 中（若有弱校验可绕过）。**依赖拿到升级工具或抓包**，纯静态无法定论。

### 6.3 路径 C：调试接口（SWD / JTAG）—— 最直接

- 小型 MCU 通常保留 **SWD（2 线：SWDIO/SWCLK）** 或 **JTAG**。若厂商**未烧写 SWD 锁**（小厂常省略），则**物理接触即可**：
  - 用 SWD 直接读整片闪存（含所有标定 / 唯一 ID / 认证密钥）；
  - 可在线调试、断点、改内存，**比任何协议面都彻底**。
- **定位**：多数转接环 MCU 的 SWD 未引出到外壳，需拆环找 MCU 的 SWD 焊盘 / 测试点；部分型号会复用 USB-C 的 D+/D- 或独立 20 pin。
- **严重性**：高（对持有物理设备者）。属于"硬件白盒"，与协议无关。

### 6.4 路径 D：USB-C 升级口（主机侧可控）

- 若转接环带 **USB-C 升级口**（VILTROX 多款环支持 USB 直连升级），则攻击者用 PC 直接对接：
  - 同路径 B 的镜像回植 / dump 后门思路，但**不依赖相机**，攻击面更直接；
  - 也可能存在"读回固件 / 读回标定"的调试命令。
- **验证方式**：对 USB-C 口做协议枚举（VID:PID、端点、控制请求），抓升级流量，fuzz 升级协议。

```
                    └───────────────────┬──────────────────────┘
                                        │ "密钥在设备上，不在文件里"
            ┌───────────────────────────┼───────────────────────────┐

   A. I2C 命令面（相机=主机）     B/D. 更新协议(USB-C/相机)      C. SWD/JTAG
   ┌───────────────────────┐    ┌──────────────────────┐      ┌──────────────┐
   │ 需要：S1RM2 OOB(已实机) │    │ 需要：抓升级协议/工具 │      │ 需要：物理拆环 │
   │ + 相机I2C可重编程(待证) │    │ + 容器格式(已解)      │      │ + SWD未锁(待证)│
   │ + 环I2C处理器有OOB(待证)│    │ + 未鉴权(未见签名→疑) │      │              │
   └───────────────────────┘    └──────────────────────┘      └──────────────┘
            与 S1RM2 研究链最契合         最易独立验证              最彻底(白盒)
```

**一句话**：`S1RM2 ffs OOB` 是"入口"，`pvc_mass_storage` 把"能控制相机内存 / 执行受控逻辑"做实，转接环的 **I2C 从机处理器**是"落点"，**更新协议 / SWD** 是两条不依赖相机的旁路。是否真正能"摸到密钥"，取决于 (4)(6.2/6.3/6.4) 中哪一个在实机上成立——**这需要动态 / 硬件验证，纯静态解包到此为止。**

## 7. 影响（条件性汇总）

| 路径 | 前提 | 可达影响 | 验证状态 |
|---|---|---|---|
| A. I2C | S1RM2 OOB 实机 + 相机 I2C 可重编程 + 环 I2C 处理器有 OOB | 读走 OTP / 认证密钥；持久篡改标定 / 认证 | **假设，待实机** |
| B/D. 更新 | 升级协议未鉴权（未见签名 → 可疑） | 回植 dump 后门 / 读回机密 | **待抓包** |
| C. SWD | 物理接触 + SWD 未锁 | 直接读全片闪存 + OTP 外数据 | **待硬件** |

对普通用户的实际风险：需要"恶意 USB 主机 + 受控相机"或"物理 / 升级接触"，**不属于"插上就中招"**；但对**供应链 / 逆向 / 设备持有者**场景，路径 B/C 是可落地的。

## 8. 缓解 / 修复建议（给 VILTROX）

1. **更新协议强制签名**：对 `.ecp` 整包做非对称签名（如 RSA-2048 / ECDSA），MCU 端在烧录前验签，拒绝无签 / 错签镜像。当前容器无签名，是最优先的短板。
2. **I2C 从机处理器加固**：对 I2C 命令 / 寄存器索引 / 数据长度做**边界校验**；拒绝超长 / 越界写；对未定义命令字返回 `NACK` 而非静默执行。
3. **锁定调试接口**：量产烧写 **SWD / JTAG 锁**，或用 OTP fuse 禁用调试端口。
4. **密钥进安全区 / OTP**：设备唯一 ID 与认证密钥不存于可被 flash 直读的普通闪存，改存 OTP / 安全区；认证握手机密用硬件密钥（不可导出）。
5. **标定与机密分区隔离**：标定数据（可公开）与机密（不可导出）分片，机密片设读保护。

## 9. 局限性与后续工作

**本次静态分析的边界（诚实声明）**：
- 拿到的 `.ecp` 是**数据分区**，**不含 I2C 处理器 / 启动代码 / 中断服务**，因此**无法静态定位具体内存破坏 bug**；路径 A 的 (4) 目前是"高可行假设"而非"已证实"。
- **未确认 MCU 型号 / 内核架构**（非 ARM/Thumb/RISC-V 可执行形态；疑似某 8/16 位或专用 MCU 的数据分区）。确认需厂商工具链或代码镜像。
- **未拿到升级协议 / 工具 / 抓包**，路径 B/D 的"未鉴权"是从"容器无签名"推断的，**需实机确认**。
- **未拆环**，SWD 是否锁定、是否引出，未知。

**建议的下一步（按性价比）**：
1. **抓 VILTROX 升级工具流量**（USB-C 或相机侧）→ 定论路径 B/D 是否鉴权（性价比最高、最易独立做）。
2. **找转接环 MCU 代码镜像**（另一份 `.ecp` / 全量 flash 转储）→ 反汇编审计 I2C 处理器，坐实路径 A 的 (4)。
3. **可控相机 + I2C fuzz**：用 S1RM2 OOB 重编程相机 I2C 主机，对转接环发畸形事务，观察崩溃 / 数据回吐（坐实路径 A 全链）。
4. **拆环探 SWD**：确认是否锁定（路径 C，最彻底）。
