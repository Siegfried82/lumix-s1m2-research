# 执行摘要（全文整合版）

对象：Panasonic DC-S5（MC801，固件 VD4.30 研究版）· 通道：Wi-Fi `cam.cgi`（UA 必须 `LUMIX Sync`）· 周期：2026-10-09 ~ 10-12

证据强度标记：✓=已实机/协议闭合 · ◐=有强证据但未完全闭合 · ✗=已证伪

---

## 总判断

> **这台 S5 的 Wi-Fi 表面没有可用的 RCE，但暴露了完整的设置面（47 个可写域）与若干"启用但未声明"
> 的隐藏功能档。最高价值的突破是隐藏录像格式解锁 + 持久化：`videoformat` 容器门一开，mov 态一次
> 拿到全部 17 个「常规 + open-gate 隐藏」档，直写 flash 后**开机即锁定、跨断电持久**
> （2026-10-13 断电终验；期间排掉一个假结论——早先"mov 回落"实为上传协议 bug，见阶段三）。**
> **固件 AES 密钥提取与网络 RCE 均为阴性；物理/调试侧（拆机 UART/JTAG 读运行时明文）是绕开 AES 最现实的高价值路径。**

## 阶段一 · 固件格式 / 启动链 / AES 绕过（10-10）

**目标**：能否从固件/转接环/总线离线恢复 AES 密钥，或绕过加密分区。

**结论（✗ 终局否定）**
- AES 密钥**固化在 MC801 芯片内**（OTP/eFuse/Crypto Engine/TrustZone），不在固件文件、转接环、镜头 I2C 总线里。
- 离线 130k+ 探测、40/41 加密分区、真实 256KB keystream，均无法恢复密钥。
- UPD 头里的"版本门"相关字段已定位：改 `comm_proto_ver` **不能**绕过版本门（字段方向 + 无比较逻辑）。

**产物**：UPD 格式 / 启动链 / 分区布局分析、`s5_layout.json`、`S5___V29.bin.parts.json`、`s5_ptp_dump`。

## 阶段二 · Wi-Fi 预言机 / RCE / 崩溃（10-11）

**目标**：除了崩溃，能不能拿到能"改内容"（访问底层并修改）的漏洞。

**已证（✓）**
- **Wi-Fi 无调试后门**：~70 个候选 mode（dmesg/memdump/flash/jtag/uart/keydump…）只读枚举全部回通用 `err_param`。
- **Wi-Fi 是"验证型 oracle"**：只有 3 个——版本门（防回滚）、固件签名校验、CAMSET 校验和（可伪造）；对"拿密钥/拿明文"零贡献。
- **固件升级 = 改内容原语**：`startsenddata→senddata→endsenddata` 一旦成功 = 重写整个 rootfs（守护进程/socket/配置路径一次到手），无需拆机/焊接。
- **唯一实机漏洞 = PTP length-DoS**：PTP 解析器校验 type 不校验 length，length 不符 → 接口挂死、无超时；拔插 USB 恢复，无写操作、不砖机。
- 服务器为 **Panasonic 定制 CGI**（GoAhead 系，XHTML 错误页指纹）。

**核心阻塞（固件升级写路径为何没打通）**
- 能干净流送全部 1474 个完整 61192B 块，但**最终部分块（41456B）始终失败**：触发 ~31s flash 定址 → `err_busy`（慢）→ 重试 `err_critical`（快）。
- 与内容无关（发的是未改动的真 V29 镜像）、与节奏无关（87ms 与 158ms/chunk 都失败）、与状态无关（拔电池重启后仍复现）。
- 只有真 90MB 镜像能走到 flash 定址；小镜像在"固件合法性"关就被拒。真实 90MB 的 ~31s 定址失败，最可能是内部 flash 对大镜像末块的擦/写超时或磨损。

**RCE / 代码注入（✗ 全阴性，仅 1 条未测）**
- 编译 C / `LD_PRELOAD` 注入（CVE-2017-17562 思路）：阴性（GoAhead 不把 `LD_*` 传入 CGI 环境，或 cam.cgi 静态链接）。
- 已公开 GoAhead 多数 CVE：不适用（多为 DoS/信息泄露）。
- **CVE-2019-5096（9.8，multipart UAF → RCE）：未测**（唯一剩余公开 RCE，需堆控）。
- HTTP 头/参数溢出 fuzz：阴性。

## 阶段三 · 隐藏录像格式解锁 + 持久化（10-12 ~ 10-13）—— 突破

**目标**：解锁 S5 的隐藏录像格式（open-gate 片门全开 / 高档 MOV），并让它持久可用。

**关键机制（✓）**
- 相机对外只暴露设置的 **RAM 副本**（`getinfo camsetting`）。两个写入路径行为不同：
  - `setsetting`（CGI）：`videoformat`/`videoquality` **只写 RAM**，断电回落默认。
  - **直写 flash**（`startsenddata/senddata/endsenddata` 上传 65533 字节 blob）：**跨断电持久**。
    注意写入是**分块协议**（`method=separate`，bufsize 61460 → 61192+4341 两块），
    单次 POST 整个 blob 不会落地——早先一轮的假"mov 回落"即由此而来。
- **`videoformat` 是单一容器门**：mp4 / mov 二选一、互斥。
  - mov 态 → 17 个 `mov_*` 高码率档可见（4K/C4K，100–200Mbps 10bit），MP4/AVCHD 常规档隐藏
  - mp4 态 → MP4 常规档可见（NTSC 8 档 / PAL 5 档），17 个 `mov_*` 隐藏
  - **mov 态"常规录制"没丢**——17 个 mov 档最低就是 100Mbps，日常够用且码率比 mp4 的 20/28Mbps 还高。
  - ⇒ **mov 态 = 常规 MOV 高档，是本机最优解**。
  - ⚠️ 更正：这 17 档**不是** open-gate 片门全开。真正的 5.9K（`mov_*_200mbps_5_9k_10bit`）
    在 `allmenu` 有定义但**被固件按机型过滤，机身菜单选不到**（实测 NTSC 少 2 档、PAL 少 1 档）。

**最终持久状态（2026-10-13 断电终验：✓ 全部持久）**
```
ntsc_pal    = ntsc                          (byte[65230]=0x00 ✓)
videoquality= mov_60p_150mbps_c4k            (byte[6986]=0x92 ✓，机身菜单可选)
videoformat = mov                            (byte[3062]=0x06 ✓，0x005e 全 13 槽 = 06)
```
容器证据：`04_工具与脚本/campaign2/out/blob_GOLD_mov_persisted_20261013_020600.bin`
（sha256 `13b59254…`，当时质量为 `0x8b`）。写入采用分块 `separate` 协议；拔电池重启后原样存活。

**机身菜单约束（10-13 用户报障后查明）**：持久化的质量码必须存在于机身菜单定义 `allmenu`，
否则机身【录制质量】整项变灰。`0x8b`(mov_…_**c4k**_10bit) 恰好是 `curmenu` 有、`allmenu` 缺的
唯一 mov 档，故会让菜单失灵；改用已声明档（如 `0x92`=mov_60p_150mbps_c4k）后恢复正常。
另：机身停在菜单界面时 `getinfo camsetting` 回 `err_reject`，退出菜单即恢复。

**假结论更正（重要教训）**：早先一轮判定"mov 写进 flash 后被固件重新派生为 mp4"，
实为 `persist.py` 用**单次 65KB POST** 上传，相机不认，**数据从未落地**——`startsenddata`
返回的 `method/bufsize` 本可直接判别。改用分块协议后 mov 立即持久。详见 07 报告。

**关键字段/码映射**
- `65230` ntsc_pal：`0x00`=ntsc，`0x01`=pal
- `3062` videoformat：`0x05`=mp4，`0x06`=mov，`0x08`=mp4hevc（最终弃用）。
  该值属于记录 `0x005e`（记录起点偏移 3056，14 字节 payload：byte[0]=活动容器，
  byte[1..12]=12 个影子槽＝偏移 3063..3074，byte[13]=0x00 结束符）
- `6986` videoquality：`0x8b`=mov_60p_200mbps_c4k_10bit（机身菜单无 → 会变灰）、
  `0x92`=mov_60p_150mbps_c4k、`0x94`=mov_30p_150mbps_c4k_10bit、`0x96`=mov_24p_150mbps_c4k_10bit、
  `0x97`=mov_24p_100mbps_c4k、`0x9b`=mov_60p_200mbps_4k_10bit、`0xc1`=mp4_30p_20mbps。
  记录 `0x0124`（起点 6980）为 13 槽 u16 数组，槽 0 = 选中码，其余保留 `0x00c0`
- 校验和：`byte[65532] = (256 − Σ(byte[0..65531])) mod 256`
- blob 结构：65533 字节；44 字节头（`"Panasonic"`+`"DC-S5"`）+ 8 字节前导（offset 44..51，含 `0xffcc`）
  + TLV 记录流（offset 52 起，`[field_id u16 LE][len u16 LE][flag u16 LE][payload len−6]`），共 **831** 条记录，
  记录流止于 65528

**踩坑记录（重要）**
- `senddata` 可能长期不响应（在等 `endsenddata`）→ `KA.send()` 的 recv() 卡死。**不是失败**：数据由 sendall 即已送达。
- 恢复：kill 卡死进程 → 健康检查 → 新短超时连接直接发 `endsenddata`（相机不绑 keep-alive）→ 复核。

## S1R2 跨团队汇入（10-12 移交，AES 路径更新）

来源：S1R2（DC-S1RM2，SC2006A）团队移交文档，已归档至
`01_研究报告/06_S1R2移交_20261012/`（含 `00_S5结合点与AES路径总结.md` 交叉校验）。

- **CAMSET 交叉互证（✓ 双证）**：S1R2 9.2MB 设置块与 S5 camsetting 同一设计家族；
  校验算法 `checksum = (256 − Σ) mod 256` 双方独立反推、完全一致；PTP/SD 写配置路径
  在 S1R2 实机闭合（含菜单外隐藏快门声），S5 同族路径（0x9422）风险评级可下调（仍不执行）。
- **FunctionFS OOB（F1/F2，✓ S1R2 实机 / ◐ S5 待审计）**：USB 主机零前置触发内核越界读/写，
  可利用性低（固定偏移、写高 16 位恒 0）→ DoS + 弱泄露，非 RCE；S5 的 PTP 同走
  FunctionFS，若 MC801 内核 OSS 有同款 `current_alt_setting` 修改则原语成立（离线审计）。
- **S1R2 已排除路线对 S5 的修正**：
  - UART：S1R2 实测 `BOOTDELAY=-2` + `console=null` 为死路 → S5 不能直接套用，
    需先离线核验 S5 的 U-Boot console 配置（48 分区 type=2 明文分区找 env 痕迹）再定生死；
  - SD.DAT：S1R2（NAND）实测无只读模式、写错 `pardata.par` = 不可逆砖 → S5 上**降级为
    JTAG 之后的备胎**，存储类型待拆机确认；
  - 新增两个零风险先行项：**服务模式组合键盲试**（GX85/ZS30 式多键开机）与上述
    U-Boot console 离线核验。

**AES（固件解密）路径更新后排序**：P1 拆机只读取证（SoC/存储/测试点）→ 零风险并行
（P2 服务模式组合键 / P3 U-Boot console 核验 / P7 S5 f_fs 审计）→ **P4 JTAG dump RAM
= 运行时明文（主线，无需密钥）** → P5 UART bootlog（视 P3）→ P6 SD.DAT（备胎）→
P8 芯片级（最后手段）。软件面（Wi-Fi/PTP/设置块）对 AES 贡献已封顶。

## 安全红线

- 常接 AC 电源；相机极易砖，恢复靠拔电池。
- 绝不真刷固件；绝不 `resetDevice`；绝不执行 PTP 配置写回（0x9422/0x9423）/ 0x9406 带副作用子码。
- 每次写后健康守卫（`getstate→ok`；重启后 ≤180s 内必须恢复，否则停止）。
