# LUMIX S1R2（MC8244）固件加密体系分析报告

**日期**：2026-10-13
**对象**：Panasonic DC-S1RM2（S1R2），SoC = Socionext Milbeaut **MC8244**
**样本**：`S1Rm2V15.bin`（162.2 MB，v1.5）、`S1Rm2V11.bin`（160.8 MB，v1.1）
**判据**：固件目录条目内自带的「明文 SHA-256」+ 4 组「同明文不同 IV」冗余分区对

## 0. 一句话结论

> **Codex核验评论**：AES-CBC、OTP、RSA/BootROM和唯一RAM路线尚未由消费者或验证明文证实；41万/282万统计也不一致。有限字典失败不能推出随机生成与存储位置。


S1R2 固件使用 **「AES-CBC 逐分区加密（密钥在 OTP）+ RSA-4096/ECDSA 容器签名（公钥在 BootROM）」的两层设计**。
我们已完整解析其容器结构、建立了**离线精确密钥判定器**，并用 **约 41 万个候选**（含 S1R2 自身头部字节遍历、
日语线索、人名/生日/公司纪念日、全部 1900–2030 日期）做穷举，**全部未命中**。

**结论：对称密钥不是任何可猜/可派生的值，是真随机且固化在 MC8244 片内。**
唯一软件可行的绕过路径是 **RAM dump**（引导后固件已被硬件解密进 DDR）。

| 偏移 | 字段 |

## 2. 密钥判定预言机（本次最有价值的产出）

### 2.1 判据一：目录条目里的「明文 SHA-256」

> **Codex核验评论**：空条目匹配SHA256空串是结构线索，不能验证任何非空受保护对象的摘要范围。


厂商把每个分区**明文的 SHA-256** 明文写在目录条目里。因此：

```
候选密钥 K 正确  ⟺  SHA256( AES_CBC_Dec(密文, K, 条目IV) ) == 条目里的 32 字节
```

**已反证该字段确实是明文的哈希**：
- `boot` / `loader2` / `loader3` / `storage` 四个 size=0 的分区，
  其 stored SHA-256 = `e3b0c44298fc1c149afbf4c8996fb924…` = **空字符串的 SHA-256** ✓

### 2.2 判据二：同明文不同 IV 冗余分区对（更快、更强）

> **Codex核验评论**：CBC首块异或式代数正确，只有在模式、相同key、真正首块/IV及相同首块明文均成立时才是必要筛选。不同长度对象不能直接按完整解密输出相同配对。


S1R2 固件里存在厂商的 A/B 双备份，**同一明文加密两次、IV 不同**：

| 对 | 分区 | 大小 | 明文 SHA-256（相同） | IV（不同） |
|---|---|---|---|---|
| 1 | `eep_ow_a` / `eep_ow_b` | 131,072 | `76195964ec78a7be…` | `8ab81e86…` / `eaeae70c…` |
| 2 | `eep_exp_a` / `eep_exp_b` | 12,288 | `9eb84b8d7df42801…` | `f3649d79…` / `1ea76581…` |
| 3 | `eep_act_a` / `eep_act_b` | 512 | `3bdcb4d0d03318c6…` | `1c8bd299…` / `505d75ee…` |
| 4 | `postboot2_r` / `postboot4_r` | 131,072 | `b5a41c3758763bbe…` | `8367989c…` / `c079552e…` |
| 5 | `postboot1_r`（两处） | 6.9M/2.0M | 相同 | 不同 |
| 6 | `postboot3_r`（两处） | 8.3M/3.7M | 相同 | 不同 |
| 7 | `postboot5_r`（两处） | 1.8M/1.8M | 相同 | 不同 |
| 8 | `dsp_eisldc_`（两处） | 65,536 | 相同 | 不同 |
| 9 | `dsp_fstack_`（两处） | 65,536 | 相同 | 不同 |

```
正确密钥 K  ⟺  AES_CBC_Dec(C_a, K, IV_a) == AES_CBC_Dec(C_b, K, IV_b)   （逐字节相同）
```

**★ 关键优化（用于暴力枚举）**：
CBC 下只需比较**第一个分组**即可：

```
D_K(C1_a) XOR D_K(C1_b) == IV_a XOR IV_b
```

⇒ 每个候选密钥只需 **2 次 16 字节 AES 解密 + 1 次异或比较**
⇒ 配合 AES-NI，单核约 50 周期/候选；8 核约 1~5 G 候选/秒

### 2.3 为什么这两个判据比"熵下降/看起来像代码"可靠得多

- 「熵下降」判据的问题：真密钥若模式/IV 假设错，也会失败 ⇒ **漏判**
- 本判据：**同明文两段必须完全相同** ⇒ 不可能漏判，只有"是/不是"

## 4. 官方加密与签名设计分析

> **Codex核验评论**：本节流程是架构假设，尚无真实发布/认证/解码/加载消费者。512字节或64字节段长不证明RSA/ECDSA验签成功。


### 4.1 双层设计

| 层次 | 作用 | 算法 | 密钥位置 | 是否保密 |
|---|---|---|---|---|
| 第一层 | **机密性**（别人看不懂） | AES-CBC 逐分区，每分区独立 IV | 片内 OTP / eFuse / Crypto Engine | **保密** |
| 第二层 | **真实性**（别人伪造不了） | RSA-4096（尾块 512B）+ ECDSA P-256（头部 0x220 候选） | BootROM 固化的**公钥** | 公开 |

**⇒ "AES 密钥是强随机"与"官方能签名固件"完全不矛盾**：
AES 密钥由产线设备写入每颗芯片的 OTP（谁也不需要记住它）；
签名私钥在厂商 HSM 里，公钥烧进所有相机的 ROM。两者独立，各管一件事。

### 4.2 官方发布流程（对照实测字段）

```
① 编译各分区明文
② 算 SHA-256(明文)                 → 写进条目 0x1C（32B）
③ 生成每分区随机 IV                → 写进条目 0x3C（16B）
④ 用型号密钥 DMK 做 AES-CBC 加密    → 生成数据区
⑤ 算 CRC32(整段密文)               → 写进头部 0x40
⑥ 用 RSA-4096 私钥对整个容器签名    → 附在文件末尾 512B
⑦ 打包发布 .bin
```

### 4.3 相机端自检逻辑（**Secure Boot 验证链**）

```
开机 / 固件更新时，安全加载器（BootROM / EL-3 安全加载器 / TrustZone）依次执行：

① 验签：用 BootROM 内公钥验 RSA-4096（+ ECDSA）
   失败 ⇒ 直接拒绝，不解密
   ★ 挡住"伪造固件"

② 校验 CRC32（整段密文完整性）

③ 逐分区解密 + 自检：
       明文 = AES-CBC-Dec(密文, 【OTP 密钥】, 条目 IV)
       if SHA256(明文) != 条目里的 32 字节  →  中止
   ★ 这就是"自检"：用【明文哈希】验证解密正确性
     密钥错 / IV 错 / 数据被篡改，全部在此暴露

④ 按条目里的加载地址把明文送入 RAM 执行
   （S1R2：program → 0x80000，compress_pr → 0x2D40000，postboot* → 0x43E0000 起等）
```

### 4.4 该设计对攻击者的"可利用特性"

| 特性 | 说明 | 对攻击者的价值 |
|---|---|---|
| **目录里明文存 SHA-256(明文)** | 等于给攻击者一个离线验证预言机 | 可精确验证候选密钥，无需相机。**不缩小 2^128 搜索空间** |
| **A/B 冗余分区（同明文不同 IV）** | 厂商的双备份 | 提供"逐字节相同"判据，用于暴力枚举的快速筛选 |
| **CRC32 对密文计算** | 改密文会被发现 | 无用（后面还有签名） |
| **IV 明文存储** | CBC 的 IV 本就可公开 | 降低攻击者需要猜的变量 |

**⇒ 设计是健壮的**：既伪造不了（签名），也读不了（AES + OTP 密钥）。
我们 282 万次撞库失败，正是这套设计"按预期工作"的结果。

```
① S1R2 固件容器已完整解析（61 分区 + 加载地址 + 类型 + IV + 明文哈希），
```

### 5.4 暴力程序用法（跑之前务必先自检）

> **Codex核验评论**：四字节生成键每种模式最多2^32不同值。模式0扩大上界只可能重复；0x1000000000000实际上是2^48，不是2^44。未交付程序和吞吐记录。


```powershell
# 环境：gcc 路径 C:\msys64\msys64\ucrt64\bin（必须先加入 PATH，否则静默失败）
# ★ PowerShell 传参坑：-msse4.1 会被拆成 -msse4 和 .1 ⇒ 用 -march=native，或写进 bat
# ★ AES 指令不在 x86-64-v3 级别里，通用编译需显式 -maes

brute32.exe pairs.bin <mode> <start> <end>

# mode 0: key = 4字节小端重复填满16     mode 1: 4字节大端重复填满16
# mode 2: 4字节小端 + 12个0             mode 3: 十进制ASCII + 0填充
# mode 4: 4字节小端重复两次 + 8个0       mode 5: 4字节小端 + 12个0xFF

brute32.exe pairs.bin 0 0 0x100000000        # 扫满 2^32（约 1~2 秒）
brute32.exe pairs.bin 0 0 0x10000000000      # 2^40（约 4 分钟）
brute32.exe pairs.bin 0 0 0x1000000000000    # 2^44（约 1 小时）
```

> **⚠️ 正式跑长任务前必须先做自检**：用一对已知答案的数据验证程序在正确密钥下会报"命中"。
> 若 AES-NI 实现有 bug，程序会安静地永远返回"未命中"，白跑数小时。
