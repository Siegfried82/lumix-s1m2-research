## 2. 相机热点：首次实际观测

> **Codex评论（原行44–148）**：信标capability/IE可描述所观察广播的网络能力；未验证实际关联或cam.cgi控制面。OUI只是信息元素中的供应商线索，不能单独确认物理芯片型号。RSSI占位/失败事件不证明线上从未发生认证交互；需要原始事件/帧证据。


### 2.1 发现与信标原始解析

`netsh wlan show networks mode=bssid`：

```
SSID 7 : <CAMERA_SSID>
    Network type : Infrastructure
    Authentication : Open
    Encryption : None
    BSSID 1 : <DEVICE_MAC>
    Signal : 88%
    Radio type : 802.11n
    Band : 2.4 GHz
    Channel : 6
```

用 **WlanAPI（`WlanScan` + `WlanGetNetworkBssList`）** 取原始 BSS/IE（自建工具 `s5_wlan.ps1`，见 §5）：

```
SSID='<CAMERA_SSID>' len=9  ssidHex=[<REDACTED_SSID_BYTES>]   ← 无尾随空格/隐藏字符
BSSID=<DEVICE_MAC>  rssi=-51  linkQ=87  chan=2437  cap=0x0401  beacon=200  phy=7(HT)
```

**capability = `0x0401`** → `ESS`(bit0) + `Short Slot Time`(bit10)，**Privacy(bit4)=0 且未出现 RSN/WPA IE**
⇒ **该热点确实是开放网络（无加密、无 802.1X）**。

### 2.2 IE 逐条（信标）

| IE | 内容 | 解读 |
|---|---|---|
| `00 09` | `<CAMERA_SSID>` | SSID |
| `01 08` | `02 84 8b 96 0c 12 18 24` | 支持速率 1/2/5.5/11/6/9/12/18 Mbps |
| `03 01 06` | 信道 6 | DS Parameter |
| `05 04` | TIM | 仅信标出现 |
| `32 04` | `30 48 60 6c` | 扩展速率 24/36/48/54 Mbps |
| `2a 01 02` | ERP：Use Protection | 存在非 ERP 设备 |
| `2d 1a` | HT Capabilities | 20 MHz，MCS 集 |
| `3d 16` | HT Operation | 主信道 6；**Basic MCS Set 全 0（非典型）** |
| `7f 01 00` | Extended Capabilities（**仅 1 字节，偏短**） | 可疑但合法 |
| `dd 18 00 50 f2 02 01 …` | **WMM Parameter** | WMM 已启用 |
| `dd 83 00 50 f2 04 …` | **WPS IE** | 见 §2.3 |
| `dd 07 00 0c e7 08 00 00 00` | **厂商 IE，OUI `00:0C:E7`** | **MediaTek** 的 OUI |

> ⚠️ 两次扫描 IE **不一致**：一次带 TIM + 短 WPS IE + WMM，另一次无 TIM + 长 WPS IE。
> 这与"探针响应 vs 信标"的差异一致（WPS 在探针响应里给全量设备信息），**不是热点在跳变**
> ——因为 60 s 连续轮询中 SSID 始终存在、强度稳定 87–88%。

### 2.3 WPS IE 泄露的信息（**本轮新信息**）

`dd 83 00 50 f2 04` 之后解析：

| WPS 属性 | 值 | 含义 |
|---|---|---|
| `0x104A` | `10` | WPS 1.0 |
| `0x1044` | `02` | **WPS State = Configured（已配置）** |
| `0x1047` | `4D454930 0000 1000 8000 <REDACTED_MAC_BYTES>` | **UUID-E**（`4D454930-0000-1000-8000-<REDACTED_MAC_BYTES>`） |
| `0x1021` | `"Panasonic"` | Manufacturer |
| `0x1023` | `"LUMIX"` | Model Name |
| `0x1024` | **`"DMC-MC801"`** | **Model Number = 内部机型代码 MC801** |
| `0x1011` | `"Digital Still Camera"` | Device Name |
| `0x1054` | `00 06 00 50 F2 04 00 01` | Primary Device Type（Digital Still Camera） |
| `0x1049` | `00 37 2a 00 01 20` | 厂商扩展 |

**要点**：
- 这是本项目**第一次从相机热点本身拿到 WPS/机型身份**，且与 §6 的 BLE 广播名同源
  （都由 Wi-Fi MAC 后 6 位 `<DEVICE_SUFFIX>` 派生）。
- `UUID-E` 里的 `4D454930` = ASCII `"MEDI"`+…，与 `cam.cgi` 的 `accctrl&type=req_acc`
  使用的 `value=<UUID 4D454930-0100-1000-8001-…>` **同一命名族** —— 可作为跨通道关联标识。
- 厂商 IE `00:0C:E7` 是 **MediaTek** 的 OUI。项目此前把"Wi-Fi 模块型号"列为**待拆机确认项**，
  本结果把范围收敛到 **MediaTek 系（MT76xx 一类）**。若后续要做 Wi-Fi 芯片侧攻击面
  （如 Broadpwn/Nexmon 式研究），**研究对象应换成 MediaTek 而非 Broadcom/Marvell**。

### 2.4 关联失败：现象与已排除项

`netsh wlan connect` 返回"成功接受"，但 **约 2 s 后**事件 `8002` 报失败：

```
Failure Reason: 特定的网络不可用。   RSSI: 255
```

`RSSI: 255` = 关联阶段拿不到任何 BSS ⇒ Windows 在选择 BSS 时就放弃了，**根本没走到认证/关联交互**。

已穷举并全部失败的手段：

| 手段 | 结果 |
|---|---|
| 配置文件连接（open/none），manual / auto | ❌ |
| 关掉 MAC 随机化（`MacRandomization=false`） | ❌ |
| 指定 BSSID 连接 | ❌ |
| `wlan_connection_mode_discovery_unsecure(3)`（无配置直连开放网） | ❌ |
| `wlan_connection_mode_temporary_profile(1)` | ❌（rc=1206） |
| 关闭/启用 WLAN 网卡（复位射频） | ❌ |
| 重启 `wlansvc` + 重新加配置文件 | ❌ |
| 强制 PHY：802.11ax → 802.11n → 802.11a/b/g | ❌ |
| 强制频段：Dual Band → 2.4 GHz Only | ❌ |
| 60 s 内确认热点是否跳变 | ✅ 始终存在 87–88%，**不跳变** |

⇒ **不是**射频/驱动/频段/PHY/配置问题；热点在广播却**不接受本机**。

**用户确认的关键事实：手机正连着相机热点。**
相机 SoftAP 常见实现是**单客户端 AP**，第 2 个客户端会得不到（或得不到及时的）关联响应 →
Windows 就报"网络不可用"。**这是目前最可能的解释，并给出了零成本验证动作**：
断开手机（关手机 Wi-Fi 或"忘记"该网络）后重试。

> 该结论同时给项目补上一条**安全含义**：相机热点是**开放网络**。一旦没有客户端占用，
> 覆盖范围内任何设备都能关联（是否能进而读取 `cam.cgi` 取决于相机的会话判定，
> 这正是 10-13 号报告里"单客户端但读类端点不受限"那条结论要扩展的部分）。
> **待验证**：手机断开后我们能否关联 + 关联后 `cam.cgi` 的可用面。

## 4. 蓝牙（BLE）方向：Windows 侧已就绪，但相机未开蓝牙

> **Codex评论（原行158–211）**：早期BLE未见广播属于扫描阴性；后来§9报告广播与连接，不应将早期“未开蓝牙”作为永久状态。工具需要bleak/Windows栈，但本次没有验证环境或再次执行。


### 4.1 本机侧前置（本轮踩到的坑）

- 首次扫描直接失败：`BleakBluetoothNotAvailableError: Bluetooth radio is not powered on`。
- 修法（**可复现**）：
  1. `Set-Service bthserv -StartupType Automatic; Start-Service bthserv`
  2. 用 WinRT `Windows.Devices.Radios.Radio::GetRadiosAsync()` + `SetStateAsync(On)` 打开射频
     （`RadioAccessStatus = Allowed`）。
- ⇒ 报告 04_环境与依赖.md 的"环境坑"清单应补：**Windows 侧蓝牙射频默认 Off 时 bleak 直接报错**，
  且**只有 Windows PowerShell 5.1 能 `Add-Type -AssemblyName System.Runtime.WindowsRuntime`**
  （pwsh 7 不行），所以 WinRT 调用要落到 `powershell.exe -ExecutionPolicy Bypass -File`。

### 4.2 扫描基线（相机蓝牙关闭时）

24 s 扫描，命中设备全部**与相机无关**：

```
GR-AC_10015_09_6abf_SC  <DEVICE_MAC>   rssi=-68
<DEVICE_MAC> / <DEVICE_MAC> / <DEVICE_MAC> / <DEVICE_MAC>  （随机 MAC，无名称）
```

**没有 `<CAMERA_SSID>`** ⇒ 相机当前**未开蓝牙/未广播**。这与 14 号报告"连接与枚举不需要配对"的前提
并不冲突——那次的相机是开了蓝牙的。

### 4.3 已就绪的工具（相机开蓝牙即可跑）

`02_工具与脚本/ble/s5_ble.py`（本轮新增，`bleak` 实现，**默认全只读**）：

```bash
python s5_ble.py scan 25      # 扫描，高亮 Panasonic/LUMIX 广播
python s5_ble.py enum         # 连接(不配对) + 完整 GATT 枚举 + 25 s 空载稳定性测试
python s5_ble.py session      # 空闲测试 → 读 idx35(INITIAL_INFORM) → idx5(SSID) → idx6(密码)
python s5_ble.py read <uuid>  # 读指定特征
```

内置文档里的路由常量与"字节置换 + 32 位 XOR"解码器（默认密钥 `0x9032782C`）。

**本轮的关键机会（相对 macOS 的增量）**：13/15 号报告卡在
"macOS CoreBluetooth 不触发绑定 → 一读即断链"。**Windows 的 WinRT 蓝牙栈有独立的
配对/绑定路径**（`DeviceInformation.Pairing`），可能做到 macOS 做不到的绑定 → 一旦绑定成功，
`idx35/idx5/idx6` 的读路径就有机会打开（= 拿到 SSID 与 Wi-Fi 密码）。
这正是"继续蓝牙方向"最该先试的一步。

   条目从 **偏移 8** 开始（不是 4）。

```
      mfg = {'0x3a': '<REDACTED_MANUFACTURER_PAYLOAD>'}
```

- **BLE 地址 `<DEVICE_MAC>` 与 Wi-Fi MAC/BSSID 无关**（Wi-Fi 侧是 `<DEVICE_MAC>` / `<DEVICE_MAC>`），
  说明相机的 BLE 用的是**独立/随机地址**；而**本地名仍泄露 Wi-Fi MAC 后 6 位**（`<DEVICE_SUFFIX>`）。
- **服务 11 个 / 特征 44 个**（Windows 实测计数）。
  ⇒ 这**解决了文档内部"41 vs 44 特征"的不一致**：macOS CoreBluetooth 报 41，Windows 报 44；
  两者差在 GAP/GATT 通用服务与部分分支特征是否暴露，**以"约 41–44，视主机栈而定"为准**。
- 完整 44 特征清单已落在 `s5_ble_watch.log`（含 handle 与属性）。

### 9.2 空载稳定 → 一读即断（Windows 复现成功）

> **Codex评论（原行288–299）**：两平台读取后断链不唯一证明相机认证策略；取取消异常也不足以排除传输、协议状态和客户端路径。源码watch行53的因果标签不作为实测结论。


```
[*] idle test: no reads for 25.0s ...            → [+] link still up after 25s idle
[*] read 03e23a31-...-de9acdc910bb (idx35) ...
[!] read failed: OSError: [WinError -2147023673]  (HRESULT_FROM_WIN32(ERROR_CANCELLED)=0x800704C7)
[!] LINK DROPPED at idx35
```

- **与 macOS 完全一致**：连接 + 枚举不需要配对、空载 25 s 稳定、**第一次读属性立刻断链**。
- 结论从"macOS 特有"升级为**跨主机栈的系统性行为**（macOS CoreBluetooth 与 Windows WinRT 都如此），
  即断链来自**相机侧策略**，不是主机栈差异。

### 9.3 新的关键问题：是否需要 BLE 绑定？

> **Codex评论（原行301–316）**：加密/绑定与应用协议前置并非逻辑互斥，可能共同需要。handshake默认dry run先扫描并连接；confirm才控制通知订阅。没有原始读回证明会话/SSID/密码取得。


- 本机枚举到的 4 个 BLE 设备 `CanPair` 全为 `False`；相机出现时是否 `CanPair=True` **尚未观测到**
  （相机只在打开蓝牙后的一小段窗口内广播，随后不再广播；本次观测窗口约 2 分钟）。
- **两种待判别的机制**（本项目此前只押注了第一种）：
  - **A. BLE 层绑定（bonding）**：相机对未加密链路拒绝读 → 需在系统层完成配对。
    项目 14/15 号的判断，macOS 侧未能触发；本轮在 Windows 侧用 `DeviceInformation.Pairing` 继续试。
  - **B. 应用层协议前置（尚未被本项目排除）**：APK 握手第 3 步是
    **先写 12 个 notify 特征的 CCCD（`0x2902=0100`）注册通知，第 4 步才读 idx35**。
    我们（macOS 与 Windows）都是**没做任何写就读** → 相机可能因为"协议状态不对"而直接断链，
    与加密无关。**这是与 A 互斥的、代价极低的判别实验。**
    工具已就绪：`02_工具与脚本/ble_win/s5_ble_handshake.py`（默认 dry-run，`--confirm` 才真正订阅）。
    ⚠️ 该步会向相机写入（标准 CCCD 订阅，官方 App 每次连接都做，可逆，不碰设置/flash），
    **按项目红线需用户明确同意后才执行**。
- 若 B 成立：读路径打开，可直接拿 `idx35` 会话密钥 → `idx5` SSID → `idx6` Wi-Fi 密码，
  **且与固件/密钥目标无关**（14 号结论不变），但对"相机 Wi-Fi 凭据交付链"是闭环。

### 9.4 Wi-Fi 关联失败的原因修正（重要）

> **Codex评论（原行318–332）**：手机断开仍失败削弱单客户端假说，但不能唯一锁定Windows驱动或某个IE异常；需要对应帧/事件和受控对照。该新增材料没有取得固件解密或实际RAM。


用户随后确认并断开了手机与相机热点的连接，但**本机仍然关联失败**。于是：

- 「单客户端占用」解释**被削弱/排除**（手机已断开仍失败）；
- 而**手机曾成功连上该热点** ⇒ **相机热点是接受客户端的**；
- ⇒ 失败原因是**主机侧**（MediaTek MT7921 驱动对这条非标准信标不买账），
  佐证：该信标的 `HT Operation` **Basic MCS Set 全 0（非典型）**、`Extended Capabilities` IE 只有 1 字节、
  `Beacon Interval = 200 TU`。驱动可以在扫描里列出它、却在选 BSS 时把它排除 —— 正好对应
  "热点稳定可见 88%，一连就报『特定的网络不可用』、`RSSI 255`"。

**行动含义**：Wi-Fi 面要继续，应该**换主机栈**（项目原来用的 macOS、或 Linux、
或用手机/Python 侧取证），而不是继续在 Windows 的 MT7921 上折腾。
