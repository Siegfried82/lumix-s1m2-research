# LUMIX Sync 2.0.17 漏洞初筛（2026-10-10）

范围：仅离线静态分析 `lumixsync.apk`（反编译源码 + native 库 + manifest）。
边界：未连接设备、未发送任何数据到相机、未对 Panasonic 在线服务做任何探测、未构造 exploit。
证据基准：`decompiled/sources/` 相对路径（jadx 反编译，行号为反编译源码行号）。

## 发现

### V1 固件列表下载使用"信任一切"TLS（高，代码证实）
- `p174v5/b.java:20-28`：`checkServerTrusted` 仅对叶证书做 `checkValidity()`（有效期检查），
  不验证颁发链、不校验 CA、不做 pin；`getAcceptedIssuers()` 返回 `null`。
- `p174v5/a.java:153-155,175`：该 TrustManager 被装入 `SSLContext("TLS")` 并设为
  固件列表下载的 socket factory。
- 受影响端点：
  - `FwUpdateActivity.java:518` → `https://panasonic.jp/support/share/eww/com/software/lumix_sync/firm_list.xml`
  - `HomeActivity.java:3126` → `https://panasonic.jp/support/share/eww/com/software/lumix_sync/apli_list.xml`
  - `InformationContentActivity.java:715/787`（同款列表逻辑）
- 后果：网络层攻击者（MITM/恶意 DNS）可替换固件列表 XML，从而控制其中 `url` 字段指向的
  固件下载地址。这是固件供应链的根。

### V2 固件文件下载无完整性校验 + 不受控重定向（高，代码证实）
- 下载器 `H5/c.java`（DownloadTask，约 180-340 行）：
  - URL 直接取自 V1 的列表 XML；
  - 手动跟随 301/302/303，`Location` 头不加校验（可 https→http 降级、可跨主机跳转）；
  - 响应体直接 `new FileOutputStream(strE)` 写盘；
  - 全程无 hash / 签名 / 内容长度终验。
- `FwUpdateActivity.java:2253`（`sb()`）：判定"已下载"仅检查本地文件是否存在。
- 注：`H5/c.java` 中 `responseCode == 200 → SERVER_ERROR` 的分支疑似反编译产物或逻辑倒置，
  未定性（未知项）。

### V3 手机→相机控制通道为明文 HTTP 且无认证（高，代码证实）
- `B5/a.java:167,1549`：相机基址 `this.f731n = String.format("http://%s", str)`（明文 HTTP）。
- 固件传输 `B5/a.java:676-694`（`O()`）：`f731n + n.c("startsenddata", ...)` 即
  明文 HTTP CGI 式端点，multipart 发送固件字节，请求头无认证（对比 `B5/m.java:50-110`
  的 SOAP 请求只有 User-Agent/Host/SOAPAction）。
- `B5/a.java:878`：`f731n + ":60606/Lumix/Server0/ddd"` 为更新相关端点（轮询握手）。
- `p202z5/a.java:213`：`"http://" + ip + ":60606/Server0/CDS_control"` 明文 HTTP 上跑
  UPnP/DLNA SOAP Browse（内容浏览/控制）。
- `libdlnaCore.so` 字符串：硬编码 `http://192.168.54.1:60606/Lumix/Server0/ddd`
  及 `DM_UPNPD_DEBUG_SSDP_PRINT` / `DM_DMS_DebugContentList` 调试开关字符串
  （字符串存在≠已启用，未定性）。
- 后果：同一 ad-hoc WiFi（或伪造相机 AP）上的任何设备可嗅探/注入相机控制流量，
  包括固件更新数据流。

### V4 远程 XML 控制应用行为（中，代码证实）
- `HomeActivity.java:3126-3133`：解析 `apli_list.xml` 后对远程字段做
  `Integer.parseInt(f30126c/f30127d)` 并直接驱动应用逻辑（更新检查/行为参数）。
  在 V1 的 trust-all TLS 下，这些值可被攻击者控制。

### V5 ZIP 条目名未净化（路径遍历，中，代码证实，依赖 V1/V2 前置）
- `N5/r.java:206-237`：固件 ZIP 解包只取第一个条目，`new File(nextEntry.getName())`
  直接拼入输出路径（`str2 + "/" + file.getName()`），无 canonical 校验。
- 攻击者若能替换固件 ZIP（V1+V2），可通过恶意条目名在应用存储目录内越界写文件。
- 前置依赖：需先获得固件下载内容控制权（V1+V2）。

## 端到端攻击链（每一跳均为代码证实）
1. 列表 XML：trust-all TLS 下载（V1）→ 攻击者可注入 `url` 字段；
2. 固件文件：不受控重定向 + 零完整性校验下载（V2）→ 任意字节落盘；
3. "已下载"=文件存在（V2）→ 无二次校验；
4. 明文 HTTP、无认证发送到相机（V3）→ 局域网内可再截获/篡改；
5. 相机端是否对收到的固件做签名/完整性校验：**未知**（依赖 S1M2 机内验证研究，
   现有离线证据既未证实也未排除）。

## 未知项
- 相机端固件校验机制（关键未决点，决定 V1+V2+V3 是否可端到端利用）。
- `H5/c.java` 响应码分支疑似反编译倒置。
- `libdlnaCore.so` 调试开关是否实际启用。
- 手机↔相机是否另有带证书的私链（Flow 的 TLS 7070/8080/9090 与 z_ca 属另一条链，
  本轮未覆盖 Flow 应用本体）。
- manifest 的 `usesCleartextTraffic`/`networkSecurityConfig` 取值未能从二进制 XML 确证
  （但控制通道代码层面已确认明文 HTTP，与 manifest 无关）。
