# Tether 维修查询：参数与接收边界核验

日期：2026-10-09。Antigravity 已停用，本轮由 Codex 直接分析既有 ARM64 反汇编；没有加载 Tether 程序或向相机发送请求。

## 本轮已核验的修正

旧报告 `analysis/tether_windows_review_20261009/maintenance_diagnostic_review.json` 将版本查询中的 `0x20001` 描述为固定请求参数。Mac 对应实现不支持该解释：

- 调用者第一个指针保存至 `x22`（`0x4aa1c`）。
- `0x00020001` 在 `0x4aa54..0x4aa5c` 构造并写入 `[x22]`，属于电脑端 API 输出；其具体版本语义仍待文档确认。
- 请求控制结构位于 `sp+8`，首字段为 `0x80030001`；附加参数数量在 `sp+0xc` 被设为零（`0x4aa60..0x4aa6c`）。
- 调用通用查询函数时 opcode 为 `0x9703`（`0x4aa7c`）。

因此这个 Mac 包装函数构造的 PTP 参数列表只有 `[0x80030001]`，不包含 `0x20001`。Windows 的同名实现应再独立追踪，不能仅凭名称认定二者完全相同。

## 可定位的通用序列化入口

底层 `Lmx_lib_ptpif_LmxExt_Mnt_GetInfo`（`0x4aadc`）并非仅接受一个固定子码：

| 控制结构位置 | 代码行为 | 定位 |
| --- | --- | --- |
| +0 | 读取调用者提供的 32 位 selector，写入请求第一参数 | `0x4ab34..0x4ab38` |
| +4 | 读取 16 位附加参数数量，请求参数数量 = 此值 + 1 | `0x4ab28..0x4ab30` |
| +8 | 数量非零时复制附加 32 位参数至请求 | `0x4ab40..0x4ab4c` |

本文件中对该底层函数的直接调用只有两个：版本查询和 USB 模式查询。后者构造 `[0x80030002]`，没有附加参数（控制结构先清零）。这限定了已观察到的公开包装用法，没有穷尽相机端支持的 selector。

## 接收容量不等于设备可读内存

`Get_NextPhase_StdOpCode` 中，`0x9703` 对应 phase 3：`1 << (0x9703-0x9701)` 命中掩码 `0x66`，保存初始值 3。查询函数在该分支分配电脑端接收缓冲区 `0x10001c` 字节（`0x4ab78..0x4ab9c`），再传入 `SendCommand`。

这推翻了“查询函数只接收 4 字节”的笼统说法，但不证明相机实际会返回如此大的数据。返回解析器只识别记录标签 `0x80030001`、`0x80030002`，分别取 16 位或 32 位值，再将其以 4 字节标量写给调用者。未知标签走失败分支。包装函数输出宽度与传输接收容量是不同层级。

## 对固件/RAM研究的意义

- 已取得一条可定位的维护查询构造链，修正了旧审计的固定参数与固定接收长度判断。
- 底层接受附加参数，仅说明电脑端可以序列化这些值；没有证据表明相机端将它们解释为内存地址或长度。
- 仍未获得相机端 handler、未知 selector 的语义、程序明文或任意地址读取能力。未知子码不得据此盲目枚举。
- 后续离线工作可继续对比 Windows 对应实现，并检查现有官方客户端中是否有同族调用或资源描述。真机验证只应使用已有语义证据的请求，并单独登记授权与预期结果。

## Windows 独立交叉核验

随后直接对本地 `Lmxptpif.dll` 进行静态反汇编。该 DLL 是 PE32+ x86-64，ImageBase 为 `0x180000000`；没有加载或执行它。

13 条关键指令检查通过，记录在 `codex_windows_maintenance.json`。关键位置如下，均为 DLL 内 RVA：

| 判断 | Windows 证据 |
| --- | --- |
| `0x20001` 写入电脑端第一个输出指针 | `0x1a6be` 保存 RCX 至 R14，`0x1a71e` 写入 `[R14]` |
| 版本请求仅含 selector，无附加参数 | `0x1a725` 写 `0x80030001` 至控制结构，`0x1a72d` 写零数量 |
| USB 模式请求也无附加参数 | `0x1a82b` 写 `0x80030002`，`0x1a833` 写零数量 |
| 内部查询构造可变参数 | `0x1a89f` 读取 +4 的数量；`0x1a8bb` 数量加一；`0x1a8c2` 读取 selector；`0x1a8da..0x1a8e6` 复制 +8 的参数数组 |
| 电脑端接收容量 `0x10001c` | `0x1a923` 构造容量，`0x1a9ba` 将其传给传输层 |
| 版本/USB 返回取值分别为 16/32 位 | `0x1aa63` / `0x1aa49` |
| 向调用者报告的输出宽度为 4 字节 | `0x1aa75` |

Windows 内部查询入口位于 RVA `0x1a870`。对整个 DLL 的已解码直接 call/jump 扫描只找到两个直接调用点：`0x1a733`（版本）与 `0x1a838`（USB 模式）。没有在这两个调用中发现传入物理地址或读取长度；但没有穷尽间接调用、函数指针或设备端处理器，不能宣布所有读取路线不存在。

这里也发现一个平台差别：Windows 内部查询函数直接构造 opcode `0x9703`，Mac 同族底层函数通过参数接收 opcode。二者的已知包装行为一致，不宜表述为底层所有行为完全相同。

`objdump` 将内部函数标注为最近导出函数加偏移，因此 `Get_UsbMode+0xd0` 只是显示标签，不是另一条 USB 模式业务入口。三个完整定点反汇编保存在 `codex_windows_version.txt`、`codex_windows_usb_mode.txt`、`codex_windows_internal_query.txt`。

本轮结果收窄了主机侧证据：通用参数序列化入口真实存在，目前定位到的两条使用路径均为标量信息查询。仍缺其他调用者或相机端 dispatcher，尚不能将该入口转化为固件/RAM 导出能力。

## 地址引用与重定位核验

`codex_pointer_xrefs.py` 从 DLL 原始 PE 元数据解析并检查了 11,940 个 DIR64 重定位项、6,957 条运行时函数范围，结合全 DLL 已解码指令和逐字节地址查找。结果保存在 `codex_pointer_xrefs.json`。

- 查询函数 RVA `0x1a870` 没有检出的绝对地址存储、DIR64 函数指针引用或已解码 LEA/MOV 地址构造，直接调用仍仅两个。
- 原始 32 位 RVA 字节仅在 `.pdata` 的函数范围记录命中：`[0x1a870, 0x1aaa3)`，unwind 信息 RVA `0x22fdb0`。该项支持函数边界，不是可调用的函数指针表。
- 两个公开包装函数的 RVA 分别存在于 `.rdata` 导出地址表及 `.pdata`，同样没有检出的绝对函数指针。导出表使外部程序可以动态解析包装函数，因此 DLL 内没有调用引用不意味着接口不能使用。
- 初版扫描曾把指令自身的地址误算为 MOV 地址构造；已排除冒号前的指令地址并重跑，三处目标的构造引用均为零。

本轮未发现这条维修查询链存在第三个静态调用者。检查不涵盖经过编码/运行时计算的地址、动态解析或运行时加载模块的数据流，不能排除相机端其他子码。主机侧证据目前不足以把通用查询转化为任意内存读取。
