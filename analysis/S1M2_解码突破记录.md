## 2. PTool 的旧款解码已经实际还原成功

从作者公开地址取得 PTool，只解析 PE、字符串、数据表与 x86 反汇编。**未执行 EXE，未使用 Wine，也未运行镜像中的代码。**

PTool EXE SHA-256：`57a0b1ab911e6e7a672ab971a8f32aef6161029104ad14f78fe8de297788dd2f`。

在这一个确定版本的 PTool 中，静态地址证据如下。这些是 PTool 主机程序地址，不是 S1M2 相机地址。

| 地址 | 可读到的行为 |
|---|---|
| `0x5260a8` | LoadFirmwareClick；调用文件读取、型号识别流程 |
| `0x4f2f24` | 计算输入文件 MD5，匹配已支持固件的数据表 |
| `0x4f44e0` | 按记录中的方法字段，选择旧编码、AES 或另一种分支 |
| `0x4f3c9c` | AES 分支：复制 512 字节头部，读取 IV、抽取 16 字节 key，再解码余下文件 |
| `0x4f1828` / `0x4f19e8` | AES 解码上下文初始化、CBC 解码流程 |
| `0x6ae10c` | 与 GH2 V1.1 输入 MD5 匹配的记录，方法字段为 1 |

对于该 GH2 V1.1 样本，还原出的磁盘文件解码为：

```text
table = [77,350,198,71,290,98,136,184,206,301,281,147,611,239,8,84]
key[i] = input[0x200 + i*0x200 + table[i]]   (i = 0..15)
iv = input[0x80:0x90]
output[0:0x200] = input[0:0x200]
output[0x200:] = AES-128-CBC-decrypt(input[0x200:], key, iv)
```

实测 key 为 `90b43b5ce34c6e667fb28376b5fa5c27`。它属于旧 GH2 样本，不是 S1M2 的密钥。

验证不是凭“看起来像代码”判断：

1. GH2 BIN 的输入 MD5 为 `0be86add14ebb1bca79a9c6222a1d617`，与 PTool 支持记录完整匹配。
2. 解码后 `[0x200, EOF)` 的 MD5 为 `d88f4506546ce8e2ab264a7548c3dee0`，与原固件头部 `[0x40,0x50)` 完整匹配。
3. 解码文件 SHA-256 为 `7d34331dda3d40798084c80b5052dc8a307079facf53f1b7d17e2e39f4a8f36b`。
4. 明文中出现型号头、填充区、错误信息和文件路径等结构；这些只是辅助检查。

PTool 还在自己的处理流程中对解码结果使用 RC4，其 key 与输入文件 MD5 相同。**这一阶段不能当成磁盘固件解密的必要层。** 单独 AES 阶段已经满足固件记录的整段 MD5；再加 RC4 会使该明文失去匹配。脚本保存的是经过校验的 AES 明文。

GH2 验证输入来自旧固件镜像站的自解压文件。文件实际包含一个未压缩 RAR4 成员，并非 ZIP；用本地解析代码提取 BIN，核对 RAR 头部及成员 CRC32。未运行自解压程序。PTool 内置输入 MD5 提供了额外的样本对应检查。

复现与证据：

- `extract_gh2_control.py`、`sources/gh2_control_extraction.json`：静态提取对照 BIN。
- `recover_ptool_crypto.py`、`ptool_crypto_results.json`：提取表、还原 AES 流程、校验及 S1M2 有限探测。
- `sources/ptool_static/aes_loader_disassembly.txt`：从明确函数起点重新反汇编，避免把数据中的任意字节当成指令入口。
- `control_decrypted/GH2__V11.bin`：验证成功的旧 GH2 明文，**不能用于 S1M2**。

## 3. S1M2 V1.3 与 V1.4 的真实差异

V1.3 的 Panasonic 旧直链返回 404，因此采用公开备份；没有宣称它经过当前官方服务器逐字节验证。其目录边界、全部组件范围和外层 CRC32均通过检查。出处与哈希保存于 `sources/additional_source_manifest.json`。

V1.3 BIN：171,605,504 字节，SHA-256 `cc512f22374005ec99cbe458809b996f3d9ee441b2a8034330708463739c9c66`。

两版组件数、组件顺序、名称及目标字段相同。62 项分为：

| 数量 | 目录哈希 | 原始载荷哈希 | 目录尾字段 |
|---:|---|---|---|
| 13 | 相同 | 相同 | 相同 |
| 37 | 相同 | 不同 | 不同 |
| 12 | 不同 | 不同 | 不同 |

13 项均属于可直接校验的填充/空组件。49 个编码组件的原始数据全都变化，而其中 37 个的目录哈希未变。因此，“密文全变了”不能解释为“全部代码都改了”。目录哈希很可能对应解码内容；未真正解码前，该含义保留边界。

目录哈希变化的 12 项：

```text
1 loader1
5 program
6 compress_pr
7 postboot1_r
9 postboot3_r
11 postboot5_r
12 postboot1_r
13 postboot3_r
14 postboot5_r
18 eep_fix
25 osdover
26 osddata
```

`osdover`、`osddata` 各增大 131,072 字节；总大小增加 262,144 字节。`hr_*`、`dsp_fstack_*`、`fstack_c_ex`、`hm_d_reid` 等候选组件的目录哈希相同。


复现：`compare_versions.py`、`version_comparison.json`。

## 4. 更严格的 S1M2 解码试验

旧 PTool 中 6 组 AES 抽取偏移表，以及 12 个输入 MD5/内部 RC4 key，均进行了有限移植探测。共 120 个已记录组合，没有匹配 S1M2 第 8、10 项的已知填充候选散列。阳性对照证明我们还原的 GH2 方法有效；阴性结果只说明这些移植组合没有成功。

此前的 11,000 次 AES 探测假定目录尾部 16 字节是 IV。此次加入一个不依赖 IV 的验证：若第 8、10 项的解码内容确为全 FF，普通固定 key 的 CBC 必须满足

```text
D_key(C2) XOR C1 = FF*16
D_key(C3) XOR C2 = FF*16
```

因此可先检查后两个块，再在 key 匹配后反推 IV，并用整段 SHA-256 作最终验证。这样不会因猜错 IV 而误排一个真正的 CBC key。

本次测试覆盖整个头部/目录每一个字节起点的 16/24/32 字节候选、XOR FF 变体，以及名称/散列/尾字段/目录项的 MD5、SHA-256 构造：33,090 个去重 key，两个组件和两个 AES 原语方向，共 132,360 次试验，未匹配。

**结论严格限于：这些候选不是所测试的固定-key CBC、原始全 FF 明文假设下的 key。** 没有确认 S1M2 使用 AES，也没有排除密钥派生、封装密钥、其他模式、不同算法、压缩或私有变换。这不是对 AES 密钥空间的穷举。

复现：`probe_cbc_without_iv.py`、`cbc_without_iv_probes.json`。

## 5. 完整逆向现在还缺哪一层

| 层级 | 本轮结束时状态 |
|---|---|
| 文件来源和完整性 | V1.4 已与官方服务器内容逐字节哈希对应 |
| UPD 封装、目录、外层 CRC | 已验证；未证明全部认证字段 |
| 旧 GH2 解码 | 已从 PTool 静态还原，并以整段 MD5 验证 |
| S1M2 解码 | 尚未成功；已记录跨版本关系与有限阴性结果 |
| S1M2 专有程序架构和加载地址 | 尚未由明文确认；开源板级代码不能代替 |
| 全部输入 RAW 的生命周期和写入路径 | 尚未定位 |

当前文件里没有可直接读取的非填充程序组件，公开源码中尚未找到专有更新解码器。关键入口是 **S1M2/同平台的明文更新加载器、可检查的解码工具/实现，或能提供真实解码流程的其他证据**。这类入口能让研究从有限猜测进入算法与数据流还原。它们目前不在已读文件中。

不能据此断言“只能实机提取”或“永远无法离线突破”；也不能把更多无依据的 key 枚举当成已经开展了程序逆向。尚未得到 S1M2 明文时，给出快门、HDR 或授权检查的补丁地址会是编造。

- [unixtract 作者支持清单](https://github.com/theubusu/unixtract)：列出的 Panasonic 部分是电视、蓝光等格式；本次未找到 Lumix UPD 支持。没有将其电视密钥或格式解码器当作相机算法。
