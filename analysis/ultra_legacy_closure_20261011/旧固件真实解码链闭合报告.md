# GH2 / TZ10 真实更新器解码链核验

2026-10-11。仅把固件作为数据读取、反汇编和离线重放；未执行固件、目标对象或自解压程序，未连接、写入或刷写相机。新增文件限于本目录。

GH2 V1.1 的更新器现在能连接到真实 AES-CBC 解码和 MD5 消费者；TZ10 V1.2 的更新器也能连接到种子 getter、双重 XOR 掩码、MT 输出和明文奇偶性控制的流解码。两条链均以完整主体 MD5 和现存明文逐字节一致作为阳性验收。它们证明所列旧格式，不能证明 S1M2 已解密，也不能把旧机型选择器的值当作新格式的算法声明。

## 2. GH2：header → resident key → AES-CBC → MD5

### 2.1 格式检查和两个独立 selector

`GH2_updater.disassembly.txt:128–160`，VA0x7bcd5b13..0x7bcd5b59：从已读入的 512 字节头读取 `header+0x08` 并比较 `0x101`，随后逐字节检查 `UPD\0`，限制 header+0x04≤512、主体长度 header+0x3c≤分配容量。`0x101` 是这一实现接受的格式条件，不能仅由该值推出密码算法。

`GH2_updater.disassembly.txt:188–240`，VA0x7bcd5baf..0x7bcd5c12：

- `header+0x2c` 为 0 或 1 时不创建此 MD5 对象；为 2 时调用 VA0x401555ae 创建；其他值走错误路径。
- `header+0x34` 为 0 时跳过此 AES 路径；为 2 时调用 VA0x40155618 创建 AES 对象、设置 128 位参数、复制 updater+0x28 的 key、设置模式 1，并复制 header+0x80 的 16 字节 IV；其他值走错误路径。

GH2 V1.1 实际头的 +0x2c=2、+0x34=2、+0x38=0x200、+0x3c=0xee0400。这里必须区分外层字段、PTool method 编号和 AES 内部 mode，不将它们合并命名。

### 2.2 resident key 是真实参数，不是仅有字节命中

`GH2_boot_copy.disassembly.txt`，VA0x40000195..0x400001b2 / file0x795..0x7b2：启动程序逐 32 位复制 ROM `[0x407f4cd0,0x407f6384)` 到 RAM0x74000000，因此 ROM0x407f4cf8 / file0x7f52f8 对应 RAM0x74000028。

`GH2_resident_key_caller.disassembly.txt:97–118`，VA0x7bcd61c6 / file0x9d67c6：明确把 RAM0x74000028 放入 a1、16 放入 d0，调用 VA0x7bcd5a8a；该函数（`GH2_updater.disassembly.txt:72–91`）将 16 字节复制到 updater+0x28，随后 caller 调用 VA0x7bcd5b67 开始主体处理。AES wrapper VA0x40155670 将 128/8=16 传给核心 VA0x4006042c，复制 key 并设 Nk=4、Nr=10。

实际 16 字节为 `90b43b5ce34c6e667fb28376b5fa5c27`。本轮确认它等于 PTool V1.1 已验收的抽样 key；没有把另一版本的文件偏移规则套入 V1.2。

### 2.3 vtable 解析和 CBC 语义

MD5 vtable VA0x40249988 只有这条对象需要的 5 个 slot；AES vtable从 VA0x4024999c 开始。上一份通用 12-word 清单会跨过 MD5 表尾，这里按构造函数和实际 slot 区分，见 verification.json 的 `vtable_slots`。

| 操作 | 更新器实际 slot → wrapper → 核心 |
|---|---|
| AES 解码准备 | +0x1c → VA0x401556a1 → VA0x400604b0 → VA0x40060d59 |
| AES 分块解码 | +0x24 → VA0x401556c9 → VA0x400605a6 |
| MD5 初始化 | +0x04 → VA0x401555ca → VA0x40003c5c |
| MD5 update | +0x08 → VA0x401555da → VA0x40003c88 |
| MD5 final | +0x0c → VA0x401555ea → VA0x40003d0b |
| 导出 16 字节摘要 | +0x10 → VA0x40155600 |

AES 准备函数先生成 round keys，再反转 round-key 次序并处理中间轮（`GH2_aes_key_schedule.disassembly.txt`，VA0x40060d59..0x40060e1c）。实际解码消费者（`GH2_aes_consumer.disassembly.txt`，VA0x400605a6..0x40060679）按 16 字节运行：保存旧 chaining block，将当前密文复制为新 chaining block，调用 VA0x400609b2 的逆向块变换（`GH2_aes_inverse_block.disassembly.txt`），再与保存的旧 block XOR。第一次旧 block 来自 header+0x80。它是 CBC 解码的数据关系，而非由 AES 表命中推断模式。

更新器在 VA0x7bcd5c34 以 header+0x38 定位源文件，读入 header+0x3c 字节至主体缓存；VA0x7bcd5cea / 0x7bcd5d1e 调用上述 AES prepare/process。随后 MD5 对同一缓存、同一长度分块 update（VA0x7bcd5dc1..0x7bcd5df0），final 并将 16 字节摘要与 header+0x40 比较（VA0x7bcd5e3b..0x7bcd5e7e）。因此样本的校验范围为解码后的 `[0x200,0xee0600)`，包括嵌套头、目录、program 与 eep，不只 program。

### 2.4 当前阳性重放

本轮直接从 resident key 位置取固定 key，用 OpenSSL AES-128-CBC、各输入自己的 IV、无 padding 解码完整主体：

| 输入 | 解码主体 MD5 = header[0x40:0x50] | 与既有完整明文 |
|---|---|---|
| GH2 V1.1 | `d88f4506546ce8e2ab264a7548c3dee0` | 逐字节一致 |
| GH2 V1.2 | `35cb77e2ef08df9ef334ff1e496b0b02` | 逐字节一致 |

V1.2 成功验证固定旧 key 复用；本轮真实调用链反汇编的是 V1.1，不能由此声称已逐函数核对 V1.2 更新器。

## 3. TZ10：更新入口、种子 getter 与真正 MT 消费者

### 3.1 从 UPD 检查连到主体处理

`TZ10_header_and_md5_wrapper.disassembly.txt`，VA0x77b8c64e..0x77b8c70b / file0x310c4e..0x310d0b：`UPD\0` 字符串位于 VA0x77c633f8 / file0x3e79f8；VA0x77b8c650 的立即数在 file0x310c52，随后按 4 字节 compare，读取 header+0x08 并比较 0x101。+0x34接受0/1；+0x2c接受0/2，另检验长度/偏移。更新器 VA0x77b8be73 / file0x310473 实际调用它。

`TZ10_update_data_path.disassembly.txt:81–186`，VA0x77b8be94..0x77b8bf85：从 header+0x38 位置读 header+0x3c 字节到主体缓存。已保存的 header 基址为0xb4bc0000，读入主体为0xb4bc0200；变换和MD5路径使用0x74bc0200。代码显示更新器按这两个地址作为缓存别名使用；这是数据关系支持的静态推断，本轮未实测MMU或缓存映射，也不外推到其他机型。

VA0x77b8bf01 / file0x310501：+0x34=1 时，配置结构+0x14作为种子参数、d1=16、d0=1，调用 VA0x7789b94c；随后以 header+0x3c 为长度调用 VA0x7789b9a6。+0x34=0则跳过。+0x2c=2时调用 VA0x77b8c7b7 的 MD5 wrapper，对同一解码缓存和完整长度计算 16 字节摘要，VA0x77b8bf77 与 header+0x40比较。`TZ10_md5_front.disassembly.txt`核验了 wrapper 的 init/update/final 落点与 padding/bit-count 行为。

### 3.2 种子来源已经有调用关系

两个 caller 分别在 VA0x77a64d04..0x77a64d4e（`TZ10_seed_origin_first.disassembly.txt:43–75`）和 VA0x77b62f7f..0x77b62f8e（`TZ10_seed_origin_second.disassembly.txt:28–35`），向配置结构+0x14传入 getter VA0x7789ba22 的输出，然后把该结构传给更新入口 VA0x77b8bded。不是仅在固件中搜索到 seed 后猜测使用。

getter VA0x7789ba22..0x7789ba60 读取长度常量 file0x341bd4=16，将 seed file0x341bc4 与 mask file0x341ba4 逐字节 XOR。初始化器 VA0x7789b94c..0x7789b9a3（`TZ10_cipher_and_seed_getter.disassembly.txt:7–54`）又把传入16字节与 mask file0x341b84 XOR，再以4个32位字调用 local MT init_by_array VA0x778956e4；两份32字节mask当前逐字节相等，所以两次 XOR 还原 seed。初始化后 context+2500 清零，这是第一轮 parity 的前一明文字。

resident seed 为 `0c9ef8efe6cd114f1f441e3e6735c285`，与 PTool 在原始 TZ10 文件所列16处抽样位置取得的 bytes 完全相同。抽样位置与两份mask相等检查均在 verification.json；固件路径使用 resident seed，不从该吻合推出相机也执行 PTool 的抽样取钥规则。

### 3.3 对 MT 输出的真实消费与阳性重放

VA0x7789b9a6..0x7789ba1f（`TZ10_cipher_and_seed_getter.disassembly.txt:57–118`）先读 context+2500 为 prev_plain。逐32位字计数前一明文的 bits：奇数时在 VA0x7789ba02 调用 local MT generator VA0x778957d8并丢弃输出；VA0x7789ba09始终取得下一输出；VA0x7789ba10把它与当前密文字 XOR 并原位写回，保存新明文作为反馈；最后更新 context+2500。这与单纯 `cipher XOR standard MT stream` 有明确区别。

local MT 初始化 VA0x778956e4、seed扩展 VA0x77895799、generator VA0x778957d8具有完整状态624字、397/227 twist和temper数据关系。GNU当前将部分乘法编码显示为 `udfu01`；官方表存在AM30乘法别名，详见工具目录AGENTS和正对照。静态助记符并非已验证的真实硬件语义，算法认定还依靠完整调用关系与下述主体阳性，未声称执行了目标ISA仿真。

本轮使用上述 resident seed、已经读过的透明Python MT实现重放原始 `[0x200,0xfd2e00)`；4,147,968 个主体字、1,593,097 次额外discard；完整主体 MD5=`7125ec82bbc118824b0a41d9d86a8716`=头部值，且与既有 TZ10 解码文件逐字节一致。此检查复用了已有Python generator，不是另一套独立MT实现，也未重新运行其旧报告所有测试。

另一套 global MT 位于 file0x3050e2/0x30511b/0x3051e3，有普通调用者（例如file0x2e5d73），当前更新解码链明确调用上述local MT；不能由另一处同常量MT认定它也承担固件解码。

## 4. 仍未确认与复现

- 分支语义限于上述已定位 GH2 / TZ10 输入。S1M2 的 MC8243 分段、selector、密钥、派生和保护算法没有因此闭合。
- 这里没有设备运行记录、刷写验收或目标ISA全程序仿真；静态地址关系与离线完整摘要阳性分开表述。
- TZ10 resident seed 与PTool抽样一致不证明跨版本固定seed；GH2 V1.2阳性不证明跨机型共钥。
- Direct-call候选搜索不排除间接调用、其他overlay、别的编码变体或其他seed/key用途；未作无依据密钥枚举。
- 本子任务没有新建Antigravity任务，以主线程已有委派为准；不将其未核验元数据当作本报告证明。
