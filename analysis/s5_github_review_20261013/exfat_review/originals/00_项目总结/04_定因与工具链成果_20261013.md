## 二、直接看结论

### 2.1 本日确认成立的

| # | 结论 | 证据 |
|---|---|---|
| **1** | **内核对簇号不做归属校验**：释放文件簇时**完全跟随卡上被篡改的 FAT 链值** | 位图实机比对：注入的簇（不属于被删文件）确实被释放 |
| **2** | **越界索引处存在 NULL 检查、会提前返回** | 决定性实验：注入 slab 填充区索引 → 只报错**不崩溃** |
| **3** | **360 个 240 字符长文件名 → DC-S5 开机反复重启** | 四组对照矩阵（见 2.3） |
| **4** | **纯目录项即可触发崩溃**，不需要文件数据、不需要任何注入 | `mkentries` 直接写目录项即可复现 |

### 2.2 本日**撤回**的（重要）

| 结论 | 状态 | 撤回依据 |
|---|---|---|
| "S5 内核越界写已实机确认" | ❌ **撤回** | 注入**必为 NULL** 的 slab 填充区索引 → 只报错不崩 ⇒ 存在 NULL 提前返回；原推理"报卡写失败 ⇒ 内存写已执行"**不成立** |
| "堆喷命中越界槽" | ❌ **撤回** | A/B 对照：**去掉注入后照样重启** ⇒ 崩溃不能归因于注入 |
| "长名崩溃 = 数量 × 长度" | ⚠️ **修正** | 初版实验里**我们自己的工具把目录链拐进了照片数据区** ⇒ 崩溃另有原因。重做后结论为：**长文件名本身** |

> **方法论教训（已写入铁律）**：
> **① 没有对照组的结论不要写进报告。**
> **② "相机报写入错误"不能当作"内存写已执行"的判据** —— NULL 提前返回的表现完全一样。
> （**S1R2 报告也用了这个判据**，后人不应照抄。）

### 2.3 长名崩溃的四组对照矩阵（全部在干净卡上）

| 组 | 文件数 | 名字长度 | entry set | 目录条目 | 目录体量 | 相机 |
|---|---|---|---|---|---|---|
| A | 241 | 240 字符 | 576 B | 2169 | 139 KB | ✅ |
| **B** | **360** | **240 字符** | 576 B | **6480** | **202 KB** | ❌ **反复重启** |
| C | 2160 | 12 字符 | 96 B | 6480 | 202 KB | ✅ |
| **D** | **360** | **12 字符**（`num_ext=17`） | **576 B** | 6480 | 202 KB | ✅ |

- **B vs C**（条目数、体量、跨簇数全同）⇒ 排除"数量/体量"
- **B vs D**（分配大小全同）⇒ 排除"分配大小"
- **⇒ 唯一剩余变量：240 字符长文件名本身**

**能解释全部数据的模型**：

```
A: 241 × 240 = 58 KB  → ✅        C: 2160 × 12 = 26 KB → ✅
B: 360 × 240 = 86 KB  → ❌        D: 360 × 12  =  4 KB → ✅
⇒ 阈值在 58–86 KB 之间，很像「定长缓冲 + 长度未校验」= 内存破坏类问题
```

## 三、这个发现的**价值边界**（很重要，别高估）

| 层面 | 评价 |
|---|---|
| **作为攻击面** | 🟡 **有限** —— 只是**拒绝服务**，而"把卡做坏"本身就能让相机没法用，不构成新能力 |
| **作为漏洞线索** | 🟢 **有真价值** —— 与文件名字节总量相关的崩溃，典型成因是**定长缓冲溢出**（内存破坏类），比被 NULL 检查挡住的 exFAT 位图路径**更接近可利用** |
| **作为诊断信息** | 🟢 **立刻可用** —— 说明 S5 的**缓冲余量很紧**，任何堆布局相关的尝试都要把这条边界算进去 |
| **进一步利用** | 🔴 **需要调试通道**（UART/JTAG）。目前只有"崩/不崩"一个二值信号，与 exFAT 那条路遇到的是**同一堵墙** |

## 四、本日最该记住的三件事

### 4.1 我们自己的工具曾把卡写坏（**已修复**）

```
根因：alloc_one_cluster() 只信分配位图；
      而相机位图【延迟写回】——未正常关机就拔卡，位图停在旧状态
后果：分配器拿到【照片正在使用的簇】→ 清零 + 断链 + 目录链拐进数据区
症状：照片"文件在、但无法访问/无法删除"
证据：FAT[39] 被改成 482（照片本该 39→40→…→115）
```

**修复**：分配簇改为**三重校验** —— `位图位==0` **且** `不在目录链上` **且** `FAT[clu]==0`。

### 4.2 由此产生的两条硬规矩

1. **拔 SD 卡前必须在相机里正常关机**（让位图落盘）
2. **每次写卡前后都必须跑 `checkalloc`**，`K > 0` 立即停手

### 4.3 三个"看起来像成功"的陷阱

| 陷阱 | 真相 |
|---|---|
| 相机报"写入错误" ⇒ 以为内存写执行了 | 可能是 **NULL 提前返回** |
| 相机重启 ⇒ 以为攻击命中 | 可能**与我们无关**（A/B 对照才发现） |
| 改了 FAT 后"能开机" ⇒ 以为补丁生效 | 可能**根本没被读到**（卡代次/指纹已变） |

## 六、复现入口（最短路径）

```bash
# 0) 拷贝工具到 /tmp（TCC 保护不到这里）
#    工具现位于 04_工具与脚本/campaign2/（原包内 02_工具链/exfat/ 的副本已去重移除）
TOOLS=04_工具与脚本/campaign2
mkdir -p /tmp/s5exfat && cp "$TOOLS"/exfat_patch.py "$TOOLS"/exfat_spray.py "$TOOLS"/s5_exfat_test.sh /tmp/s5exfat/ && chmod +x /tmp/s5exfat/*

# 1) 相机格式化 SDXC（>32GB）→ 拍 1 张 → 【正常关机】→ 拔卡插到 Mac

# 2) 写前体检（必须 K = 0，否则停手）
sudo bash /tmp/s5exfat/s5_exfat_test.sh checkalloc /dev/disk8s1

# 3) 写 360 个 240 字符长名目录项（复现崩溃）
sudo bash /tmp/s5exfat/s5_exfat_test.sh mkentries /dev/disk8s1 360 240 0

# 4) 写后体检（K 必须仍为 0；并检查"目录簇链"的新簇不在照片数据区）
sudo bash /tmp/s5exfat/s5_exfat_test.sh checkalloc /dev/disk8s1

# 5) 【正常关机】后拔卡 → 插进相机开机 → 应反复重启
```

**恢复**：从相机拔卡 → Mac 上 `diskutil eraseVolume ExFAT LUMIX /dev/disk8s1` →
插进相机让它自己格式化。**卡可完全恢复，无硬件损伤。**
