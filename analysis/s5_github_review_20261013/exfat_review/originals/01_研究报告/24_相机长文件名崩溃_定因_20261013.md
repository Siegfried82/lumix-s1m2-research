# DC-S5「长文件名导致开机反复重启」——定因报告

2026-10-13 · 一次纯软件、**不改固件、不拆机**的相机崩溃复现与归因
承接：`23_S5_exFAT越界写实机确认_20261013.md`（本文澄清了其中被污染的结论）

---

## 0. 结论

> **在 `DCIM/100_PANA` 里放入约 300 个以上「240 字符长文件名」的目录项，
> DC-S5 开机时会反复重启（boot loop）。**

| 已排除的变量 | 证据 |
|---|---|
| ❌ 文件数量 | 2160 个短名文件 → 正常 |
| ❌ 目录内容体量 | 202 KB 的短名条目 → 正常 |
| ❌ 目录跨簇数 | 139 KB 跨 2 簇正常、202 KB 也跨 2 簇却崩 |
| ❌ entry set 分配大小（576 B） | 360 个**短名+篡改 `num_ext`**（同样 576 B 分配）→ 正常 |
| ✅ **长文件名本身** | 360 个 **240 字符**长名 → **崩**；360 个 12 字符 → 正常 |

## 1. 四组实验矩阵（全部在**同构的干净卡**上）

| 组 | 文件数 | 名字长度 | entry set | 目录条目 | 目录体量 | 相机 |
|---|---|---|---|---|---|---|
| A | 241 | 240 字符 | 576 B | 2169 | 139 KB | ✅ |
| **B** | **360** | **240 字符** | 576 B | **6480** | **202 KB** | ❌ **反复重启** |
| C | 2160 | 12 字符 | 96 B | 6480 | 202 KB | ✅ |
| **D** | **360** | **12 字符**（`num_ext=17`） | **576 B** | **6480** | **202 KB** | ✅ |

- **B vs C**：条目数、目录体量、跨簇数**完全相同**，只有名字长度与 entry set 大小不同 ⇒ 排除"数量/体量"
- **B vs D**：分配大小**完全相同**（都是 576 B），只有名字长度不同 ⇒ **排除"分配大小"，锁定"长文件名"**

## 2. 一个能解释全部数据的模型

若相机把文件名**累加**到某块固定缓冲中：

```
A: 241 × 240 字符 = 58 KB   → ✅ 正常
B: 360 × 240 字符 = 86 KB   → ❌ 崩溃
C: 2160 ×  12 字符 = 26 KB  → ✅ 正常
D: 360 ×  12 字符 =  4 KB   → ✅ 正常
```

**完全吻合"在 58 KB 与 86 KB 之间存在一道墙"。**

这很像 **定长缓冲 + 长度未校验**，即**内存破坏类**问题，而不仅是普通 DoS。
**要确认阈值是否对齐某个整数（如 64 KB），只需再做一次二分**（见 §5）。

## 3. 复现配方（纯目录项即可触发）

**不需要任何真实数据**，只要目录项：

```bash
# 前提：相机格式化的 exFAT SDXC 卡，DCIM/100_PANA 存在（相机拍过至少 1 张）
# ① 写前体检（必须 K=0）
sudo bash /tmp/s5exfat/s5_exfat_test.sh checkalloc /dev/disk8s1
# ② 写 360 个 240 字符长名条目
sudo bash /tmp/s5exfat/s5_exfat_test.sh mkentries /dev/disk8s1 360 240 0
# ③ 写后体检（必须 K=0、且目录新簇不在照片数据区）
sudo bash /tmp/s5exfat/s5_exfat_test.sh checkalloc /dev/disk8s1
# ④ 相机里【正常关机】后拔卡 → 插卡开机 → 反复重启
```

**恢复**：把卡插回 Mac，`diskutil eraseVolume ExFAT LUMIX /dev/disk8s1`，
再插进相机让它自己格式化。

## 4. 这条发现值多少？

### 4.1 作为攻击面：**价值有限**

它只是**拒绝服务**，而且触发方式就是把卡做坏 —— 攻击者本来就能让相机没法用，
**不构成新的攻击能力**。

### 4.2 作为漏洞线索：**有真价值**

> 「与**文件名字节总量**相关的崩溃」典型成因是**定长缓冲溢出** ——
> 属于**内存破坏类**，比被 NULL 检查挡住的 exFAT 位图路径**更接近可利用**。

### 4.3 作为诊断信息：**立刻可用**

它说明 S5 的**内存/缓冲余量很紧**，任何后续堆布局相关的尝试都要把这条边界算进去。

| 优先 | 动作 | 目的 |

## 6. 必须记录的两个自身教训

### 6.1 我们的工具曾把卡写坏（已修复）

`alloc_one_cluster()` 早期**只信分配位图**。而相机的位图存在**滞后风险**
（未正常关机就拔卡 → 位图停在旧状态）⇒ 分配器拿到了**照片正在使用的簇**：

```
症状：照片"文件在、但无法访问/无法删除"
证据：FAT[39] 被改成 482（照片本该 39→40→…→115）
```

**后果**：除了毁掉照片，还**污染了当时的实验结论** ——
早期那次"崩溃"很可能是目录链被拐进数据区后内核遍历到垃圾所致。

**修复**（已实现）：分配簇时**三重校验** ——
`位图位 == 0` **且** `不在目录链上` **且** `FAT[clu] == 0`。

### 6.2 由此产生的两条硬规矩

1. **拔卡前必须在相机里正常关机**（让位图落盘）
2. **每次写卡前后都必须跑 `checkalloc`**，`K > 0` 就停手
