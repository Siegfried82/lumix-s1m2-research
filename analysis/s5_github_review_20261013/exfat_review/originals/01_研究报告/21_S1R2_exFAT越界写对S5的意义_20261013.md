# S1R2 exFAT 内核越界写：对 S5 固件解密路线的意义（2026-10-13 评估）

> 输入：S1R2 团队《LUMIX S1R2 exFAT 内核越界写提权》阶段成果报告。
> 本文只回答一个问题：**它对我们（DC-S5）的固件/密钥路线有什么用、能不能用、怎么验证。**

---

## 1. 最大价值：把"物理线"变成"纯软件线"

我们项目此前对"改内容/取明文"的排序是：

| 优先级 | 路径 | 现状 |
|---|---|---|
| P1–P3 | 拆机取证 / 服务模式组合键 / U-Boot console | 需拆机或不可行 |
| **P4** | **JTAG dump RAM（运行时明文）** | **主线，但需拆机** |
| P5–P6 | UART bootlog / SD.DAT | 备选 |
| P8 | 芯片级 | 最后手段 |

S1R2 这条链给出的是：**用一张只改 4 字节的 SD 卡，让相机内核在自己的内存里执行一次位清除写**
——**不拆机、不接 UART/JTAG、不改固件**。若 S5 同款，则：

> **P4（拆机 JTAG dump RAM）可降级为备选，取而代之的是纯软件路径。**

这一点是全部价值所在。

## 2. 拿到 root 之后，对"固件解密"能做什么

| 我们现在卡在哪（实测结论） | 有 root 之后 |
|---|---|
| AES 密钥在 **MC801 芯片 OTP/eFuse**，不可离线提取 | 密钥虽然仍在 OTP，但**解密后的明文在 RAM 里** —— 直接从内存取 |
| `zimage` / `rootfs1/2` 全是密文（本项目 grep 实测：`exfat`/`Linux version`/`set_alloc_bitmap` **均为 0 处**） | `dd /dev/mtd*` 或读 `/dev/mem` → 拿到**解密后的内核与 rootfs**，可静态反汇编 |
| 固件升级**最终-chunk 定址失败**（我们卡住的地方） | 有 root 可**直接写 mtd**，绕开 UPD 分块/校验流程 |
| 不知道该机内核版本 / 有无同类缺陷 | `uname -a`、`/proc/version`、`/proc/kallsyms` 一目了然 |
| 不知道 OTP/安全世界如何校验 | 可**观察活体解密/校验流程**（甚至在内存里打补丁） |

**关键**：S1R2 报告测到 **无 KASLR、堆地址跨启动稳定**。若 S5 相同，则
`/proc/kallsyms`（若有）可直接读符号 —— 后续利用与打补丁都变得工程化。

## 3. 前提未验证：S5 是否同款漏洞

**离线无法判定**：

- S5 固件是 **UPD 容器 + 分块 AES**（每块独立 IV）；`zimage`/`rootfs` 密文，
  实测 grep 不到任何内核/exFAT 字符串（那 15 万条明文串来自 `ninsho_db`/`wifi_info`/
  `menu_save`/`music`/`osddata` 等**未加密数据分区**）。
- SoC 代际不同：**S1R2 = Socionext SC2006A（4×Cortex-A53，Linux 4.19.124）**；
  **S5 = MC801（32 位）**，内核版本未知。
- 但 Panasonic **同代复用 BSP**（S1/S1H/S5 同为 MC801），且 staging sdFAT 是
  **厂商整包搬入**的常见做法 → **同款可能性不低**。

⇒ **唯一可靠判定 = 实机试**。

## 4. 建议的验证路径（分两级，先低风险）

我们有相机 + SD 卡 + 相机自带的 exFAT 格式化流程，**复现条件齐备**。
但**越界写是内核内存破坏**，S5 的槽位分布完全未知 → **选错槽位 = 崩溃/变砖**。

### 第 1 级（几乎零风险）：验证"补丁卡是否被接受"

- 做 S1R2 方案那张卡：**只改 FAT 表 4 字节**，但链尾值**指向正常范围内的簇号**（不触发越界）。
- 目的：确认 S5 对"FAT 链尾改值"这类补丁的**接受度**。
- S1R2 已证明这种方式**卡 100% 自洽、相机不要求格式化、照片可显示可删除**；S5 大概率相同。
- 产出：如果 S5 也接受 → 说明攻击面存在（第 2 级才有意义）。

### 第 2 级（有风险）：触发真正的越界

- 链尾指向卡外（如 `FAT[50] = 1101826`）→ 删除照片 →
  相机若报 **"写入错误 请检查卡"**：
  - 因为 `clr_alloc_bitmap()` 是**先内存写、后卡写**，卡写失败才报错
  - ⇒ **内存位清除已经执行** ⇒ **S5 同款漏洞成立**
- 风险：这一刻有概率命中坏槽位（NULL → 崩溃）。
- 防护：用**牺牲卡**；做好"相机可能需要拔电池"的准备；优先选一个**已有先例的良性槽位**。

## 5. 与既有成果的衔接

- 本项目已证明 **CAMSET 校验和可伪造**（`(256−Σ) mod 256`），说明"容器/校验逆向"这套方法我们熟。
  S1R2 报告里的 **Boot Checksum（跳过 106/107/112）**、**Entry Set Checksum（跳过第 1 条 byte2/3）**
  属于**同一类工作**，方法直接复用。
- 思路同构：**都是"数据级伪造 + 让内核沿合法流程自己走到越界"**（不改代码）。
- 堆喷（`num_ext=63 → kmalloc-2048`，与 `vol_amap` 同 slab）说明这是**可控堆布局**，
  不是"撞运气"——比我们原先评估的物理线更工程化。

## 6. 必须说清的两点

1. **它本身不是"固件解密"**。它给的是**一个能读明文的立足点（root）**；
   AES 密钥仍在 OTP —— 只是我们**不再需要它**。
2. **风险不可逆**：第 2 级测试是内核内存破坏，可能变砖。建议**先做第 1 级**，
   并在一台可承受损失的机器上做第 2 级。

## 7. 结论

| 问题 | 回答 |
|---|---|
| 对固件解密有帮助吗？ | **有，而且是目前最有希望的一条** —— 它把"必须拆机 JTAG"变成"纯软件取明文" |
| 能直接用在 S5 上吗？ | **不能直接套**：SoC 代际不同、偏移全要重推；且**固件加密导致我们离线无法确认 S5 是否有同款缺陷** |
| 下一步该做什么？ | **第 1 级验证**（只改 4 字节、链尾指正常范围）→ 确认 S5 接受补丁卡 → 再评估是否做第 2 级 |
