## 0. 修订后的结论（2026-10-13 19:xx）

| 结论 | 状态 |
|---|---|
| ① 内核对簇号**不做归属校验**，释放路径**完全跟随卡上被篡改的 FAT 链值** | ✅ **成立**（位图实机证据，见 §3） |
| ② 内核对越界索引**存在 NULL 检查，会提前返回、不写内存** | ✅ **成立**（决定性实验，见 §0.5） |
| ③ "越界内存写已在 S5 执行" | ❌ **撤回** |

### 0.5 推翻 ③ 的决定性实验

**实验**：把注入值设为 `491522` → 内核索引 `i = (491522-2) >> 12 = 120`。
索引 120 落在 **120–127 这个 slab 填充区**（`map_sectors=120`，槽 0–119 合法），
填充区按 kmalloc 惯例为 0，即 **`vol_amap[120] == NULL` 几乎必然**。

| 观察 | 含义 |
|---|---|
| 相机报**「写入错误 请检查卡」**，**未崩溃** | ⇒ `vol_amap[120]` 未被解引用 ⇒ **存在 `if (vol_amap[i] == NULL) return -EIO;`** |

**这直接推翻了 §4 的推理。** 原文的论证是：

> "`clr_alloc_bitmap` 先内存写、后卡写；相机报卡写失败 ⇒ 内存写必然已执行。"

**该论证有漏洞**：代码里若存在 NULL 提前返回，那么"写入错误"同样会发生，
**且此时根本没有触碰内存**。两种情形在相机屏幕上**不可区分**。

因此原先 `FAT[112] → 524290`（索引 128）观察到的"写入错误"，
**既可能是"有效指针 + 卡写失败"，也可能是"NULL + 提前返回"**，无法据此认定内存写已执行。

> ⚠️ **顺带的一个方法论警告**：S1R2 报告同样把"相机报写入错误"当作
> "内存位清除已执行"的判据。若其代码同样含 NULL 检查，该判据在**任何机器上都不可靠**。
> 他们大概率另有验证手段（报告提到 GDB），但**判据本身不应被后人照抄**。

## 1. 原判定依据（已证伪，保留作记录）

`clr_alloc_bitmap()` 的执行顺序是**固定**的：

```c
/* drivers/staging/exfat/exfat_core.c */
s32 clr_alloc_bitmap(struct super_block *sb, u32 clu) {
    ...
    i = clu >> (p_bd->sector_size_bits + 3);          /* ← 越界索引 */
    exfat_bitmap_clear((u8 *)p_fs->vol_amap[i]->b_data, b);   /* ① 纯内存写，无返回值、不会失败 */
    return sector_write(sb, sector, p_fs->vol_amap[i], 0);    /* ② 卡写，会失败 */
}
```

相机报的是 **② 失败**（"写入错误"）⇒ **① 必然已经执行完毕**。

而且**相机没有死机** ⇒ `vol_amap[i]` 被成功解引用（非 NULL）⇒ 内存写确实落到了
`vol_amap[i]->b_data` 指向的地址上。

## 3. 现场与后果

- **相机**：报「写入错误 请检查卡」；未死机。
- **卡**：macOS 仍能列目录，但**读文件报 `Invalid argument`** —— 文件系统已被这次失败的写操作弄成不一致状态。
- **恢复**：在相机里**重新格式化**即可（数据均为测试用）。

## 4. 越界阈值（本卡）

```
索引公式: i = (clu - 2) >> 12     （clu = 卡上 FAT 中填入的簇号）
```

| 簇号 | 索引 | 后果 |
|---|---|---|
| ≤ 491521 | 0–119 | ✅ 合法 bitmap 缓冲（内存安全） |
| **491522 – 524289** | **120–127** | ❌ kmalloc-1024 slab 填充为 0 → **NULL 解引用 → 必崩** |
| **≥ 524290** | **≥128** | ❓ 相邻堆对象（**本次用的 524290 → 索引 128，命中有效指针**） |

> 与 S1R2 对照：其卡 `map_sectors=239`（kmalloc-2048），报告称槽位 239–255 全 0、
> 256+ 才有有效指针。**规律完全一致**。本卡 index 128 也是有效指针 —— 两侧的堆布局可类比。

## 8. 堆喷实验：**全部失败**，并发现一个新的崩溃点

> ⚠️ 本节原写于"越界写已确认"的错误前提之下。地基（§0.5）既已推翻，
> **堆喷的全部尝试（第 1 轮 240 长名 / 第 2 轮 120 长名 / 第 3 轮 120 短名+篡改 num_ext）
> 都无法证明其意义** —— 因为即便命中相邻槽，NULL 检查也可能让内存写根本不发生。
>
> **实际观察**：三轮尝试相机均只报「写入错误」，从未崩溃。
> 这与"槽位是 NULL、提前返回"完全一致。

### 8.1 做了什么

按 S1R2 报告的手法，用**文件名长度**控制 `get_entry_set_in_dir()` 的
`kmalloc(bufsize)` 档位，在 `DCIM/100_PANA` 里铺喷洒文件：

| 组 | 文件名长度 | bufsize | 目标 slab |
|---|---|---|---|
| 512 档 | 150 字符 | 392 | kmalloc-512（S5 若为 32 位） |
| 1024 档 | 240 字符 | 584 | kmalloc-1024（S5 若为 64 位） |

共 **240 个文件**（各 120 个），文件名以 `P########` 开头以伪装成相机照片。

**⚠️ 一个必须记录的推算更正**：`vol_amap = kmalloc_array(map_sectors, sizeof(struct buffer_head *))`
——**指针大小取决于机器位宽**：

| 机器 | 指针 | vol_amap（map_sectors=120） | slab |
|---|---|---|---|
| S1R2（64 位 A53） | 8 B | 239×8=1912 | kmalloc-2048 |
| S5（MC801，**32 位**） | **4 B** | **120×4=480** | **kmalloc-512** |

两种情况下"slab 内槽位数"都是 128，索引边界都是 120–127，**从越界行为无法区分**；
这正是喷洒必须**两个档位都铺**的原因。

### 8.2 结果（A/B 对照）

| 组 | 条件 | 相机行为 |
|---|---|---|
| B | 喷洒 240 文件 **+ 越界注入** | 开机即**反复重启** |
| **A** | 喷洒 240 文件 **+ 无注入**（已把 FAT[113] 还原为 0xFFFFFFFF） | **仍然反复重启** |

⇒ **A 组也崩 = 崩溃不能归因于越界注入。**
之前把 B 组的重启解读为"堆喷命中越界槽"是**过度解读，予以撤回**。

### 8.3 副作用发现（**独立于 exFAT 位图漏洞**）

> **在 `DCIM/100_PANA` 放入 240 个"长文件名 + 无效 JPEG 内容"的文件后，
> S5 会在开机扫描阶段反复重启。**

尚未隔离是**文件名长度**、**文件数量**还是**无效内容**导致。
若要继续，建议做隔离实验：

| 测试 | 变量 | 判据 |
|---|---|---|
| T1 | 仅 10 个长文件名文件 | 不崩 ⇒ 与数量/资源压力有关；崩 ⇒ 与文件名长度有关 |
| T2 | 240 个**短名**文件（无效内容） | 不崩 ⇒ 内容无关；崩 ⇒ 与数量有关 |
| T3 | 240 个长名**真 JPEG**（相机照片副本） | 崩 ⇒ 与内容无关 |

### 8.4 堆喷的下一步（若继续）

1. **先修掉污染的变量**：用 T1–T3 把"文件本身导致崩溃"这个干扰排除，
   才能重新让 A/B 对照有意义。
2. **换触发时机**：把喷洒放在**删除操作直前**（相机打开那张照片预览后再删），
   而不是开机扫描时。
3. **缩小喷洒规模**：240 太多，改成 8–32 个，减少对相机自身逻辑的干扰。
4. **内容改成真 JPEG**：确保相机确实对每个文件做路径查找（`get_exfat_entry_set`）。
