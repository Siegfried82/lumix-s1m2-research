有新材料和具体研究入口。最扎实的实物增量是服务模式导出的三个参数区；最接近机内原生处理入口的增量是 exFAT 消费者线索。没有得到现代 UPD 解码器、S1M2 的49个 flags=3 载荷验证明文、真实加载映射或真机完整 RAM。

不能从 README 的历史强断言判断当前进度：后续文稿已有重要撤回，旧密码脚本则仍保留先前已指出的问题。

随后新增的S1R2加密报告及S5配对包已另做[实物核验与纠正](../s5_pair_review_20261013/固件配对核验与纠正.md)。新增包重复了上述0x200切片错误，35个记录的所有V29首块均不正确；因此不能将新配对包计为有效解码或密码枚举成果。其正确零内容候选及条件明确的CBC机制仍可作对照材料。

## exFAT：具体源码候选，实机成功断言已撤回

作者最新[定因总结](https://github.com/williamwu1234/S5-reverse-engineering/blob/872b9bc83e1f2ba8e291c07fe28da6f1de8382cb/00_项目总结/04_定因与工具链成果_20261013.md)撤回“S5内核越界写实机确认”和“堆喷命中”。长名重启四组对照是改进，但没有原始调用栈、PC或内存读回来定位具体处理函数。

本次沿这条线索核对了[S1M2官方发布源码](https://ospo.panasonic.com/oss/dsc/DC-S1M2ES.html)：`linux-4.19.124.tar.gz`完整SHA为 `2067822653621ff9f3e1acdad99d7777812d0dc1036007921014da18fc9c6fce`。[exfat_core.c](exfat_review/source_evidence/exfat_core.c)的 `exfat_free_cluster`（344–398行）和 `clr_alloc_bitmap`（609–628行）构成明确的FAT链释放→位图索引消费路径；后者本函数没有索引上界检查。指针数组分配也不能支持“额外空间必为NULL”的假设。

这是可以继续离线核验的具体源码入口。尚未匹配S1M2实际运行内核、配置和挂载驱动，也未证明上游输入检查能否阻断异常值。S5运行版本不能用这份4.19发布源码替代。因而不能宣称S1M2已存在实机可利用写、代码执行或RAM读取链。

现有前后位图的采集时间、卡指纹和注入阶段不同，不能独立复算报告22的关键同卡差分；“未崩所以有NULL提前返回”仍超过观察。工具中还有旧成功提示，`mkentries`实际写入伪JPEG，与“纯目录项无数据”的描述不一致。详见[源码与实验核验](exfat_review/review.md)、[实际字节检查](exfat_review/evidence_check.json)。
