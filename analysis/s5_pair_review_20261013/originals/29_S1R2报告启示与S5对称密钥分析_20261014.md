**本文目的**：把该报告的方法论**直接应用到 S5（MC801）**，并给出新增的实测结果

## 0. 一句话结论

> S1R2 报告提供了**两个可直接复用的判据**，我把它们应用到 S5 固件后，
> **找到了比 S1R2 更多的判据数据（32 组跨版本对，约 28.9 MB）**，
> 并**发现了一条报告里没有的结构：零明文区段 ⇒ 纯 `E_K` 链**。

> AES 已知明文不破，2^128 依然是墙 ⇒ **最终结论仍与 S1R2 报告一致：只能走 RAM dump。**

## 2. ★ 把判据应用到 S5：找到了 **32 组跨版本同明文对**（约 28.9 MB）

### 2.1 版内对（V29 自身）

| 组 | 分区 A | 分区 B | 大小 | 明文 SHA-256 |
|---|---|---|---|---|
| 1 | `eep_ow_a` | `eep_ow_b` | 131,072 B | `6c4be51bd4c8fb00…` |
| 2 | `eep_act_a` | `eep_act_b` | 2,048 B | `59aa79d1fdaa9ed5…` |

⇒ 等于一份**完整的「已知明文 + 密文 + IV」对照**。

| `ipu_data` 密文块唯一性 | **16384 / 16384 全唯一** | 无短周期，**强加密结构** ✅ |

## 3. ★★★ 新发现：**零明文区段 ⇒ 纯 `E_K` 链**（S1R2 报告里没有）

### 3.1 实测数据

```
history 明文（type=2，固件里直接可读）:
   共 16,384 块，其中【16,353 块全为零】
   只有第 1 块 + 另外 31 个块非零
```

### 3.2 这在 CBC 下的含义

```
C1 = E_K(P1 XOR IV)          ← 第 1 块，P1 含一个 64 字节头
C2 = E_K(P2 XOR C1) = E_K(C1)     ← P2 = 0
C3 = E_K(P3 XOR C2) = E_K(C2)     ← P3 = 0
C4 = E_K(C3)
   …
```

**⇒ 从第 2 块起来就是一条纯 `E_K` 迭代链，与 IV 完全无关**：
```
C(n+1) = E_K(C(n))
```
**⇒ 一份【16,383 组】已知的 AES 输入/输出对** ✅

### 3.3 由此得到的**极快密钥验证器**

| 验证方式 | 每候选代价 |
|---|---|
| 明文 SHA-256 预言机（原方案） | 解密 131 KB + SHA-256 ⇒ **约 10^5 周期** |
| **零块链判据（新）** | **1 次 AES 块加密 ≈ 40 周期** |

**⇒ 快约 3 个数量级** ✅

粗算吞吐（AES-NI，8 核 @3GHz）：
```
≈ 6 × 10^8 候选/秒
  2^32 → 约 7 秒
  2^40 → 约 30 分钟
  2^48 → 约 5.4 天
  2^128 → 仍不可行
```

**⇒ 它把"验证"加速了，但没有把"搜索空间"变小。** ⚠️

## 4. ★★ 我们的独有资产：**ROM BACKUP 的 `eep_adj` / `eep_fix` 明文**

S1R2 团队**没有**这个。我们有：

| 文件 | 大小 | 熵 | 零字节 | **全零 16 字节块** | 固件同名分区 |
|---|---|---|---|---|---|
| `ADJUST.bin` | **131,072 B** | 1.6250 | 85.5% | **6,844 / 8,192（83.5%）** | `eep_adj` 131,072 B type=3 ✅**大小完全一致** |
| `FIX.bin` | **131,072 B** | 2.2980 | 75.6% | 4,591 / 8,192（56.0%） | `eep_fix` 131,072 B type=3 ✅**大小完全一致** |

`ADJUST.bin` 开头即机身序列号：
```
30303030303030303030303030…  = "0000000000000"   （与 CAMERA INFO 一致）
000107ffff                   = ADJUST 0x001C 处的已知字段
30303030303030303030303030…  = "0000000000000"
```

### 意义

1. **这把"已知明文"从"猜"变成了"确知"** —— 而且量巨大（各 131 KB）
2. **`eep_adj` 有 83.5% 的块全零 ⇒ 固件里对应位置也是零块链** ⇒ 可用 §3 的极速判据
3. **两份不同来源的明文（ROM BACKUP + 固件）可交叉验证**候选密钥是否正确

> ⚠️ **注意**：ROM BACKUP 拿到的是**本机的当前值**，固件里是**出厂镜像**。
> 开头（序列号等）必然不同，但**大段零区应一致** ⇒ 仍可作**部分已知明文**。

## 6. ⚠️ 一处**与 S1R2 报告的分歧**：`0x9606` 地址参数

S1R2 报告把 **"PTP `0x9606` 地址参数疑似不校验"** 列为**第 3 优先路线**（不需拆机）。

**但我们项目已经审计过并关闭了这条路线**：

| 我们项目的结论 | 依据 |
|---|---|
| `0x9606` 负载 = `[Size][Addr][DataType]`（32 位 12 B / 64 位 16 B） | 离线审计 Tether 2.12 arm64 ✅ |
| **地址来自相机 `0x9605` 的回复**，客户端协议上可覆盖，相机侧校验未知 | 已确认 |
| **要到达可测试状态，必须先发 `0x9406/0x00090013`（FWUP Request）** | 已定位 |
| `0x9406/0x00090013` **疑似先擦除目标区** ⇒ **高砖机风险，且无安全恢复**（SD.DAT 有砖机史） | 判定 |
| **且数据仍必须通过签名校验** ⇒ **拿不到执行自编代码的能力** | 判定 |

**⇒ 建议**：请 S1R2 团队说明他们**如何在不触发 `0x00090013` 的前提下**进入数据传送态。
如果确有办法，我们再重新评估；否则维持关闭判定。

> **⚠️ 项目红线不变**：**永不发送 `0x9406` 子码**（8 个子码全为带副作用动作）。

## 7. 结论与建议

### 7.1 本报告的新增成果

```
① S5 固件的同明文对数据：版内 3 组 + 跨版本 32 组（约 28.9 MB）
② ★ 零明文区段的 CBC 纯 E_K 链（16,383 组已知 AES 输入/输出对）
③ ★ ROM BACKUP 明文资产（eep_adj/eep_fix 各 131 KB，83.5%/56% 全零块）
④ 验证了 S5 加密【非 ECB】，与 S1R2 的 CBC 判定一致
⑤ 用两份独立分析交叉印证：首选路线 = RAM dump
```

### 7.2 但要诚实说明

> **这些成果加速了"验证"，没有缩小"搜索空间"。**
> AES 在已知明文下依然安全，2^128 是硬墙。
> **⇒ 密钥仍是真随机、固化在 MC8244/MC801 片内 ⇒ 纯离线数学破解不可行。**
> **这与 S1R2 报告的结论一致，不是新突破。**

### 7.3 建议的下一步（按可行性）

| 优先 | 路线 | 是否需拆机 | 说明 |
|---|---|---|---|
| **1** | **RAM dump**（服务模式 / PTP vendor 扩展 / Wi-Fi 诊断口） | ❌ | 引导后固件已由硬件解密进 DDR ⇒ **内存里是明文** |
| **2** | **JTAG / SWD** | ✅ | 直接 dump RAM，需找 SoC 调试测试点 |
| **3** | 向 S1R2 团队**索取 `0x9606` 免擦除进入法** | ❌ | 见 §6，有分歧需澄清 |
| 4 | 用 §3/§4 的极速判据重跑一遍**大规模撞库**（如 2^48） | ❌ | **期望值低**（但成本也低，AES-NI 几小时） |
| 5 | 继续扩大语义字典撞库 | ❌ | **不建议**（S1R2 已穷尽 282 万角度） |

### 7.4 可直接复用的判据数据（建议交给 S1R2 团队）

```
pairs_s5.bin —— 32 组跨版本同明文对 + 3 组版内对 + 1 组"明文/密文"对
每条记录: [IV_a:16][IV_b:16][C_a首块:16][C_b首块:16][size:4][name:12]
用途:     D_K(C1a) XOR D_K(C1b) == IVa XOR IVb  （每候选 2 次 AES 解密）
```
