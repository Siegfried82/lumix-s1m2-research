# 对象读取路线：缺口与下一次采集准备

2026-10-09。当前没有相机，仅做离线准备，Antigravity 停用。

## 已核验的缺口

在 analysis 下一级目录的 14 个 capture_log.json 中，没有 0x1007（GetObjectHandles）、0x1008（GetObjectInfo）、0x101b（GetPartialObject）或 0x9112（厂商部分对象读取）的操作记录。搜索范围不是整个文件系统，不能证明从未有人在其他工具里测试过。

已有 0x1005 对 0x10000/0x20000 的响应是 0x2008（InvalidStorageId）；它不能单独证明没有插卡、必须使用 SD、不能使用 CFexpress，或枚举没有对象。日志没有记录这些失败的确切机身原因。

第三方 ASCOM 驱动的 UsbCamera.cs:328-354 从事件取得对象句柄，再调用格式、大小、对象读取接口，并以图像头过滤结果。这是拍摄对象接收流程，未显示程序/内存对象。不能从只接受图像的上位机过滤逻辑推断相机永远只提供图像。

libgphoto2 的 camlibs/ptp2/ptp.c:2174 起构造 0x1007(storage,format,association)。其中针对 (0xffffffff,0,0) 的错误分支将错误替换成成功、零句柄；本次准备的工具保留原始响应，避免把失败解释成空数组。

## 准备的工具

- capture_object_inventory.m：独立副本，不改动原来的基线采集器。必须显式提供读取计划，允许的操作仅为 0x1004、0x1005、0x1007；校验参数数量及整数范围，没有对象数据、写入、格式化、拍摄、厂商诊断请求。任意非 0x2001 响应会保留日志并结束。
- stage1_plan.json：只查询存储标识与全存储对象句柄。只有拿到设备返回的句柄后，才有基础决定是否查看某个对象元数据；当前没有猜测句柄或地址。
- parse_handles.py：离线解析保存的句柄数组，响应错误与成功空数组分开表示，校验计数和载荷长度。
- offline_validation.json：14 个日志的限定范围检查结果、解析器检查与工具源码哈希。

工具通过 macOS 完整编译和链接。已运行的只有 `--validate-plan` 离线分支，且该分支在创建设备浏览器之前直接退出；未运行设备采集分支，没有连接设备，没有得到对象响应。离线解析检查验证了设备错误保留、成功空数组、两个句柄以及四种畸形载荷的拒绝。

额外验证了 11 种非法计划会在浏览设备之前被拒绝，包括写入操作码、超过 16 位的操作码、非整数操作码/参数、参数数量错误、负数、超过 32 位的参数、文件名路径穿越及无效结构。两个合法计划的完整请求包已与预期字节一致，记录在 offline_validation.json。此检查只证明构造和前置校验，不能证明相机一定支持请求。

编译得到的 capture_object_inventory 可在相机回来后直接使用。本次未执行采集启动命令。验证方式为：

```text
capture_object_inventory --validate-plan stage1_plan.json
```

## 相机回来后

首轮只需要当前 CFexpress 卡；本阶段不要求 SD 卡。相机连接状态与模式仍需实机确认，不能承诺现有模式一定支持枚举。由 Codex 在确认设备可用后执行准备的两条元数据读取，保留原始响应码。若错误则先定位模式/介质可见性，不枚举未知厂商操作码。

若成功取得句柄，下一步查对象元数据并判断对象类型；若只有照片/视频对象，这条路线仍没有程序读取证据。即使成功读取一个对象，也必须识别其内容才能判断是否涉及固件，不能把普通文件传输称为 RAM dump。

## 对目标的影响

此处只准备了此前缺失的对象枚举实验，尚未完成程序逆向或新增机内功能。它有参考价值的前提是实机暴露与程序相关的对象；目前没有这样的证据。无需用户现在接机，也不自动运行工具。
