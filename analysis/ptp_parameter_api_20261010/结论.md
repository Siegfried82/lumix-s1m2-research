# 0x9414 / 0x9415 / 0x9416 寻址核验

本轮静态检查Tether 2.12 arm64，不连接相机。functions.json保存25个含这些立即数的完整函数、原始行号与反汇编SHA-256；这里只覆盖直接立即数引用。

## 已确认的寻址

- 0x9414是多类信息共用操作码，通常一个32位PTP参数作为标签，不限于0x08命名空间。
- USB速度：LMX_func_api_GetUSBSpeed，24711行起；0x1a488/0x1a48c合成0x18000010，0x1a4b4放入唯一参数。
- 白平衡AB微调：LMX_func_api_WB_Get_ADJ_AB_Sep，49375行起；0x31e40/0x31e44合成0x02000055，0x31e48放入唯一参数。
- 0x9415的SetLvTransImg（60088行起）使用调用者的第三参数w2作为标签，第二参数w1为数据长度，第一参数x0为数据指针。不能据此认为它能写全部菜单。
- 0x9416的多种控制封装调用Rec_Ctrl_with_data（67333行起）。该函数读取输入结构第一个u32作为标签，作为唯一PTP命令参数；发送数据含[tag u32, length u32, serialized payload]。长度与序列化函数来自虚拟地址0x230198的表：58项，每项16字节[tag u32, length u32, serializer pointer u64]。搜索标签的指令范围0x43258–0x43270；构造头0x43340–0x4337c；调用serializer 0x433ac。

control_table.json直接从散列核实的libLmxptpif.dylib的arm64切片提取。原始指针还需逐函数及dyld重定位核验，不能仅从表的标签名称推导设备支持或行为。

## 结论和下一步

此前仅扫描0x08设置标签并不能覆盖0x9414的信息标签；已有具体调用可替代盲猜。但这些是主机静态事实，尚未在S1M2/S1RM2验证新增请求。下一步追58项序列化函数和调用者，完成字段大小、字节序与语义映射；不执行控制指令。参数族并不等于所有菜单可读写，更不是主固件明文入口。

## 序列化函数已还原

58个原始函数指针全部能对应反汇编中三个明确函数入口，当前映射无须猜测：0x44204为PACK_UINT16_PARAMS、0x44230为NOP、0x44234为PACK_UINT32_PARAMS。证据在serializers_evidence.txt，完整类型表在control_table_typed.json。

两个PACK函数都从主机输入结构+4读取u16元素数量，从+8起读取每项u32。UINT16版本将每项低16位以连续2字节写入输出；UINT32版本按4字节写入。arm64为小端，实际网络数据为小端。NOP不写payload。目录length是有效payload字节数，不是元素数量；控制数据外层另含8字节[tag,length]。

各表项长度可被对应元素宽度整除，因此可以算出与表长一致的预期元素数量。但原客户端serializer按调用者count执行，不能把表长当作充分输入验证；我们不会复制这种未检查count的实现。表只定义封包方式，没有验证相机侧支持或每个数值的语义。Menu/Backup等wrapper仅传递REC_CTRL指针，不能仅凭函数名给任意标签定性。

下一步需要从主机实际构造REC_CTRL的调用者追tag与count来源，才能生成具体、经过验证的请求。这个结果是参数封包还原，不是新增设备执行入口或固件解密。
