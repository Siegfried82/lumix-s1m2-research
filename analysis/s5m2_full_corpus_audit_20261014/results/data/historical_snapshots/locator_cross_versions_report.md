# Panasonic S5M2 更新檔跨版本核驗報告

日期：2026-10-11  
樣本：S5M2 V3.2、V3.3、V3.7

## 結論

這條研究路線沒有被「證明鎖死」，但目前能確定的是：

1. 更新檔具有可重現解析的 `UPD` 外層、CRC32、分區表、每分區摘要與 12-byte 欄位。
2. V3.2 → V3.3 的分區布局完全相同，只有 **9 個分區摘要改變**；同時 **42 個非零 12-byte 欄位全部改變**。
3. 其中 **27 個分區的摘要未變、12-byte 欄位改變、儲存內容也改變**。這是「邏輯內容不變，但包裝／加密輸出被重新生成」的強證據。
4. `+0x2C` 的 32-byte 欄位在可驗證的常量分區中符合邏輯內容的 SHA-256，因此可當作日後解密結果的可靠驗證標尺。
5. `0x220` 的 64 bytes **只能稱為簽章候選欄位**。目前沒有公鑰、沒有成功驗章，也沒有確定簽署範圍，不能把它正式定性為 ECDSA P-256。
6. 現有證據同樣不足以把分區演算法定性成 AES-CTR、AES-GCM、每分區獨立金鑰或硬體唯一金鑰。

目前最有價值的方向不是繼續猜密碼演算法，而是取得實際更新驗證器、驗證公鑰或相機端的更新執行軌跡。

## V3.2 → V3.3：真正改了什麼

分區布局、檔案大小與分區數完全相同。

摘要改變的 9 個分區：

- `program#0`
- `postboot1_r#0`、`postboot1_r#1`
- `postboot3_r#0`、`postboot3_r#1`
- `postboot5_r#0`、`postboot5_r#1`
- `eep_fix#0`
- `osdover#0`

54 個實際位於檔內的分區分類如下：

| 摘要 | 12-byte 欄位 | 儲存內容 | 數量 | 解讀 |
|---|---|---|---:|---|
| 未變 | 未變 | 未變 | 10 | 完全沿用 |
| 未變 | 未變 | 改變 | 3 | 另有未解析的定位／稀疏資料機制 |
| 未變 | 改變 | 未變 | 5 | 內容可能為全零或空配置，表欄位刷新但 payload 不受影響 |
| 未變 | 改變 | 改變 | 27 | 邏輯內容不變，但儲存表示重新生成 |
| 改變 | 改變 | 改變 | 9 | 實際邏輯內容更新 |

「摘要未變、12-byte 欄位與 blob 都變」的 27 個案例，比單一版本的熵分析更有判別力：它支持 probabilistic wrapping／加密，但不單獨辨識演算法、金鑰範圍或 AAD。

三個「摘要、12-byte 欄位不變，但 blob 改變」的分區是：

- `lens_hist#0`
- `vkizu_data#0`
- `lut2_data#0`

這三項都屬於摘要可驗證為全零邏輯內容的特殊／稀疏資料分區。因此 `+0x4C` 不是解釋所有儲存差異的唯一參數，或分區內還有隱藏的 generation/tweak/placement 規則。

## V3.7 的結構變更

用「名稱＋同名出現次序」配對，而不是用表索引配對後，V3.7 相較 V3.3：

- 保留 56 個共同分區。
- 新增 `compress_pr#0` 與 `grid_data#0`。
- 分區布局不再相同。
- 有 15 個共同分區的摘要改變。
- 42 個共同的非零 12-byte 欄位改變。

因此先前若用 `(index, name)` 比對，遇到插入分區後會錯配並低估變動；本次工具已修正。

## 已確認的格式事實

- `0x000`：`UPD\0`
- `0x00C`：機型字串，本樣本為 `MC8223`
- `0x03C`：`file_size - 0x200`
- `0x040`：CRC32，範圍為 `[0x200, EOF)`
- `0x220..0x25F`：64-byte 版本相關候選欄位
- `0x2DC`：分區表起點
- 分區表項大小：`0x5C` bytes
- 表項 `+0x2C`：32-byte 摘要，常量案例支持 SHA-256(logical plaintext)
- 表項 `+0x4C`：12-byte 版本相關欄位；很像 nonce/IV，但演算法尚未證明

## 對參考專案結論的修正

參考專案：<https://github.com/ShaoCI-Hz/lumix-fullframe-reverse>

### 1. `0x2A0` 不是完整的 512-byte 備份頭

三個版本都只有前 **64 bytes** 與主頭相同。`0x2DC` 已開始分區表，所以「完整 512-byte duplicate header」不成立。

### 2. `0x220` 尚未完成 ECDSA 驗證

參考腳本只把 64 bytes 切成 `r || s`，檢查兩個 256-bit 整數是否小於 P-256 的階 `N`。由於 P-256 的 `N` 非常接近 `2^256`，隨機 32-byte 數通過此範圍檢查的機率也幾乎是 100%；這個測試不能辨識 ECDSA。

要把它定性為 ECDSA，至少需要：

- 找到可信公鑰；
- 確認 byte order 與 raw/DER 編碼；
- 找到確切 signed range 或 message construction；
- 對至少一個官方映像成功驗章。

另外，三個 S5M2 候選值都是 high-S。這不排除 ECDSA，但也沒有提供「標準化簽章」的額外支持。

### 3. AES-CTR／GCM 尚未被識別

高熵、區塊不重複及 12-byte 欄位可支持「強加密或偽隨機轉換」的假說，但不能區分 CTR、GCM 或廠商自訂封裝，也不能證明每分區獨立 key。

### 4. MTP `0x9102` 尚未證明能讀資料或解密

參考紀錄中，`0x9102` 建立了 read context，但 `TRANSFER_TOTAL_DATA_SIZE = 0`。`0x9103`、`0x9104` 尚未完成測試；因此目前只證明 vendor opcode 可被枚舉與呼叫，尚未證明存在記憶體讀取、韌體明文輸出或可用寫入能力。

## 接下來的實際研究順序

1. **找驗證器與公鑰**：優先搜索 LUMIX Lab APK、桌面更新工具、相機可取得的 boot/update 元件；用 `0x220` 候選欄位與已知官方檔做真實驗章。
2. **安全的 USB/PTP 探測**：在相機可實體復位時，逐一測 `0x9103`、`0x9104` 的無資料／讀資料型態，完整記錄 response code、參數需求與 data size；不要先假設是記憶體讀寫。
3. **更新流程觀測**：記錄相機讀 SD 更新檔時的檔案存取與錯誤差異，使用單點、可回復的測試檔判斷 CRC、機型、版本、分區摘要及候選簽章的檢查順序。
4. **若取得明文或驗證器**：立即用表項 SHA-256 作判定，避免再依賴熵或 magic 猜測。

## 重現方式

工具只讀取映像，不修改韌體：

```powershell
python .\outputs\s5m2_upd_audit.py `
  .\work\firmware\V32\S5m2_V32.bin `
  .\work\firmware\V33\S5m2_V33.bin `
  .\work\firmware\V37\S5m2_V37.bin `
  --output .\outputs\s5m2_cross_version_audit.json
```

輸出 JSON 保存每個分區的 identity、位置、大小、flags、摘要、12-byte 欄位、檔內狀態、blob SHA-256，以及逐版本差異分類。
