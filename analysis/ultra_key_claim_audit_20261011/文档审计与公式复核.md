## 本轮结论

当前主进度、恢复文档及多份 Codex 核验已明确撤回 OTP/eFuse、签名算法、静态不可行等高确定性说法。残留的同类说法主要在第三方 S5 原始交付包和历史 AGY 报告，不能当项目当前结论。本项目整理的阶段汇总还留有一处“GH2 key 不是 S1M2 key”的过强否定，建议修正文句。

五款旧 AES 机型解码明文各含自身已验证 key；GH2 V1.2 也含 V1.1 key。独立按 PTool 表读取源文件的 16 个取钥字节，并在明文所记偏移读 16 字节逐一比较，六处全部一致，记录见 `small_control_results.json`。这不证明 S5/S1M2 密钥同样存在于包内，但直接阻止把“Panasonic 密钥从来不在固件明文”用作一般前提。

GH2 文件偏移 `0x7f52f8` 的 key 按启动 ROM 段 `file[0x600] → 0x40000000` 映射为 `0x407f4cf8`。`GH2_boot.disassembly.txt:189–203` 显示复制 `[0x407f4cd0,0x407f6384)` 至 `0x74000000`，key 因而落在 RAM `0x74000028`。`GH2_key_consumer.disassembly.txt:1087–1092` 取该 RAM 地址，长度为 16，调用文件地址 `0x9d608a`；映射后的 `GH2_updater_mapped.disassembly.txt:80–84` 为 `0x7bcd5a8a` 函数把输入复制至状态对象 `+40`。这些是旧 GH2 的具体静态消费者证据，不能移植为 S1M2 地址图或解码成功。

## `check_feedback_modes.py` 公式与控制复核

设均匀候选明文字节为 `v`，恢复的候选流 `S=C XOR v`。

- **CFB128**（`:19–20`）：第二块起 `S_i = E_K(C_{i-1})`。ECB 一次加密所有前序完整块再与 `S[16:]` 比较，正确且去除初始 IV 依赖。
- **CFB8**（`:21–24`）：第 16 字节起，128 位移位寄存器全部来自前 16 字节密文；当前流字节为 `MSB_8(E_K(C[i-16:i]))`。批量寄存器的每块首字节下标 `(i-16)*16` 正确。不是 CFB1、CFB32 或其他 segment size 的穷尽。
- **OFB**（`:25–26`）：完整相邻候选流块满足 `S_{i+1}=E_K(S_i)`，正确且不依赖 IV。这里要求流块边界与组件原点一致。

脚本自身六组控制（0/FF × 三模式）和第 64 字节损坏拒绝能验证实现不是恒 true/false。额外只调用 `check()` 的十八组控制（32/48/128B × 0/FF × 三模式）均成功，并分别拒绝一个损坏密文字节、错误均匀值和错误 key。记录及脚本哈希见 `small_control_results.json`；复現入口：`PYTHONDONTWRITEBYTECODE=1 analysis/s5_delivery_review_20261010/.venv/bin/python analysis/ultra_key_claim_audit_20261011/audit_small_controls.py`。

这些必要关系若不满足，足以拒绝当前 key 与均匀明文假设下的标准模式，不需要知道 IV。控制通过不能证明实际组件的明文均匀、目录摘要作用对象或真实模式；尤其 CFB8 仅检查起始 16 字节之后的关系，命中也不能替代完整解码校验。

`evidence.json` 实际列出七项（S1M2 两版各两项、GH5 两项、S5 一项），尺寸均至少 65536B，脚本采样各项原点前 128B，不跨现有组件边界。五把旧 key 会形成 35 对，不是“全部新格式组件”。GH3/GH4 的空 entries 不构成其 CFB/OFB 失败证据。保持 `:82–85` 的假设边界：固定旧原始 AES key、直接标准 CFB128/CFB8/OFB、无 KDF/额外变换、组件原点对齐且目录摘要确实指向均匀明文。未来复用脚本可加 `entry['size']>=128` 与范围断言，当前数据未见越界问题。
