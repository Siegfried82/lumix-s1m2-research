# 04 · 固件升级写路径（核心：改内容原语 + 最终-chunk 失败深潜）

> 这是**软件侧唯一真正"能改内容"的通道**：一旦 `endsenddata` 成功 = 相机用我们流送的 90MB 映像重写整个 flash = rootfs（守护进程、socket、配置路径）一次性到手，完全不用拆机/焊接。本章记录协议、判别探针，以及当前卡住的**最终-chunk flash 定址失败**深潜。

## 4.1 协议序列（反编译自 `com.panasonic.jp.lumixsync`）

```
GET  /cam.cgi?mode=camctrl&type=fw_update_mode&value=VX.XX      # 打开"版本门"
GET  /cam.cgi?mode=startsenddata&type=fw&value=<file-size>      # 回 method + bufsize
POST /cam.cgi?mode=senddata   (multipart, 每块 iA 字节)          # 循环
GET  /cam.cgi?mode=requestsenddata                                # 非最终块后间插
GET  /cam.cgi?mode=endsenddata                                    # 末块后 → 触发验签+刷写
GET  /cam.cgi?mode=abortsenddata                                  # 取消
```
- 通用头：`User-Agent: LUMIX Sync`；可选 `X-SESSION_ID`。
- multipart 边界：`"=====" + UUID + "====="`（46 字符，进程内静态）。
- 传输层 10000ms 超时；`endsenddata` / `requestsenddata` 用无超时 binary GET。
- `upload.py` 的协议与官方 App 完全一致（46 字符边界、每个非最终块后 `requestsenddata`）。

## 4.2 `method=once` vs `separate`（本轮关键判别）

`startsenddata` 回 `<method>`：
- **`once`**：总长 **≤ bufsize(61460)** → 单发 POST 整文件，**无 `endsenddata`**。
- **`separate`**：总长 **> 61460** → 分块 + `endsenddata`；每块 payload `iA = bufsize - V()`，实测 data/chunk = **61192**。

**分块数学**：`1474 × 61192 + 1 × 41456 = 90,238,464`（真 90MB 映像 = 1474 个完整块 + 1 个 41456B 尾块）。

## 4.3 ★ 最终-chunk 失败深潜

### 现象
真 90MB 映像能**干净流送全部 1474 个完整 61192B 数据块**（~81–108ms/块），但**最终部分块（41456B）始终失败**：
- 首个尝试 → **`err_busy`**（触发 **~31s 的 flash 定址操作**）
- 重试 → **`err_critical`**（快，~0.6–31s）
- **从未触达成功的 `endsenddata`**。

### 三次独立实验（原始日志见 `logs/写路径/`）

| 实验 | 节奏 | 结果 | 日志 |
|---|---|---|---|
| **CONTROL**（未改真 V29，fast keep-alive） | 81ms/块 | 1474 块 ok（536s）→ final 12 次重试全 `err_critical`（第 4 次起 ~30.8s/次）→ `abortsenddata=error`；**未改数据也在末块失败** → 判"传输问题，与内容无关" | `control_run1.log` / `campaign.md` |
| **TESTA-1**（final ONCE → 45s 静置 → endsenddata） | ~54–130ms/块 | 1474 块 128.4s → final 一次性 `err_busy`(0.05s) → 静置 45s → `endsenddata → error`(30.09s) | `phaseI_run12_fast.log` / `campaign.md` |
| **TESTA-2**（final 1/4 次 → err_busy 30.12s → 重试全 err_critical） | pace 150ms（比官方 App 138ms 还慢） | 1474 块 232.7s → final 4 次全失败 → `abortsenddata=error` | `campaign.md` |

### 判别结论
1. **与内容无关**：CONTROL 发的是**未改动的真 V29 镜像**（字节一致），仍失败 → 排除"我们改坏了镜像"。
2. **与节奏无关**：fast(81ms)、pace(150ms，比官方 138ms 更慢) 都失败 → 排除"送太快 flash 没跟上"。
3. **与状态无关**：拔电池全新重启后依然复现 → 排除"残留状态"。

### 关键小样本探针（判别"能否用小样本逼近真实定址"）

| 探针 | total | 模式 | 末块结果 |
|---|---|---|---|
| `probe_final_chunk` | 61192 (1 块) | **once** | `err_reject`(0.12–0.46s) —— 小映像"非法/太小"，**没走到定址** |
| `probe_partial_final` | 102648 (1 整 + 1 部分尾) | **separate** | 整块 ok → 部分尾 41456 `err_reject`(0.10s 快拒) —— 小映像仍在"合法性"关被拒 |

⇒ **只有真 90MB 映像能走到真正的 flash 定址阶段**；小 / 假映像在"固件合法性"这关就被拒，无法用小样本逼近真实定址行为。

### 当前最可能解释
真实 90MB 的 ~31s 定址失败，**内容 / 节奏 / 状态无关** → 最可能是**内部 flash 对大映像末块的擦/写超时或磨损**（本会话已对同一块 flash 做了大量 90MB 流送测试，可能已触发磨损 / 写放大）。**尚未看到过一次成功的 `endsenddata`**，因此**签名 / 版本 oracle 仍是开放问题**——我们还没能拿到"相机对已签名 vs 未签名 / 已改版本固件的真实验签反应"。

## 4.4 为什么这条线价值最高（且最接近"改内容"）

- 它**不改单个文件**，而是**整幅重写 rootfs** —— 能改代码（守护进程 / 二进制）+ 数据（配置 / socket 路径），是"改内容"的天花板。
- 它**完全软件 / Wi-Fi**，不用拆机。
- **卡点单一**：就差"打通一次成功 `endsenddata`"。若末块定址失败是**可恢复的 flash 状态问题**（而非硬损伤），换一块干净 SD / 换机、或在**全新 flash 状态**下一次性流送（不反复重试末块、不静置、让相机自己 drain），有机会拿到第一次真实验签反应——那将直接回答"改版本 / 改内容能否过签名"。

## 4.5 未用过的、低风险的末块处理变体（待 §10 决策后执行）

1. **不重试、不静置**：末块 `err_busy` 后**立即**直接发 `endsenddata`（相机可能已在后台擦写，只是忙）。
2. **末块静置更久**（60–120s 再 `endsenddata`），排除擦写未 drain。
3. **全新 flash 状态**：拔电池彻底重置后，一次性 fast 流送、末块单次、立即 `endsenddata`（避免反复重试把末块写坏）。
4. **换 SD 卡 / 换机**：排除"这块 flash 已被反复 90MB 流送写坏"的可能。

> 安全提示：上述都属于"可能再触发 ~31s 定址 / 卡死"的操作，需 AC 常供电 + 健康守卫，且**绝不真刷**（V29 为 RECOVERY-ONLY）。详见 §11。
