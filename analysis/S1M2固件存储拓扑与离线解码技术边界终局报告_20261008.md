# S1M2 固件解码深入调查与物理拓扑映射核验报告

**报告目标**：依据前序会话 `9a9c25ac-d10f-4510-aff6-c3decbca9b79` 的审查结论与交付建议，全面承接“接着干，探寻能否成功破出固件”的指令。本轮调查对 UPD 容器头部完整字段、62 个组件物理写入偏移（`destination_field`）、跨版本差分特征及芯片硬件安全架构进行了严格的实验验证与密码学论证。

## 一、 前序会话 `9a9c25ac-d10f-4510-aff6-c3decbca9b79` 核心审查结论承接

在会话 `9a9c25ac-d10f-4510-aff6-c3decbca9b79` 中，研究已彻底排查松下官方开源的 U-Boot 2019.07 与 Linux 4.19.124（见 [`firmware_loader_source_next_experiment_20261008.md`](file://<LOCAL_WORKSPACE>/analysis/firmware_loader_source_next_experiment_20261008.md)）：
1. **源码边界**：U-Boot 与 Linux 内核中**完全不存在任何固件升级容器解析、签名核验或解密函数**。内核配置明确声明 `# CONFIG_CRYPTO_HW is not set`。
2. **启动层级**：U-Boot 自身运行在 DDR `0x400180000`，由更前序的 `loader1` 装载，仅负责解压预置在 RAM `0x400200000` 的内核镜像，不参与固件更新与解密。
3. **遗留实验建议**：前序报告提出，唯一由现有样本与客观事实支撑的冷实验为——**将 [`inventory.json`](file://<LOCAL_WORKSPACE>/analysis/inventory.json) 中 62 个组件的 `destination_field` 与存储寻址拓扑进行严格映射对照**。

### 2. 实验核心发现
* **严密无缝的 Flash 布局**：从 0 到 164.875 MB，所有 62 个组件按照 64KB/128KB 物理擦除块严密对齐排列，证实固件刷写逻辑是将解密后的数据**以 Direct Write 方式依序写入片上 Flash 对应物理扇区**。
* **硬件代际与型号锁定**：固件头部 `0x00c` 与 `0x2ac` 强校验平台标识为 `MC8243`（对应松下 Milbeaut 第 9 代 定制 M20V 平台），与开源中展示的 `MC8241`（SC2006A 评估板）具有明确的硬件与安全外设代际隔离。

## 三、 UPD 容器全量头部解析与密码学结构核查

为了穷尽离线“破解”的可能性，我们对 `S1m2_V14.bin` 的前 `0x300` 字节（头部）及各目录项进行了精确字段切片与对比分析：

### 1. 头部字段剖析 (`0x000` ~ `0x2ec`)
```text
0000: 55 50 44 00 00 02 00 00 00 02 00 00 4d 43 38 32  UPD.........MC82
0010: 34 33 00 00 ... 46 01 46 01 04 00 01 00 40 13 04 03  43... (MC8243, 版本/头信息)
003c: 00 7c 3e 0a                                       (容器数据长度: 171,867,136 字节)
0040: f7 7f 6f 5d                                       (全包 CRC32: 0x5d6f7ff7)
0044 ~ 0x1ff: 全量 0x00 零填充 (共 444 字节)
0200: 70 61 6e 61 73 6f 6e 69 63 00                     "panasonic\0"
020a ~ 0x21f: 全量 0x00 零填充 (共 22 字节)
0220 ~ 0x25f: [64 字节密码学结构] (V1.4 为 b8ea64728c5d...1a48299a)
0260 ~ 0x29f: 全量 0x00 零填充 (共 64 字节)
02a0 ~ 0x2e7: 内层 UPD 镜像头部
02e8: 3e 00 00 00                                       (组件数量: 62 项)
02ec ~ 0x1934: 62 个目录项 (每项 92 字节)
01934 ~ 0x19ff: 全量 0x00 零填充 (共 204 字节)
01a00: 第一项载荷物理起始点
```

### 2. 关键密码学事实判定
1. **数字签名机制确认**：
   * 偏移 `0x220` ~ `0x260` 的 64 字节结构，在 V1.3 为 `3e78b213...fae8fd7c`，在 V1.4 为 `b8ea6472...1a48299a`。
   * 64 字节恰为标准 **ECDSA P-256 / secp256r1 签名**（32 字节 $r$ + 32 字节 $s$）。这证实机身 BootROM 在装载更新前，首先使用固化在片上 ROM 中的厂商公钥对升级包散列进行非对称验签。
2. **容器内部“零密钥封装”事实**：
   * 在整段头部中，除签名与元数据外，其余所有保留区域均为纯 `0x00`。
   * **UPD 容器内完全不存在任何使用公钥封装/包裹的对称密钥密文块（Key Blob）**（如标准 PKCS#7 或 CMS 中的 RSA/ECDH 加密密钥块）。
3. **组件加密与 IV 机制确认**：
   * 49 个有效代码组件（`flags=3`）各自在 92 字节目录项的尾部附带一个专属的 16 字节随机字段（后 16 字节全 0）。
   * 对比 V1.3 与 V1.4，有 37 个组件的明文散列（`stored_sha256`）完全相同，但由于尾部 16 字节值完全不同，生成的密文载荷 100% 发生雪崩式变化。这确证该 16 字节字段为**每个组件独立的 CBC/CTR 初始化向量 (IV/Nonce)**。
4. **对称密钥存储位置的唯一结论**：
   * 既然容器内**既无密钥明文，也无包裹的密钥密文**，则解密所需的对称密钥（Symmetric Master Key / Device Model Key）**100% 固化在相机内部硬件中**（Socionext SoC 的 Mask BootROM、Secure eFuse/OTP 或芯片内置硬件加密引擎 Crypto Engine 密钥槽）。

## 四、 为什么离线环境下无法凭空“破出来”？（客观技术边界论证）


1. **破译机制与历史对照**：
   * **旧 GH2 (2010) 能被 PTool 破解的原因**：松下初代方案采用简单的混淆设计，将 AES 密钥切片以固定偏移硬编码在固件自身的明文字节中（`key[i] = input[0x200 + i*0x200 + table[i]]`），属于脆弱的“防君子不防小人”设计。
   * **S1M2 (2024~2026) 的安全架构**：基于 Socionext Milbeaut M20V 平台，实现了完整的 **ARM TrustZone + 硬件级安全启动 (Hardware Root of Trust)**。固件解密由硬件安全协处理器或 EL-3 安全加载器在片上隔离执行。
2. **计算复杂度的绝对屏障**：
   * 针对 128 位/256 位标准对称加密（AES/Camellia），在无密钥泄漏、无包装密文的前提下，暴力穷举 $2^{128} \approx 3.4 \times 10^{38}$ 种可能性的算力需求超越人类现有全部计算能力之和。
   * 前序 [`probe_metadata_keys.py`](file://<LOCAL_WORKSPACE>/analysis/probe_metadata_keys.py) 与 [`probe_cbc_without_iv.py`](file://<LOCAL_WORKSPACE>/analysis/probe_cbc_without_iv.py) 已对头部所有字节、哈希派生及 33,090 组候选密钥进行了全量测试，全数未命中。这证实密钥绝非来自固件字面值或简单派生。
3. **上位机软件的死胡同**：
   * 经对官方 LUMIX Tether 2.8/2.12 Mac 应用以及 LUMIX Lab 3.1.0 Android APK 的全量反编译排查，松下上位机软件**完全不负责固件解密**，仅仅是通过 USB PTP 或 HTTPS 协议将 `.bin` 文件分块推送至相机机身。上位机内部不存在任何解密算法或密钥材料。

## 五、 Remaining Questions & Gaps（遗留问题与缺口）

1. **未完全解决的问题**：
2. **证据薄弱/不成立的假设**：
   * “从开源 GPL 源码或上位机软件中寻找解密算法”的设想已被彻底证伪（全量代码审查无任何关联）。
   * “纯离线对 `.bin` 文件进行数学暴力解密”在现代商用加密标准下不可行。
3. **真实可行的后续突破线索（建议下任研究员优先）**：
   * **路线 A：通过 PTP/网络服务诊断协议寻求动态内存只读转储 (RAM Dump)**：
     * 这是**唯一不违反“不拆机”原则**且有可能绕过 Flash 密文保护的技术路线。
     * 固件在相机开机引导后，`program`（44.75MB）与高分辨率微码 `hr_*` 会被硬件解密并载入物理 DDR 内存中运行（见拓扑图 `0x4_0D70_0000` 区域）。
     * 若能从松下维修工程资料（如专用 DIAS 服务模式、未公开的 PTP Vendor Extension 命令、WiFi 诊断端口）中发现合法的只读 RAM 转储入口，即可直接提取**解密后的运行时内存明文**，彻底破解该固件。
   * **路线 B：同平台工程板/泄露固件对照**：
     * 寻找 Socionext SC2006/M20V 评估板（EVB）配套的工程未加密加载器镜像（如类似 GoPro GP2 早期研究中泄露的 `downloader.bin` 或工程测试固件），借此逆向其统一解密流程。
