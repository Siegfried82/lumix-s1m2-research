# 二、🔴 已发现的漏洞 / 安全问题

## A 类：设计缺陷（已确认，不需要实测）

| 编号 | 漏洞 | 严重度 | 证据 | 影响 |
|---|---|---|---|---|
| **A1** | **鉴权形同虚设**：`{"AppInfo","FriendlyName","Uuid"}` → 返回 `AuthToken`。无密码、无挑战应答、无签名、无时间戳 | **高** | 实机请求体 | 只要连上相机 WiFi，任意 UUID 都能拿到有效 token → 全权控制相机 |
| **A2** | **硬编码 Basic Auth 凭据** `sub-avcweb:1qaz` | **中** | APK 代码（`Lh6/h->j()`，base64 `c3ViLWF2Y3dlYg==` / `MXFheg==`） | 默认凭据；`avcweb` = 松下相机 web 服务器 |
| **A3** | **TLS 自签证书 + App 侧无证书固定**（自定义 TrustManager 放行一切） | **中** | APK（`Lh6/f`、`Lh6/g`） | 可 MITM，全 API 明文 |
| **A4** | **敏感操作无二次确认**：`{"Command":"wifioff"}` 可远程关 WiFi | **中** | 内存 + APK | 拒绝服务 |
| **A5** | **PTP/API 暴露破坏性操作**：`SelfTest` / `ResetDevice` / `FormatStore` / `PowerDown` | **中** | 协议表 | 潜在数据毁坏 |

## B 类：待 fuzz 验证的漏洞假设（按优先级排序）

| 编号 | 假设 | 位置 | 为什么可疑 | 验证方式 |
|---|---|---|---|---|
| **B1** ★★★ | **LUT 文件名路径穿越** | `POST /lut/send-prepare` 的 `filename` 字段 | 客户端完全可控，直接参与相机端文件命名；响应里出现了 `lut_0038` 这类相机端文件名 | 试 `../` `..%2F` `%00` 绝对路径 超长 中文；目标是读/写相机任意文件 |
| **B2** ★★★ | **长度字段错配 → 堆溢出/OOB** | `FileSize` / `bufsize` / `transferIndex` | 相机端若用 C 按 `FileSize` 分配缓冲 → 经典堆溢出；`bufsize` 无上界 | 试 `0` `-1` `0x7FFFFFFF` 与实际字节数不符 |
| **B3** ★★ | **槽位号越界** | `LutId` / `deviceLutId` / `PrimeId` / `DestinationId` | 整数无范围校验 → 数组越界写 | 试 `-1` `99999` `0x7FFFFFFF` |
| **B4** ★★ | **JSON 解析器 DoS** | 所有 JSON 端点 | 深嵌套/超长/畸形 | 试 1000 层嵌套、10 万字符 |
| **B5** ★ | **照片风格参数注入** | 十六进制字符串参数（`"0x0031"` 式） | 参数以字符串形式解析 | 试越界值、非数字、超长 |
| **B6** ★ | **固件更新 URL 注入** | 固件接口 | 若签名校验缺失 → RCE | 需先确认签名链 |

## C 类：服务端技术栈判断（重要）

```
证据：
  ① 响应信封出现拼写错误 `meassage` / `responseCodeCode`
     ⇒ 手写序列化/解析，不是成熟框架
  ② 分块协议是自定义四元组（FileSize/bufsize/transferIndex/transferType）
     ⇒ 嵌入式自定义协议

结论：相机服务端偏向【自研 C/C++】
     ⇒ B1 / B2 这类内存安全漏洞的概率【不低】✓

⚠️ 注意：App 侧的 OkHttp / Retrofit / Gson 只是【客户端】，
        不能代表服务端。服务端是另一套代码。
```

# 三、完整协议摘要（详见独立文档）

## 3.1 连接模型
```
相机 = WiFi 热点，固定 IP 192.168.54.1（SSID 形如 DC-S1RM2-XXXXXX，隐藏广播）
手机 = 客户端，拿到 192.168.54.x
★ 相机不响应 ICMP（ping 不通是正常的）
★ Web 服务（443）【按需启动】—— App 连上才开
```

## 3.2 鉴权
```http
POST https://192.168.54.1/（鉴权端点，待确认）
Content-Type: application/json

{"AppInfo":"LUMIX LUT Creators APP 3.1.0","FriendlyName":"<手机型号>","Uuid":"<任意UUID>"}
→ 返回 AuthToken
```

## 3.3 LUT API（三个端点）
```http
GET  /lut/info           列出全部 LUT（Data.DataList，含 LutId/LutName/PhotoStyle/LutType）
POST /lut/send-prepare   传输准备  {"FileSize":N,"LutId":N,"filename":"..."}
POST /lut/send           传输数据（分块裸二进制）
```

## 3.4 相册 API
```http
GET /media/gallery/count
GET /media/gallery/info
GET /media/gallery/thumbnail
```

## 3.5 统一响应信封
```json
// LUT/照片风格（PascalCase）
{"Header":{"ResponseCode":200,"Messages":"ok"},"Data":{"Result":0,...,"DataList":[...]}}
// 相册（camelCase）
{"header":{"responseCode":200,"messages":"..."},"data":{"dataList":[...]}}
```

## 3.6 LUT 文件格式
```
TITLE "Generated by Resolve"
#LUMIXPHOTOSTYLE CNEV2       ← LUMIX 专用标签
LUT_3D_SIZE 33
0 0.0310826 0.056611         ← 33³ = 35,937 行 RGB
```

# 五、给同事（S1M2）的操作步骤

## 预期差异

```
DC-S1M2（S1 II）与 DC-S1RM2（S1R II）:
   · 同代机身、同代固件架构、同一个 LUMIX Lab App
   · 预期【协议完全一致】（同一套 App 代码）
   · 差异可能在于：
       - 型号代码（S1R2 = MC8244，S1M2 待确认）
       - LUT 槽位数量 / 内置 LUT 列表
       - 支持的录制规格
   · 相机 IP 预期同为 192.168.54.1
```

## 他的操作步骤

```
【A. 只做协议确认（最省事，30 分钟）】
   ① 装 LUMIX Lab + Termux
   ② 连相机（同上第 0 步）
   ③ Termux 跑：
        curl -sk https://192.168.54.1/lut/info | head -c 2000
      ⇒ 应该返回他自己的 LUT 表 ✓
   ④ 对比我们的 LutId/LutName 结构是否一致

【B. 做内存抓取（拿到完整协议实证）】
   前提：手机 root（KernelSU/Magisk）
   ① adb 连上手机 → su
   ② 在 App 里进 LUT 页面 + 传一个 LUT
   ③ dump 堆：
        PID=$(pidof com.panasonic.jp.lumixlab)
        dd if=/proc/$PID/mem of=/data/local/tmp/heap.bin bs=4096 skip=8192 count=131072
      （0x02000000-0x22000000 = 512MB dalvik 主堆，约 1 秒）
   ④ gzip 后拉回电脑：
        gzip -1 -c /data/local/tmp/heap.bin > /data/local/tmp/heap.gz
        adb pull /data/local/tmp/heap.gz
   ⑤ 搜 URL：
        grep -a -o -E 'https://192[.]168[.]54[.]1[^ ]{0,200}' heap.bin | sort -u
        grep -a -o -E 'lut[a-zA-Z0-9_/.-]{2,60}' heap.bin | sort -u

【C. 跑 fuzz】
   同我们的脚本（recon.sh / fuzz_lut.sh）
```

# 八、本次逆向的关键经验（给同事避坑）

```
① 【LUMIX Lab 检测 VPN】→ 它发现有 VPN 就拒绝传 LUT
   ⇒ 所以不能用 Reqable/HttpCanary 的 VPN 模式抓包
   ⇒ 解决：root dump App 内存（读它自己的记忆，不碰网络）✓

② 【相机热点只允许 1 个设备】
   ⇒ 电脑挤不进相机网络 → 没法用电脑当代理抓包
   ⇒ 解决：同上，走内存 dump ✓

③ 【相机 Web 服务按需启动】
   ⇒ App 不连上，443 端口就是关的，curl 一定超时
   ⇒ 必须先让 App 连上相机

④ 【Android 会踢掉"无互联网的 WiFi"】
   ⇒ 关掉移动数据 + WiFi 助理，否则手机会自动切走

⑤ 【adb 反复 offline】
   ⇒ adb kill-server 会触发 USB 重新枚举 → 在 OPPO 驱动下容易变 offline
   ⇒ 别频繁 kill-server；手机重启一次能恢复
   ⇒ USB 尾插松的话，改用【无线调试】或 Termux 手敲
```
