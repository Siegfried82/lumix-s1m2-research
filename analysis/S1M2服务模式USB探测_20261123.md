# S1M2 服务模式 USB（04DA:2370）只读探测：有界读可用，绝对地址读冻机

> 日期：2026-11-23　机型：DC-S1M2（机身报告固件 V1.4）　边界：**只读，未发送任何写命令**
>
> 本轮只在自己持有的机身上进行。未上传固件、维修资料或商业软件；未使用网络凭据。

## 1. 要验证的问题

公开前作（flickering-star/lumix-firmware-research 的 GM1/GM5/GX9/GX8，
gavenomix/lumix-gx8-usb-service，以及 USER-HFC/Lumix_Tool 的 S5 音效替换）
都通过服务模式厂商 USB 接口 `04DA:2370` 读取机身 RAM，并在部分机型上用
`0x9C` 写 RAM。问题是：

1. S1M2 是否保留这个服务模式 USB 接口？
2. 保留的话，帧格式和命令族是否与旧机型相同？
3. 能否用 `0x5C`（1 KiB 绝对地址读）/`0x9B`（绝对半字读）访问 Linux DRAM？

## 2. 环境与身份

- 入口：关机后按住 `回放（PLAY） + AF-ON` 再按电源开机。普通开机并接 USB
  时，机身先弹出 USB 模式菜单（PC storage / PC tether / PC web cam / LUMIX Flow）。
- 服务模式下枚举：

```
04da:2370  bDeviceClass 0x00
  if0 alt0: class=0xff sub=0xa0 proto=0xb0  endpoints=3
    ep 0x01  bulk OUT
    ep 0x81  bulk IN
    ep 0x82  interrupt IN
```

- 主机：macOS（Apple Silicon），libusb 1.0.30。Windows 下同一接口可用 WinUSB 绑定。
- 帧格式与公开前作一致：16 字节请求 `08 00 ff <op> ... <sum> 00`，
  校验和 = `sum(bytes[1..13]) & 0xFF`；`0x5C` 为 1030 字节帧，
  地址与结束地址各 4 字节小端，校验和在 1028、终止符在 1029。
- 交换时序：vendor control OUT（`0x40, bRequest 0`，`wIndex 0`）→ bulk OUT →
  等待 100 ms → vendor control OUT（`wIndex 1`）→ 读 1 字节响应类型 →
  再次 control（`wIndex 1`）→ 读完整回复帧。

## 3. 工具

只读客户端源码随本报告提供：`service_usb_probe_20261123/svc_probe.c` 与 `Makefile`。
它只实现 `0x35`、`0x38`、`0x3A`、`0x75`、`0x9B`、`0x5C` 六个读 opcode；
源码中不存在 `0x9C`（写）与 `0x70`（旧程序相对读，已知会冻机）的构造路径。

```sh
make
./svc_probe selftest          # 离线帧构造校验，不碰设备
./svc_probe identify          # 0x38, area 0x20, index 0x3F80..0x3F8F
./svc_probe raw 0x3a          # 元数据查询
./svc_probe raw 0x35 000010   # index 0, selector 0x10
./svc_probe sweep 0x38 0x22 0 0xFFFF   # 有界字扫描（未在本轮执行）
```

## 4. 观察

### 4.1 `0x38` 旧识别选择器被拒

请求 `0x38, area 0x20, index 0x3F80` 的回复（16 字节，校验和通过）：

```
08 00 ff 01 03 00 00 00 00 00 00 00 00 00 03 00
```

`[3] = 0x01`，不是旧机型识别成功时的 `0x36`。**这与 GX9 公开记录中相同请求的
回复逐字节一致**（flickering-star 文档：area `0x20` 容量为 0，属越界拒绝）。

### 4.2 `0x3A` 元数据查询成功

回复 262 字节（帧类 `0x10`），opcode `0x3B`。按本机解析，`[4]` 为条目数
（本轮为 0x10），随后每条 5 字节：1 字节 area id + 4 字节小端容量（word 数）。

| area | 容量（words） | 说明 |
|---|---|---|
| 0x10 | 65536 | 与 GX9 公开表一致 |
| 0x11 | 65536 | 同上 |
| 0x21 | 65536 | 同上 |
| 0x22 | 65536 | 同上 |
| 0x30 | 3072 | 同上 |
| 0xFF | 256 / 256 / 6144 / 6144 / 0 ×6 | 占位行，不证明可读 bank |

回复开头（hex）：

```
10 00 ff 3b 10
10 00 00 01 00
11 00 00 01 00
21 00 00 01 00
22 00 00 01 00
ff 00 01 00 00
ff 00 01 00 00
ff 00 18 00 00
ff 00 18 00 00
ff 00 00 00 00
30 00 0c 00 00
[... 其余 0xff / 0 行，尾部补零]
```

**area 表与 GX9 公开结果完全一致**，说明 S1M2 沿用同一套服务中间件。

### 4.3 有界字读成功

16 字节 `0x35` 请求，`[4..5] = index`、`[6] = selector`：

| 请求 | 回复 | 值 |
|---|---|---|
| `0x35`, index 0, sel 0x10 | `08 00 ff 36 00 00 00 00 00 00 00 00 00 00 35 00` | 0x0000 |
| `0x35`, index 0, sel 0x20 | `08 00 ff 36 f9 61 00 00 00 00 00 00 00 00 8f 00` | **0x61F9** |
| `0x35`, index 0, sel 0x22 | `08 00 ff 36 00 00 ...` | 0x0000 |
| `0x38`, index 0, sel 0x22 | `08 00 ff 36 00 00 ...` | 0x0000 |

`0x36` 回复与校验和均有效。`0x61F9` 的语义本轮未确认，只记录为 selector `0x20`
下的非零设置字。

### 4.4 绝对地址读全部冻机

| 请求 | 结果 |
|---|---|
| `0x5C` @ `0x40000000`（1 KiB） | `LIBUSB_ERROR_OTHER`，随后设备从总线消失 |
| `0x9B` @ `0x80000000`（2 字节） | `LIBUSB_ERROR_NO_DEVICE`，设备消失 |
| `0x9B` @ `0x03700000`（2 字节） | 发送后**立即**冻机（操作者现场观察），设备消失 |

三次都通过断电重启恢复；每次之后重新进入服务模式，`0x3A` 元数据查询仍正常。
没有发送过 `0x9C`、`0x70` 或任何未知 opcode。

`0x03700000` 是按“地址字段 = 物理地址低 32 位、固件自动补 `0x4_0000_0000`”
假设选的候选（S1M2 Linux DRAM 物理基址 `0x4_0370_0000`，低 32 位即
`0x03700000`）。它同样立即冻机，否定了这个假设。

## 5. 推论

- S1M2 保留服务模式厂商 USB 接口，帧格式与旧机型相同，`0x3A` 元数据表与 GX9
  逐项一致。**服务中间件是同一族。**
- `0x35`/`0x38` 的有界设置读可用；`0x3A` 的 area 表可信。
- 绝对地址读在三个候选地址上都直接冻机，且没有“返回错误帧”的安全探测空间。
  这与 GX9 在 `0x40000000` 的表现同型（GX8/GX9 的工作地址是 `0x80000000`，
  因为它们的 DRAM 物理基址就在 32 位内）。
- S1M2 的 Linux DRAM 在 `0x4_0370_0000`（34 位），而协议地址字段只有 4 字节。
  现有证据不足以证明服务固件提供低 32 位别名、窗口或 64 位地址扩展；
  `0x03700000` 的冻机排除了最直接的低 32 位别名假设。
- 因此，在没有 S1M2 专用服务/调整软件（内含真实地址映射与新命令语义）的情况下，
  继续盲试地址没有可复现的收敛路径：每次失败都是一次冻机。

## 6. 未知

- 服务固件的 32 位地址字段到底对应哪个地址空间（物理、RTOS 虚拟、还是窗口偏移）。
- 是否存在 64 位地址扩展或窗口选择命令（例如 GX9 原生文档提到的 `0x48/0x49`
  半字/字访问；本轮未发送）。
- 冻机的具体机理（RTOS 取址异常、总线挂死、复位）以及是否可由某个状态位阻止。
- 服务模式菜单的 ROM BACKUP 是否能导出 6 个 EEPROM 区之外的内容；本轮未检查。
- S1M2 专用 DIAS/服务软件的命令集与地址映射。公开检索只找到 TSN 登录入口；
  第三方维修手册（remont-aud 的 DC-S1M2 PDF）未定义 USB 协议或地址。

## 7. 与既有实验的差别

- 既有 `S1M2_RAM读取入口_核查结果_20261008.md` 检查的是原厂 Tether/Lab 的
  PTP 路径，结论是未找到任意物理地址读；本轮检查的是**服务模式厂商 USB**，
  两者是不同的传输层。
- 本轮首次在 S1M2 上实测 `04DA:2370`、`0x3A` area 表和 `0x35` 有界读；
  并把绝对地址读的失败边界记到具体地址。
- 本轮不涉及固件解码、不写机身、不执行供应商软件。

## 8. 什么结果会推翻本结论

- 在 S1M2 上找到任一可用的绝对地址读（例如某个 32 位窗口、`0x48/0x49`、
  或带基址选择的命令），且能重复读回稳定数据；
- 证明冻机由时序（settle）而非地址引起——例如同一地址在调整时序后成功；
- 获得 S1M2 专用服务软件并静态确认其地址映射/命令集，证明存在本轮未试的读路径。

## 9. 安全与恢复

- 工具只读；`0x9C`/`0x70` 在源码中不存在。
- 冻机恢复：拔 USB，长按电源关机，再按 `回放 + AF-ON` 重进服务模式。
  三次冻机均如此恢复，未观察到持久影响。
- 服务模式空闲数分钟后会自动关机；长时间读取需要机身保活。
- 不建议在未验证地址语义前发送 `0x9C`。S5 的暂存区 `0x8F000000` 是 S5 自身的
  映射，不能移植到 S1M2。
