## 2. 最有价值的新证据：S1H 的原厂隐藏格式选择

### 2.1 可以直接从归档核验的内容

`Panasonic_hidden_format_research_20261012/evidence/s1h_activation/` 下的原始 XML：

- capability 机型为 S1H。
- allmenu 有 106 个不同录像质量声明值；普通 MP4 上下文 curmenu 有 21 个启用质量值。
- 集合差恰好 16 项，与候选报告一致。目标 `mp4ed_25p_400mbps_4k_10bit` 不在 allmenu 的质量 setter 声明中，却在该 curmenu 中启用。
- `target_set.bin` 返回 `ok`，两份后续读回均为上述完整 token，格式读回为 `mp4ed`。
- 初始与目标后的状态均为 `rec=off, cammode=rec`；状态版本字段 VD3.60 不能冒充公开固件 V2.8 的版本证明。

核验结果：`s1h_menu_check.json`。两份同内容读回支持归档记录的一致性，不能仅凭它们相同的散列独立证明两次真实发送。历史 requests.json 无逐项时间戳；三项内容计数/模式切换记录缺少对应原始响应。

直接查看了 `native_menu.png` 与 `reboot_contact.png`：机身画面显示 MP4(LPCM)、Full-frame、3840×2160/25.00p、422/10bit/ALL-I、400Mbps、LPCM，质量列表与“添加到列表”可见；拼图也包含空白格式选择框。由此支持原厂 UI 显示发生变化，但不能把空白格式选择器写成永久新增的正常菜单入口。

### 2.2 媒体证据的实际边界

该包 README 明确为轻量版，两段原 MP4 均不在目录中；原手机菜单/重启视频、CAMSET 前后快照也未附。不能在本轮重新计算原视频散列、重新完整解码或证明原采集过程。

我独立解析了元数据中存档的 AVC SPS 字节，而非直接信任 `verified_recording.json` 的标签：

| 归档片段 | SPS 独立解析 | 日志核对 |
|---|---|---|
| P1022640 | 1280×720，chroma_format_idc=1，亮度/色度8bit | 软件解码日志最终180帧；无逐帧showinfo，不能做逐帧类型核验 |
| P1022641 | 3840×2160，chroma_format_idc=2，亮度/色度10bit | 168条showinfo，索引0–167连续、PTS间隔3600、全部I/关键帧、yuv422p10le |

P1022641 元数据中的 604800/90000=6.72秒、168/6.72=25fps 相符；日志音轨为 PCM s16be、48kHz、双声道。按223826574字节与6.72秒重新计算文件平均码率为266.460Mbps；400Mbps是菜单标称档位，不能作为恒定实测码率。

这些结果使作者关于4K25/422/10bit/ALL-I/LPCM的记录具有多处相互一致的证据。仍应表述为“归档响应、截图、SPS与逐帧日志支持；原媒体待独立重验”，而非“本轮亲自在相机录出”。结果见 `sps_check.json`、`media_log_check.json`。

正常重启保留仅有作者转述用户确认及事后图像，未附完整重启录像。14项精确读回、各格式后台记忆tag、848条S1H CAMSET记录及逐字节完整恢复，缺少足够原始快照供本轮逐项重验，保留为作者记录。

### 2.3 成果意味着什么

这是已有固件配置/显示路径的可达性证据，比单纯setter=ok或旧GX9叙述更有力。它没有提供程序解密、任意代码执行、新传感器时序或更高硬件性能的证据。也不证明S5、S1M2或S1RM2拥有同一可用路径。

较值得继续的是隐藏格式与“我的列表”的原厂消费者：能否保存后从其他普通格式重新进入、其配置字段与列表字段如何关联。这是可验证的问题；当前材料未完成它。

## 4. S5 总报告：可用输入与重要更正

### 4.1 原固件和配置实际核验

本包 `S5___V29.bin`：90238464字节，SHA-256：

`b2ec4aeec209693b874df8dfdf11fc85b38fa4675b44ec554b7a167f430827e1`

- 重算外层CRC32(data[0x200:])=`0x8e73aac0`，与头字段一致。
- 独立重读0x2ec起的48个92字节条目，逐项保留索引。
- 以原始文件偏移解释存储offset，只有2项目录摘要匹配；加0x200基准后7个type2均匹配，41个type3均不匹配。
- type2匹配区为常量填充；这些匹配验证此输入的载荷位置，不能单独证明密码算法或type3明文。
- loader1正确范围为[0x1600,0x2600)，4096字节只有20个零；报告“512B零头+3584B密文”来自旧错误偏移，不成立。
- 尾512字节与附带 `.sig` 完全相同，证明两份数据相同，尚未证明RSA算法、位数、签名覆盖范围或验证位置。

结果：`s5_firmware_directory.json`。`03-固件格式与启动链.md`把offset写成绝对值，并解释成目录/数据重叠44B，属于仍需撤回的旧叙述。隐藏格式包内静态修正材料较接近本轮独立结果；同一来源中的新旧矛盾必须保留并指出，不能只读总摘要。

S5 PTP配置为65545字节，SHA-256：

`e808a6b899173a5a7ee8ef7a790c5ca24ba450d64b80ea3fe731db10123f20ab`

外层tag=0x080000a2，长度65537；内大小65533。原始文件0x40（去外层8字节后0x38）起连续解析831条记录，终点0x10004，尾部ffff0000bd，从原始+12求和模256为0。两份配置副本相同，且与已有交付包一致。这是已有配置样本再归档，不能算新读取；“全量出厂配置明文、所有设置、导入格式已彻底破解”超过结构验证范围。结果：`s5_config_check.json`。

13个新目录文件与之前S5交付包逐字节相同，包括配置、采集日志、设备信息、部分目录JSON与PTP Python工具；重复关系见 `previous_delivery_matches.json`。

## 5. 新增S5可分发版的价值与缺陷

### 5.1 独立可复核的数据

25个文件，24个manifest载荷全部匹配，无未列出文件。机型响应为S5；没有可直接证明公开固件版本的productinfo/version。报告写“固件VD4.30”混淆接口状态字段与公开固件版本。

- allmenu SHA-256=`2cf69074d41ac134e9a65ca631cf4842cefc5c49d24cc855ac2094fdbd1e857c`，与此前S5菜单相同；不能算新的菜单版本。
- allmenu声明47个不同setsetting域。它只证明菜单声明，不证明47域逐一写入且持久生效。
- hlg声明值只有4k/full/off；curmenu含hlg_photo_8k且enable=yes。这是候选UI标识，不单独证明setter精确映射或真实8K输出。
- `videoformat=mp4hevc`已经在allmenu声明。curmenu该格式enable=no，但 `mp4hevc_25p_72mbps_4k_10bit` 质量条目enable=yes；说明两个菜单层级的状态不同，不构成格式已经可选的证明。
- 6K PHOTO相关setter已经声明，属于已有功能；把它等同6000×4000全传感器Open Gate视频、把4:3仍写成6000×4000、把不同6K画幅统称2:1裁切，都缺实际输出依据。
- 新HTTP CAMSET为65533字节，831条记录，尾ffff00004d，全体求和模256为0；与旧PTP去前12字节后等长，但21字节不同。采集上下文未完整附，不能给差异贴功能含义。

此包无HLG/HEVC照片或视频、无本次握手成功的完整原始轨迹。作者关于play模式写hlg=8k后读回off的记录不证明“切照片模式必成功”；模式门控只是解释候选。

### 5.2 枚举汇总并非接口全覆盖

surface_map.json实际保存137个getinfo类型、116个mode，数字不是文档的约110/90。getinfo的4个interesting项为capability/allmenu/curmenu/camsetting；modes只有getstate被其分类器标为interesting。

mode扫描都用type/value=zzprobe；已知getsetting也被err_param排除，足以说明错误参数阴性不能判断接口不存在。旧报告已有startsenddata/senddata/endsenddata等接口，它们不在本次mode列表，因此“整个mode面只有7个”和“RCE基本不可行”不能从此汇总推出。摘要只有状态码、结果和分类，缺逐项原始响应/时间戳，证据不闭合。

结果：`s5_distribution_check.json`。

握手部分有参考价值，但“只一个pending槽、彻底修好根因、没有token所以不存在X-SESSION_ID、协议版本路线完全关闭”需要客户端实际分支和受控成功/失败轨迹。通信协议版本与固件升级版本是两件事，不得把两份报告的“版本门”混成同一个问题。

## 6. 对S1M2研究的推进顺序

1. **继续离线追踪已有功能消费者。** 把S1H的菜单差集→连续精确读回→原厂UI→真实文件的证据方法迁移到S1M2录像详情；不移植S1H/S5的token或配置tag。已有S1M2的114详情/80能力差异需同一状态对照与实际输出验收。
2. **补原媒体与同状态快照再定位映射。** 只有原始MP4才能重新独立验证样片；只有前后原CAMSET才能核验MP4ed后台记忆、我的列表与完整恢复。没有这些输入时保持为候选，不虚构字段含义。
3. **沿已确认客户端和开源读取路径寻找新格式的真实生产者/消费者。** 本次S5输入修正了偏移，但并未给出selector3解码代码。继续目标仍是0x200新格式处理代码、输出到RAM的链路，不重复扩大无依据候选key扫描。
4. **把新包工具缺陷先消除，再另行考虑机身采集。** 本次只授权资料解析；没有设备通信/写入授权。任何后续采集工具需精确型号、固定只读白名单、逐请求时间和原响应、不自动握手或recmode；写实验必须真实读到原值、精准验收与后台状态恢复。

现有材料没有证明S1M2程序解密、任意地址写、新LUT能力或自定义快门声音。电子快门现有结论仍仅是内置声音选项变化。总体目标未完成，保持继续研究。
