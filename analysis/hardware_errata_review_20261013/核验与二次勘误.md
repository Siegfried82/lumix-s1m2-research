1. 旧05报告第131–143行的九个宏定义不在真实`pvc04v-MC8241-rtos.h`中。真实头文件为47行，完整SHA与新稿列出的`8c995294...ead61`吻合。旧文的`snrtos_Original_table`也不存在；实际DTS第82–95行是shared_commem，第154–159行定义ipcufs Unit0、发送邮箱7和接收邮箱6。旧IRQ归属错误应改为NAND SPI199、eMMC SPI213（DTSI第709–732行）。

3. 旧06接口表确实把路径/方法写错；真实`p084h6/a.java`共289行，SHA与新稿给出的完整值吻合。唯一remote路径8个、photostyle12个、lut9个、media9个加auto-transfer1个、firmware3个。实际固件路径是`firmware/send`（第55行）、`firmware/send-prepare`（第59行）、`firmware/abort-send`（第205行）；方法r是`photostyle/set-display-setting`（第255行）。这只校正已审接口表，不能顺便宣布旧稿其余所有BLE/TLS推导全部通过。
4. 静态DTS的black-list恰有403个唯一值；在0..415全集中，剩余13个为185、186、189、192、194、197、306、312、315、321、385、386、387，与新稿表一致。它是所保存源码配置的事实，未屏蔽不等于已加载驱动，更不证明剩余403个中断都由当前机身RTOS处理。
5. 保存的维修手册文本确实在第1227–1228行标出2G-bit NAND、第1270–1271行标出两颗32G-bit LP-DDR4，第1224–1225行列有独立副MCU。容量换算为256MiB NAND和8GiB总DRAM成立。副MCU存在不证明固件包内有`sub_prog`。

## 新稿必须纠正的实物错误

### 组件表混用了另一套目录

32..60的29项中，5项名称及大小错误；21项明确给出的destination端点全部不符。区间表中另外8个内部地址未逐项写出，不能计作21项之外的“已核错误值”。原稿中8个具体候选摘要前缀也均不匹配该S1M2输入。

| 索引 | 新稿说法 | 此SHA对应的真实目录 |
|---|---|---|
| 0/1 | `[0] loader1`，64KiB，destination0x80000 | `[0] boot`零长；`[1] loader1`128KiB，destination0 |
| 32 | hm_c_ddr，destination0x076c0000 | 名称/3MiB相符，destination **0x084c0000** |
| 34 | hr_c_prog，destination0x07ac0000 | 64KiB，destination **0x088c0000** |
| 37 | hr_d_ddr1，零长 | **pzm_data，65,536字节，flags3** |
| 38 | hr_d_ddr2，零长 | **xtk，131,072字节，flags2** |
| 39 | hr_d_ddr3，零长 | **lut_data，8,781,824字节，flags2** |
| 49 | enc_c，64KiB | **dsh_adj，131,072字节，flags2** |
| 60 | sub_prog，512KiB | **ai_awb_data，1,835,008字节，flags3** |

全62项没有sub_prog、enc_c或名为rtos的条目。名称未出现也不证明这些功能或执行域不存在；只是禁止用伪造的条目建立加载映射。正确32..60全表见[实际目录与候选边界](实际目录与候选边界.md)，完整摘要和源偏移见verification.json的firmware.rows。

### NAND/运行地址推导未闭合

62项只有**58项**destination为128KiB整数倍，例外为41、43、45、48，它们落在64KiB边界。实际非连续destination关系有7处，但并非原稿所列7处：

| 前项→后项 | 实际gap |
|---|---|
| 3→4 | 0x60000 |
| 19→20 | 0x1fe00 |
| 20→21 | 0x1fe00 |
| 21→22 | 0x1d000 |
| 22→23 | 0x1d000 |
| 34→35 | 0x10000 |
| 37→38 | 0x10000 |

NAND控制器DTSI第712行两个reg窗口均为0x10000，不是新稿表中的64B/4KiB；该节点没有给出128KiB擦除块几何。芯片总容量、地址数值规整或这些gap不能证明`entry+0x14`就是NAND物理偏移，也不能证明余下85MiB用于特定配置/日志。不得把它直接作为RAM加载地址或读出范围。

## 硬件与消费者的关键断点

- 源码DTSI第931–945行真实compatible是`socionext,dsp-peri-device`加`is-xm6`，不是新稿初版引述的`socionext,xm6-peri-device`；DT确有0x1c000000/512KiB和0x1c200000/64KiB两个资源。驱动并没有新稿所称的两个D_XM6地址宏定义。
- DMA分支实际在`sni_dsp_drv_m20v.c`第907–947行。第925/927/930行三个常量都是注释；第917、926、928、929行实际从用户结构读取dstAddr/srcAddr/size。`0xAC908000`不构成固定机内暂存区证据。第1027–1053行TCM资源ioremap还在`#if 0`内，不能当成当前启用的装载路径。
- 组件大小吻合TCM窗口，只支持候选关系。还缺解码后长度、真实调用者的具体dst/src/size以及载荷ISA/格式，不能将hr_c_prog/hr_d_prog和IC实体标为已闭合。
- 以名称＋出现序对照SL3，32..60只有**15项候选目录摘要匹配**，不是全部29项。网络1st..8th匹配，9th不匹配；hr_c_prog、hr_d_prog、EIS/LDC、fstack等多个项目也不匹配。15个保存SL3载荷仅flags2全FF的mbr_dummy_d完整摘要相符；14个受保护样本没有原始摘要阳性。去掉XOR FF不等于解开受保护载荷。
- R5/e.java实际读取bufsize及8种预检码，R5/h.java第72行调用上传，R5/f.java第46行识别err_fw。这能恢复客户端协议；缺HTTPS daemon处理函数、临时文件路径、ipcufs实际调用者及RTOS认证/解码代码，不能宣布“上传必经ipcufs写SD，再复用同一刷写链”。错误码也不单独证明err_fw由某种容器认证失败产生。
- MC8266整份DTS在统一子型号token后与MC8241相同，差异包括include与compatible，不仅model一行；Leica保存DTS的Wi-Fi设置有差异。这不覆盖预处理后的完整DTB或机身硬件。开源发布页列出devmem2也不证明它已装入特定未解码rootfs、具有足够权限或能读取全部物理地址。
