## 当前实际判断

## 新核查的公开来源

### 1. 原厂高分辨率与多重曝光路径

[高分辨率模式](https://eww.pavc.panasonic.co.jp/dscoi/DC-S1M2/html/DC-S1M2_DVQP3227_eng/0053.html)明确描述多图合成、RAW/JPEG 输出，以及保存第一张普通尺寸照片的选项；强制使用电子快门或电子快门加降噪。该页没有给出全组输入帧导出接口，也没有给出所查模式的内部帧数。

[多重曝光](https://eww.pavc.panasonic.co.jp/dscoi/DC-S1M2/html/DC-S1M2_DVQP3227_eng/0071.html)提供最多四次曝光效果、按张数自动调亮度的 Auto Gain，以及从本机 RAW 开始叠加的 Overlay。高分辨率 RAW 不支持 Overlay，多重曝光与高分辨率模式互斥。


### 2. 官方 Tether 与公开 SDK 不应混为一谈

[LUMIX Tether](https://av.jpn.support.panasonic.com/support/global/cs/soft/download/d_lumixtether.html)列明 S1M2，更新记录显示 2.10 起增加支持。当前所读页面提供 Mac 与 Windows 下载，且明确不能控制相机全部功能。下载流程要求序列号与许可接受。本轮没有提交序列号、接受许可或下载/安装该程序。

[公开 SDK 页面](https://av.jpn.support.panasonic.com/support/software/tool/sdk.html)列出曝光、对焦、拍摄、照片复制和实时取景等 API；所读支持型号列表没有 S1M2。不能因 Tether 支持就宣布旧 SDK 对 S1M2 已验证可用；同样不能从列表缺失断言其绝对不兼容。

意义：可研究原厂支持的拍摄控制路径。它不证明有任意命令执行或内存导出。

### 3. libgphoto2 的 Panasonic 协议是有源码的入口

来源：[ptp.h](https://github.com/gphoto/libgphoto2/blob/master/camlibs/ptp2/ptp.h)、[config.c](https://github.com/gphoto/libgphoto2/blob/master/camlibs/ptp2/config.c)、[library.c](https://github.com/gphoto/libgphoto2/blob/master/camlibs/ptp2/library.c)。本轮通过网页读取 master，未取得固定提交 SHA；后续本地快照应固定提交并记录哈希。

ptp.h 中有 Panasonic 的属性读取、设置、拍摄、取景、事件和对象传输操作码，以及 ISO、快门、光圈等属性定义。config.c 有 Panasonic 手动对焦、取景、Bulb 等实现。所读 library.c 对 S1M2 的精确文本检索未命中；这只能说明该文件未列此名字，不能排除通用 PTP 支持。

对象传输读取的是 PTP 对象，不应解释为读取任意物理内存。ptp.h 中 Leica 的调试命令与 Panasonic 命令是不同厂商扩展，不能跨机型直接试用。本轮没有发送任何操作码。

## 从原始源码核实的反证

### MC8241 配置不能直接代表 S1M2 的最终构建

源包 `analysis/sources/linux-4.19.124.tar.gz` 中的 `linux-4.19.124/arch/arm64/configs/pvc04v_MC8241_defconfig` 与选取副本 SHA-256 均为：

`757efee7162ca853d1970dc5d988accc6a0c07a2ef362ca6fc14408b3a9cc0c2`

该文件含 `CONFIG_VMSPLIT_2G=y`、`CONFIG_THUMB2_KERNEL=y` 等 32 位 ARM 配置，又含 `CONFIG_ARM64_SVE=n`。因此文件路径和名字不能证明最终内核构建架构。也不能将 MC8241 源配置直接等同于头部标识 MC8243 的 S1M2 更新包。

### STRICT_DEVMEM 关闭仍不能推出任意地址可读取

直接读取上述原始 Linux 源包 `drivers/char/mem.c`：

- `open_mem` 绑定 `open_port`，检查 `CAP_SYS_RAWIO`。
- `read_mem` 仍调用 `valid_phys_addr_range`，失败返回 `-EFAULT`。
- 未启用 STRICT_DEVMEM 时放开的是 `page_is_allowed`/`range_is_allowed` 这一层。
- `arch/arm64/include/asm/io.h` 声明架构自己的地址范围检查。
- 进一步核查原始包 `arch/arm64/mm/mmap.c`：`valid_phys_addr_range` 要求 `memblock_is_region_memory(addr, size)` 且 `memblock_is_map_memory(addr)` 成立。因此以 `dd`/read 读取 Linux 未登记或 NOMAP 的其他域内存，可能直接被这一层拒绝。`mmap` 有另一个物理位宽检查；这不能代替目标映射和访问权限的验证。

这直接反驳“关闭 STRICT_DEVMEM 就能无越狱读取整个物理空间”。真实运行配置、节点可用性、能力权限、地址范围、硬件隔离和诊断入口仍需独立验证。

### 转储示例的地址计算存在问题

项目解析器把 `DDR_BASE_ADDR = 0x400000000` 注释成 4 GB；实际为 16 GiB 的物理地址数值，并不意味着装了 16 GiB RAM。


### RAW 容量与提取器均不能支撑报告承诺

6000×4000×14/8 = 42,000,000 字节；16 帧为 672,000,000 字节，约 640.9 MiB。若按每像素 16-bit 容器则每帧为 48,000,000 字节；机内实际排列、压缩、步幅和帧数未知。

`s1m2_firmware_project/tools/dump_memory_parser.py` 的 `scan_for_raw_frames` 仅在固定对齐位置找 PANARAW 或 RAWFRAME 文字标记，没有验证真实 Bayer 数据。`carve_assets` 只写 JSON 报告，没有提取 RAW 像素、DSP 或 CNN 文件。测试自己植入 PANARAW，不能当成真实内存样本验证。

参考结构体与合成测试仅用于工具验证，不能证明设备端实际行为。

### 补充实验：公开 Panasonic A/V 算法不能直接套用

取得 [pana_dvd_crypto](https://github.com/theubusu/pana_dvd_crypto) 源码，固定提交 `bf2650e81034e937e34095c376519ebc3f04e5cd`。只审阅源码，没有编译或执行其程序。

`src/crypto.rs` 使用调用者提供的 8 字节密钥；`decrypt_data_inplace` 为全部独立 8 字节块使用同一个密钥调度，不包含 IV 或跨块链式状态。源码注释提及 `libfmupre.so`，仓库没有 S1M2 样本或成功验证记录，也没有直接提供本机密钥。

用原始 V1.4 包核对第 61 项：其 128 KiB 数据全部为 FF，实际 SHA-256 与第 8、10 项目录散列相同。在“第 8、10 项明文也是相同全 FF 数据”这一待证实假设下，直接使用同一密钥的独立可逆块变换应产生重复的 8 字节密文块。实际两个编码项各有 16,384 个块，全部互不相同。

因此可排除这个公开实现对上述全 FF 假设的直接适用。不能排除额外链式模式、逐块不同密钥、压缩/预处理或其他构造；也不能因此确认 S1M2 采用 AES。

复现：`python3 analysis/audit_public_decoder.py`。结果、源文件散列和限制见 `analysis/public_decoder_structural_check.json`。脚本核对输入固件散列且不写原始固件。

协议方面，libgphoto2 `ptp.h` 将 `0x9703` 注释为 `Mnt_GetInfo_GetVersion ... 1 arg?`，但所查 Panasonic 实现没有相应调用包装或参数解释，不能据此构造可靠的 S1M2 版本查询。标准 `DeviceVersion` 字段有显示代码；其返回内容和库初始化副作用仍需按具体设备验证。当前未连接相机。

### 补充源码路径：内部缓冲驱动

直接读取 `linux-4.19.124.tar.gz` 中四个原始文件并记录散列，结果见 `analysis/buffer_interface_evidence.json`，复现脚本为 `analysis/audit_buffer_interface.py`。

- `drivers/pvc/buffer/main.c` 使用 `<linux/scullp.h>`；不能拿同目录未被该 include 使用的旧 `scullp.h` 中固定两个缓冲区的定义当成实际 ABI。
- 真正的 `include/linux/scullp.h` 用 `CONFIG_BUFFER_NUM` 定义缓冲区数量，定义缓冲列表、地址查询和两个方向的复制操作。物理到虚拟复制分支执行 `ioremap` 和 `memcpy`，其地址、目标内核指针和长度来自调用者提供的结构体。
- 所查 ioctl 函数没有显式 `capable()` 检查；设备节点/VFS 权限、模块加载状态、ABI、指针有效性和硬件访问仍然制约使用。它不能被称为安全或可直接使用的机身转储接口。
- MC8241 配置含 `CONFIG_PVC_USB_BUFFER=m`，未显式设置 `CONFIG_BUFFER_NUM` 与 `CONFIG_BUFFER_SIZE_ORDER`。Kconfig 默认分别为 1 和 7，但实际缓冲大小还取决于最终配置与 PAGE_SIZE，且源配置不能直接代表 S1M2。
- 普通 read 读取的是驱动自己的缓冲区；没有证据说明里面保存高分辨率输入 RAW。物理复制分支也不是电脑侧 PTP 对象传输。

这条线索比“关闭 STRICT_DEVMEM 即可读取整个地址空间”的推断更具体，但仍缺机身内部代码执行入口、真实模块/节点和地址验证。本轮没有构造或执行调用这些 ioctl 的设备程序。

U-Boot 的 MC8241 配置将 gzip 内核解压后通过 `booti` 启动，并以 `CONFIG_BOOTDELAY=-2` 关闭自动启动中断；这不提供电脑侧解码 UPD 或直接进入控制台的方法。其 `mach-milbeaut/milbeaut.c` 映射 0x400000000 起的地址窗口，也不能据此确定 S1M2 的实际 RAM 容量或运行态分区。

### 进一步核查：实际组件载荷

使用 `analysis/compare_sl3_payloads.py` 按目录范围请求官方 SL3 固件的 12 个组件，每次严格要求 HTTP 206、正确 Content-Range 与长度。下载范围包括八个 `hm_d_nw_*`、`hm_d_reid`、两个全 FF 候选 postboot 和直接可读的 `mbr_dummy_d`。没有下载完整升级包，没有执行任何固件。

下载字节去除外层 XOR FF 后保存，并逐项计算 SHA-256，与本地原始 S1M2 对应载荷比较。结果见 `analysis/sl3_payload_comparison.json`：

- 九个 `hm_d_*` 项均为大小相同、目录散列相同、目录尾字段不同、实际编码载荷不同；归一化载荷的散列均不匹配其目录散列。因而不能称为已经取得九个明文模型，也不能从密文不同断言密钥不同。
- `mbr_dummy_d` 在去除 XOR 后全部为 FF，载荷 SHA-256 匹配目录字段，并且与 S1M2 对应项逐字节相同。这为取样偏移及外层 XOR 提供了具体阳性对照。
- 两个 postboot 候选项的目录散列相同，但实际载荷不同且不能直接校验；其全 FF 明文仍是待检验假设。
- 对保存的 12 个文件重新计算散列和长度，均与结果清单一致。

这确认“共享部分解码内容”是值得追踪的假设，也确认仅除去 SL3 外层 XOR 仍不足以读取内部编码组件。下一步需定位两者加载器的真实解码规则，不能直接互刷或宣布已有可用解码器。

## 后续实查：旧 DLL 的命令分类函数补齐

此前扫描只覆盖 PE 展开表中的函数。实际追踪 `0x2c97` 的直接调用发现 `0xc280` 是未出现在该表中的叶函数，不能用之前的阴性结果概括整个 DLL。已扩展 `audit_lumix_sdk_binary.py`，对代码段做补充线性扫描，并保存命令分类表、30 个直接调用位置与关键路径反汇编。结果统一保存在 `analysis/lumix_sdk_command_classes.json`，脚本仅解析字节，不执行 DLL。

在固定 SHA-256 的这个 DLL 中，`0xc280` 到 `0xc3dc` 范围包含命令比较和跳转表。静态读取跳转表得到：

| 命令编号 | 分支目标 RVA | 分类整数 |
|---|---|---|
| 0x9108、0x9402 | 0xc3ae | 3 |
| 0x9406 | 0xc3bc | 5 |
| 0x9606、0x9607 | 0xc3ca | 4 |
| 0x9703 | 0xc3ae | 3 |

`0x9703` 有直接比较，`0x9606/0x9607` 以减去 0x9606 后判断范围的方式识别；`0x9406` 通过跳转表识别。这解释了为何只查精确立即数会遗漏命令。它们存在于命令分类器，而非已经找到独立升级函数。

属性读取调用实例：RVA `0x2c5b` 将 0x9402 放入 ECX，`0x2c97` 调用分类器，`0x2ccd` 将分类值写入请求结构，`0x2d70` 调用 `0x18f10`。后者把请求结构中的命令、事务和参数字段复制到传输结构，并依分类 3/5/其他分派到 `0x13d20`、`0x13bb0`、`0x13ea0`。三条分支进一步调用共同函数 `0xeba0`，分别传入接收缓冲、无数据缓冲、发送指针和长度。由此推断 3/4/5 对应接收/发送/无数据阶段；此语义仍是基于静态调用关系的推断，没有实机报文对照。
