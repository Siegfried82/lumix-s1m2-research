# Tether 2.12 固件上传：原始缓存及地址来源

2026-10-11。只读取现有官方客户端的 ARM64 代码，未执行客户端库、通信相机或写入设备。库完整 SHA-256 已重新核对：`b767e5680676eefdc05d02a4772c4120a45916e246169b79393356499c07ec97`。版本 2.12，build 2.12.0.5。

## 文件缓存的数据流

原反汇编：`../tether_2_12_ptp_arm64_disassembly.txt`。本目录窗口保留原文件行号；`evidence.json` 保存输入和反汇编摘要。

1. `Get_FileData_FileSize`（VA `0x4687c`，原行70891起）使用 `stat` 取得文件长度，申请同长度缓冲，再调用 `read`。该函数返回读取缓冲和长度，没有解析组件目录或解码载荷的指令。
2. 更新调用者 `0x46154` 接收上述输出；`0x46164/0x4616c` 分别把读取指针和长度保存为 `x24/w25`。随后检查开头 `UPD` 三字节。
3. `0x4647c/0x46480` 将同一 `x24/x25` 作为参数传入 `Send_FWUP_Data`（调用点 `0x46490`，原行70639）。
4. `Send_FWUP_Data` 将参数指针保存至 `x20`；`0x46e4c` 从 `x20+块偏移` 取上传数据，`0x46e58` 调用 `LmxExt_Send_Data`。正常最大块大小为 `0x7d000`（512,000 B，500 KiB）。

**已追踪的直接路径传递文件读取缓存及 stat 长度，没有可见的组件解密步骤。** `read` 返回后的 `0x46968..0x4696c` 只检查是否为 −1，没有检查实际读取字节数等于 stat 长度；不能由这条静态链保证完整读取或实机上传逐字节等于输入。本轮没有闭合 allocator/lock、底层发送器的全部转换，也没有实机抓包。该结论不覆盖全部客户端、间接调用或机身实现。它支持把解码消费者调查重点放到接收端；不能据此确定接收端具体位于 Boot ROM、bootloader、RTOS、Linux 或硬件密码模块。

## `0x9606` 中的地址从哪里来

1. `LmxExt_Get_Event_Info` 构造 **`0x9605`**，请求事件信息，经 `SendCommand` 获取返回数据。
2. 64位分支 `0x4703c/0x47040` 将返回缓冲 `x22+0xc` 的64位字复制到结果对象 `+0x20`；32位分支 `0x47094/0x47098` 将同位置的32位字复制到对象 `+0xc`。
3. 上层调用使用结果对象基址 **`0x49e724`**，因此两分支的地址缓存分别为 **`0x49e744`** 和 **`0x49e730`**。
4. `Send_FWUP_Data` 的 `0x46d34` 或 `0x46d70` 从相应缓存读取地址，组装12/16字节元数据；`0x46df0` 交给 `LmxExt_Send_Data_Info`，后者构造 **`0x9606`**。

**该原厂流程回传的是机身提供的准备事件地址。** 地址不是在这条路径中由固件目录字段直接读出，也不是该高层函数的任意地址输入参数。

这确认了地址字段存在及其数据来源，不能确认机身会接受自行指定的地址、缺少范围检查、存在任意地址写入，或允许修改固件通过认证。机身侧命令处理和地址校验仍未知。

## 对照与边界

- `regenerated_disassembly_check.json` 记录从当前库重新生成并逐函数比较的结果；不以旧报告的函数名称当作证明。
- 状态机还包含准备、完成和错误事件。本报告只闭合读取缓存、地址来源与发送消费者，不宣称已还原完整机身更新器。
- 新格式 `header+0x34=3` 的实际算法、密钥来源、目录摘要作用对象和校验顺序仍未由这份客户端确定。
