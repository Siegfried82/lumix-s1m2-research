# Tether 应用层维护接口审计核验

本轮只检查现有原厂文件，没有发送机身命令或运行供应商二进制。

## 直接核实的证据

- 应用反汇编 154427 行通过符号存根调用 `Mnt_GetInfo_Get_UsbMode`；154459–154481 行校验返回值处于 0–3，并更新缓存或输出指针。库反汇编 75353–75362 行构造固定子命令 `0x80030002`，交给 `0x9703` 通用封包器；未出现物理地址或请求长度输入。
- 应用反汇编 95925、96073 行调用 `Mnt_Ctrl_LiveView`，对应开始/停止预览的封装。库 73666 行选择 `0x9705`。该控制调用不构成 RAM 读取。
- 本应用 ARM64 反汇编全文中，`Mnt_` 相关外部调用的可见存根只有上述两个接口；未找到维护版本查询、USB 模式写入或通用 `Mnt_GetInfo` 的应用调用。此结论限定于该反汇编可见符号，不覆盖所有间接调用或机身实现。

## 对 Antigravity 报告的修正

原始建议保存在 `tether_app_maintenance_audit_gemini_20261008.json` 和对应 Markdown 文件（若已交付）。

1. 没搜到 `dlsym`、`dlopen` 等符号，只证明这些名字未出现在当前反汇编；不能据此断言不存在任何动态加载、间接调用或所有外部通信都经已识别存根。
2. 返回 0–3 的范围检查已确认；把这四个值解释为 USB 物理协商速率，需要额外枚举定义或 UI 转换证据。本核验暂只称 USB 模式值。
3. 通用子命令封包结构不能证明机身“极可能”有更多诊断分支；仍须目标侧实现或兼容软件的真实调用证据。
4. 建议直接在 S1M2 明文里检查命令分发器的前提尚不成立：专有组件仍未解码。在高熵载荷中搜索常量，不能验证真实代码跳转表。
5. AW 版库的维护接口是否不同，是可以继续做的有限离线比较；但必须比较调用者与参数，不因找到相同常量就认定 S1M2 支持。

## 结论

这轮补上了此前未核实的应用层调用，尚未得到新的 RAM 读取入口。下一步可以比较已有 AW 版维护 API，或继续将成功采集的能力枚举映射到原厂应用含义。目标机内功能仍未完成。
