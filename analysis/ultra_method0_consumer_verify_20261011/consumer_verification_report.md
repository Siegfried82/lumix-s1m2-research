# 旧镜像消费者独立复核及 AGY 原稿修正

2026-10-11。离线读取既有 GH1__132 镜像及 AGY 原稿；没有通信相机、刷写、运行固件或分析 S1M2 未知密文。以下是限定地址范围内的指令与数据消费者结论，不能推广为整份固件的全局排除。

复现：运行本目录 `verify_consumers.py`。输出含逐输入 SHA-256、GNU 工具 SHA-256、原始指令字节、反汇编、官方 assembler alias 回组装、直接调用候选与已核验边界，以及实际升级包和反例的校验结果。输入与外部原稿均未修改。

## 1. 应立即撤回的原稿结论

| 原稿结论 | 独立核验 |
| --- | --- |
| `65 89 07 6c` 跨越两条指令，排除 PRNG 常数 | 错。文件 `0xb2756..0xb275b` 是完整 **6 字节** `fd 15 65 89 07 6c`；下一条在 `0xb275c`。GNU 显示 `udfu01 1812433253,d1`，官方 GNU AM30 `mulqu 1812433253,d1` 回组装六字节完全相同。不能从 `udfu01` 名称推断真实硬件执行异常。 |
| `0x9908b0df` 在 OSD 表，排除 MT19937 | 错。启动映射将文件 `0x4c9450` 的 `[0,0x9908b0df]` 复制到生成器实际引用的 `RAM 0x741268bc`；这是有消费者的 twist 数据。原稿所述原始上下文也错误：紧前一字是零。 |
| 已确认不存在流密码 / PRNG 例程 | PRNG 全局否定已被下面完整种子、twist、tempering 及调用者链反驳。RC4 / UPD 解析器否定没有全程序证明。 |

## 2. 34 字节横向校验：机制确认，原稿入口和指令需纠正

见 `horizontal_34b.objdump.txt`、`horizontal_entry_boundary.objdump.txt`。

- 实际调用入口：文件 **`0xc844a`**，在 `0xc877b` 被调用；`0xc8448` 的 `c0 08` 是前段 `blt`，并非本函数入口。
- `a0` 每次读取连续两个字节，把首字节存入 `sp+1`、次字节存入 `sp`，通过小端 `movhu (sp),d1` 得到大端 `uint16`；`d2` 循环计数至 16，`d0` 累加并保持低 16 位。
- 实际 `not d0` 位于 **`0xc846b`** (`f2 30`)，加一位于 **`0xc8473`** (`40`)；不是原稿的 `0xc8467 not d1 / add 1,d1`。
- 最后两个字节同样组成大端半字，比较是否等于 `(-sum(payload_words))&65535`，相等返回 1，否则返回 0。

## 3. 纵向检查：32 字节缓冲中折叠 8 槽，检查 16 槽

见 `stream_and_folded_vertical.objdump.txt` 与 JSON `vertical`。完整循环为 `0xc8817..0xc883f`，清零验证为 `0xc8840..0xc8855`。

- 实际入口 **`0xc8817`**；`0xc8813` 是前一函数的成功返回路径。流解码器使用 **`sp+0x20` 栈缓冲**；不是原稿断言的全局 `0x74011ea8` 数组。`0xc8710..0xc8723` 从 ROM `0x404ae3bb` 复制 32 个零字节初始化。
- `d3=0`，输入字节位置每次 `+2`；`d1=15; and d3,d1; add d1,d1` 得到槽字节偏移 `2*(d3&15)`。针对 32 字节输入，偏移是 `0,4,8,...,28` 然后再次重复；**16 个输入半字折叠至 8 个偶数半字槽**，每槽为两列之和。其余 8 个半字维持零。循环用 `d3<input_byte_length` 作为边界。
- 零验证函数顺序读取 16 个半字。这不能命名为严格独立的 16 列检查。
- 相容性实测：原始 GH1__132 文件 8,912,930 B、262,145 条 34 B 记录，横向错误 0；严格 16 列和机内索引折叠槽均全零。**通过同一实际文件不意味着两种算法相等。**
- 反例：同一块中第 0 列为 1、第 8 列为 65535，其余为零，横向检查字为零。机内折叠和全零，严格 16 列仍有两列非零。本目录记录的是公式的离线数学执行，没有执行固件。

这修正的是机内消费者描述；不会推翻已独立验证的 PTool 输出采用严格 16 列尾块的事实。

## 4. 34→32 流式消费者：核心链确认，具体偏移修正

见 `stream_and_folded_vertical.objdump.txt`、`stream_caller_arguments.objdump.txt`、`copy_32b_consumer.objdump.txt`。

1. 入口 `0xc8705`；读请求最大 8704 B (`256*34`) 实际在 **`0xc874e`** 的 `mov 8704,d2`，剩余量不足时选更小长度。
2. 每记录调用 `0xc877b→0xc844a` 做横向检查；`0xc8799→0xc8817` 累加前 32 B。
3. `0xc87a3→VA 0x7bc455a8`，参数 `a0=目标、a1=当前记录、d0=32`。已检查真实消费者：它逐字节原样复制，无密钥变换。
4. **`0xc87ae` 目标加 32、`0xc87b2` 输入加 34**，`0xc87b5` 回跳下一记录。原稿所列 `0xc87cf/0xc87d1` 步进字节并不匹配。
5. 已核验调用者 `0xbbbba` 与 `0xbbc5d` 提供 staging 目标 `0xb4a00000`（后一条在条件分支可选择 `0xb5300000`）与输入缓冲 `0x74011dc8`。
6. 本流函数复制每条记录的前 32 B，包括末尾校验记录；`0xc87f2..0xc87fa` 返回当前目标减起始目标，**未在该函数中减去末尾 32 B**。外部格式解码器剥离尾块的行为不应直接套在这段机内消费者上。

## 5. 完整 MT19937 静态链及当前用途边界

见 `seed_twist_temper_candidate.objdump.txt`、`startup_initialized_data_copy.objdump.txt`、`random_integer_selector.objdump.txt`。

- 种子函数 `0xb2734` 存入 `RAM 0x74153c94`，循环 `i=1..623`，实现 `state[i]=1812433253*(state[i-1]^(state[i-1]>>30))+i` 的 32 位结果；不是单个常数猜测。
- 生成器 `0xb276d`，初始索引 625 时以 5489 调种子函数，624 项状态更新包含相距 397 项 / -227 项、`0x80000000/0x7fffffff` 掩码，以及 `[0,0x9908b0df]` 条件 twist 表。
- `0xb285e..0xb2880` tempering 包含右移 11、左移 7 与 `0x9d2c5680`、左移 15 与 `0xefc60000`、右移 18，完整静态结构匹配 MT19937。
- `.data` 启动拷贝 `0x102c..0x1049`：ROM `[0x404c43f0,0x404d0420)` → RAM `0x7412185c`。因此 RAM `0x741268b8` 对应文件 `0x4c944c` 的 625；RAM `0x741268bc` 对应文件 `0x4c9450` 的上述 twist 表。此映射由真实拷贝循环验证。
- 直接生成器调用者共发现并核验五处：`0x12c091/0x12c0a5/0x12c0b9/0x12c0cd/0x12c0e1`。属于 `0x12c064` 范围选择函数，分别返回 `%6+7`、`%6+13`、`%6+14`、`%3+20`、`%7+23` 的小整数。

**可结论：旧 GH1 固件存在完整 MT19937 静态算法链，已观察到通用的小整数随机选择用途。没有建立它到升级解码 / 固件解密的调用或数据链，不能命名为 method2，更不能推用于 S1 或 S1M2。** 直接调用扫描范围与编码已保存，间接调用及未追踪的更上层业务仍在边界之外。

ROM 指令映射采用 `VA=0x40000000+file_offset`。已查看 overlay 启动拷贝 `0x10e4..0x112c` 的 ROM `0x40510000` → RAM `0xbbc00000`，配合复位和调用目标的 `0x7bc00000` 执行别名定位复制消费者。独立的尾部身份块拷贝 `0xc717f..0xc7191` 确认 ROM `0x407f4000` → RAM `0x740045c4`、长度 0x8000；以上映射都按当前 GH1 输入验证，没有从其他机型移用。
