# S1M2 V1.5：UPD 容器、PTP 0x9421 与服务接口 04DA:2370 实机验证

## 0. 元信息

| 项 | 值 |
|---|---|
| 目标机型 | DC-S1M2（VID `0x04DA`） |
| 固件 | `S1m2_V15.bin`（Panasonic 官方 `S1m2_V15.zip` 解压） |
| 固件大小 | 171,867,648 字节（`0xA3E7E00`） |
| 固件 SHA-256 | `800537aadcfd9a828ecdb06ea9beb7443c2a74d0e77a384cc290ee27f4a8c054` |
| 机身固件版本 | 菜单显示 1.5 |
| 相关既有记录 | PR #2（V1.4 ROM BACKUP 实机）、`multimodel_diff_20261012`、`format_transition_audit_20261011`、`unpacked/` |

## 1. 要验证的问题

- **Q1（容器）**：V1.5 是否仍为 UPD-v2（62 × 92 B 目录、外层 CRC32 覆盖 `0x200..EOF`、逐项 `SHA-256(明文)`）？
- **Q2（版本门）**：`0x1C` 的 u16×2 是否为版本门？改动后相机是否接受该包？
- **Q3（PTP）**：`0x9421` 在 V1.5 上是否可用、参数与返回结构是什么？
- **Q4（服务接口）**：`04DA:2370` 的块读协议、地址空间边界与可读范围是什么？

## 2. 输入与取得方式

固件来自 Panasonic 官方固件页的分发 ZIP（`S1m2_V15.zip`），解压后得 `S1m2_V15.bin`。
本文所有结论只用该文件的字节与实机 USB 行为，不含任何厂商工具或受限维修资料。

工具（随本文提交）：`upd_tool.py`（容器解析/校验/重打包）、`ptp.py`（PTP 客户端）、
`svc2370.py`（2370 客户端：门铃 + `0x5C` 块读 + 窗口扫描/dump）。依赖：Python 3.10+、`pycryptodome`（仅 reduced-round AES 检验用）、`capstone`（仅反汇编用）。

## 3. 结果

### 3.1 容器（Q1）

- 魔数 `UPD\0`；型号串 `MC8243`；`0x3C` = `0x0A3E7C00` = 文件长度 − 0x200。
- `0x40` 的 CRC32 = `0xBF88FCAE`，`zlib.crc32(data[0x200:])` 一致。
- 内层头 `0x2A0`：`+0x40`= `0x1800`（首项相对偏移）、`+0x44` = `0x0A3E6400`（62 项 size 合计，逐项相加一致）、`+0x48` = `0x3E`（62）。
- 目录 62 项 × 92 B，`0x2EC` → `0x1934`；载荷区 `0x1A00` → EOF，58 个非空段**无空隙无重叠**。
- 项结构：`name[12] | u32 rel | u32 size | u32 dest | u32 flags | sha256[32] | iv[16] | reserved[16]`。
- flags 分布：`3` × 49（合计 151,544,832 B）、`2` × 13（其中 4 项长度为 0）。
- **摘要语义证据**：4 个零长项摘要 = `SHA-256("")`；9 个非空 `flags=2` 项摘要与自身字节一致；
  49 个 `flags=3` 项摘要与密文**全部不一致**；其中 `[08]`/`[10]` 摘要 = `SHA-256(0xFF × 131072)`，
  而 `[61] mbr_dummy_d`（`flags=2`、裸存）持有**同一摘要**且字节确为 `0xFF × 131072`。

### 3.2 版本门与更新（Q2）

- `0x1C` / `0x1E` = `0x0150`（BCD 1.50）；`0x24/0x26` = `0x0325 / 0x0825`。
- 将 `0x1C/0x1E` 改为 `0x0151` 后，外层 CRC32 **不变**（`0x1C` 位于 `0x200` 之前，不在 CRC 覆盖范围）。
- 该包拷入 SD 卡根目录、正常开机进「固件更新」→ 相机提示**「开始更新？」**并完成更新，
  重启后**版本仍显示 1.5**，其它功能正常。
- 未验证：更新过程中是否另有逐分区哈希/签名校验通过（本条只证明版本门与 CRC 层不拦该包）。

### 3.3 PTP `0x9421`（Q3）

- 正常模式下相机为 `04DA:2382`，接口 `06/01/01`（Still Image），端点 `0x01` bulk OUT / `0x81` bulk IN / `0x82` interrupt。
- Windows 以 WPD/MTP 驱动接管时无法发厂商 opcode；用 Zadig 将 `2382` 替换为 WinUSB 后可直连。
- 流程：`GetDeviceInfo → OpenSession → 0x9421 → CloseSession`。
- **参数是 tag，不是地址**：

| tag | 返回 |
|---|---|
| `0x080000a2` | DATA **9,197,673 B** + RESPONSE `0x2001 OK` |
| `0x080000a1` | `0x2002 GeneralError` |
| `0x00000000` | `0x2002 GeneralError` |

- 结构：外层 TLV `tag=0x080000a2`、`len=0x8C5861`、`len2=0x8C585D`，随后 `"Panasonic\0"` `"DC-S1M2\0"`；
  记录表 3085 条，`{u16 idx, u16 grp(0/1/2), u32 len, u32 type}`，覆盖到 `0x8C5864`（余 5 字节尾）；
  最大记录 `idx=1311 type=0xC len=8,840,924`；结尾 `ff ff 00 00` + 校验 `0xb3`。
- 内容为菜单/风格**名称表**与用户设置：如 `CLASSIC CHROME - STD`、`REALA-ACE - STD v2`、`ETERNA - STD v2`、
  `Leica Contemporary`、`Leica Eternal`、`Leica Std`、`Custom Mode C5-1…10`、`MY PHOTO STYLE 1…10`。
  `license/licence/auth/activat/trial/unlock/serial/token/valid/expire` 关键词**零命中**。
- **未在其中发现固件或 RAM 对象**；与既有 PTP 对象枚举结论一致。

### 3.4 服务接口 `04DA:2370`（Q4）

进入方式：关机 → 按住 `PLAY` + `AF-ON` → 开机（依 PR #2，驱动拨盘需在 `[Single]`）。

- 描述符（实测）：`bcdUSB=0x0210`，接口 `ff/a0/b0`，3 端点
  **`0x01` bulk OUT / `0x81` bulk IN / `0x82` interrupt IN(64, interval 16)**。
  → 与 S5 的 `0x01/0x82` **不同**，直接套用 S5 客户端会 `err=121` 超时。
- 门铃：`ctrl(bmRequestType=0x40, bRequest=0x00, wIndex=0)` → 写帧 → `ctrl(…, wIndex=1)` → 读。
  设备刚进服务模式时门铃会被 STALL，需等待其就绪。
- `0x5C` 帧（1030 B）：`f[0]=0x01, f[2]=0xFF, f[3]=0x5C, f[4:8]=addr, f[8:12]=end, f[1028]=Σf[1:-2]`，
  成功应答 `01 00 FF 05` + 1024 B 数据。
- **关键：`end` 必须非零**。`addr=0,end=0` 只是 ping（返回成功但数据无意义）；
  `end` 越界会让固件崩、USB 掉线（`err=31/433`），需重启相机。
- 可读窗口（实测，`0x5C` 只能访问这三段）：

| 基址 | 可读范围 | 大小 | 说明 |
|---|---|---|---|
| `0x8400000` | `+0x0..+0x2FFFF` | 192 KB | `0x0` 是它的别名（内容逐字节相同） |
| `0x8000000` | `+0x0..+0x3FFFF` | 256 KB | |
| `0x8200000` | `+0x0..+0x1FFFF` | 128 KB | |

  `0x8600000`、`0xC0000000`：`err=22`（拒绝，不崩）；`0x40000`、`0x8040000`、`0x8220000`：`err=31` 掉线。

- 三段内容均为 **ARM64** 代码/数据（capstone 可反汇编），含 `FAT12/16/32`、`"SD      .DAT"`、`"SDRAM   .PAR"` 字符串。
- 窗口 C（`0x8200000`）的 `+0x2C0` 起有指针表：`0x08214EE0 / 0x08400040 / 0x08400200 / 0x0840C198 / 0x08400000 / 0x08200000`，
  印证服务固件以 `0x8400000`、`0x8200000` 为自身基址。
- 在这三段的代码区反汇编搜索 `cmp/mov #0x5C / #0x9B / #0x38 / #0x75 / #0x35`：**0 命中**（未定位到 USB 命令分发）。
- 其它读 opcode 在就绪状态下均被拒：`0x9B`（绝对字读）→ `ctrl(wIndex=1) err=22`；`0x75`/`0x35` 同。

## 4. 观察、推论、未知（分列）

**观察（可直接复核）**
1. V1.5 容器结构、CRC、逐项摘要语义与 3.1 一致；
2. `0x1C/0x1E` 改一档后相机接受该包并完成更新，版本显示不变；
3. PTP `0x9421` 只有 tag `0x080000a2` 有效，返回 9,197,673 B，结构如上；
4. 2370 的 `0x5C` 在 `end != 0` 时可读三段落、合计 576 KB；越界即掉线；其它读 opcode 被拒。

**推论（有条件）**
1. 逐项摘要对应**明文**（零长项 = `SHA-256("")`、`flags=2` 自洽、`[08]/[10]/[61]` 三方互证）；
   但"机身消费者用它校验明文"仍需机内代码证据；
2. 服务固件以 `0x8400000` 为窗口 A 基址，故 `0x0` 读到同一段；
3. 主固件（`program`，`dest=0x80000`，46.9 MB）不在这三段落内，`0x5C` 无"切换窗口/设置基址"参数。

**未知（不可由本文断定）**
1. `0x220` 的 64 B 字段性质（已排除常见哈希构造，未确认签名/MAC）；
2. 主固件在 RAM/flash 中的落点与是否可经其它命令读取；
3. `DSC->SD` 导出与容器 `eep_* / kizu / xtk` 的对应关系（本次缺 SD 卡，未执行）；
4. flash 内是明文还是密文（H1/H2 未定）。

## 5. 与既有实验的差别

- PR #2 是 **V1.4** 的 ROM BACKUP 菜单/导出实测；本文是 **V1.5** 的容器、PTP `0x9421` 与服务接口 `2370`，两者不重叠。
- `format_transition_audit_20261011` 用旧密钥做"不猜 IV"的 CBC/CTR 检验；本文改用 **已知明文**（`0xFF` 填充的 `[08]/[10]`）做判据：
  自写 reduced-round AES（1–10 轮，R=10 与标准 AES 逐字节一致）扫描"key = 载荷前 256 KiB 任意 16 B 窗口"，
  CBC-无-IV / CTR(目录 IV) / CTR(零) 三判据、约 236 万次/条目，**0 命中**；MT19937 种子自采样滑窗同样 0 命中。
  → 有限排除"5 轮 AES-128-CBC + key 自采样于载荷前部"这一族，不等于排除 AES。

## 6. 什么结果会推翻本文结论

1. 若 `0x5C` 的 `end` 实际是"长度"且允许更大值 → 推翻"只能读三段落"；
2. 若在其它 `wIndex/wValue` 或未试 opcode 下存在"设置基址/选窗口"命令 → 推翻"无切窗口能力"；
3. 若 PTP `0x9421` 的其它 tag 有效并返回固件/RAM 数据 → 推翻"仅 a2 且只给配置"；
4. 若机内代码显示摘要用于校验密文而非明文 → 推翻 3.1 的摘要语义推论。
