## 已核对的真实代码

路径相对 decompiled/sources/：

- B5/a.java:886-897：U() 发送 req_acc_g，分割响应 CSV，把第二字段作为十六进制整数解析；这是客户端期望格式，不是某台相机返回该字段的证据。
- com/panasonic/jp/service/c.java:823-843：u() 在 Encrypt 模式下调用 U()，再用 N5.o.b() 处理设备标识和名称；未取得值则报告 encrypt_key_failure。
- N5/o.java:51 起：b(String,int) 按四字符分组，执行 XOR 和字节重排，输出十六进制文本。属于连接握手变换，不是 UPD 组件解密函数。
- com/panasonic/jp/service/c.java:684-699：f() 根据连接模式选择 req_acc_e 或 req_acc，并解析结果。
- 同文件 :258-268：T() 仅在响应长度至少 5 且首字段为 ok 时保存第五字段。四字段响应会直接返回，不能由客户端的第五字段解析规则推断相机已经发放令牌。
- p142r5/b.java:87-91：仅当已保存会话字符串非空时给 HTTP 请求加 X-SESSION_ID。

dex_handshake_transform_references.jsonl 记录 N5.o 的 14 处外部方法引用，其中 DeviceConnectService.c.u 的两条调用指向 b，与上述变换位置一致。静态引用不是成功握手的证据。

## 对 PR #1 的判断

PR 引用的类名与本次 2.0.17 的混淆命名不同，不能宣称取得了原作者使用的完全同版本 APK。本次独立代码支持其通用客户端流程：条件选择握手、CSV 解析、四字符变换和可选会话请求头。

但这不解决其 S5 实测段落的内部矛盾。客户端包含 Encrypt 路径不能证明该 S5 支持 req_acc_g/req_acc_e；可选令牌头也不能证明所有控制类命令都不要求鉴权。没有执行握手或控制测试，原作者的真机结论仍是作者陈述。

未取得固件解码算法、程序对象或 RAM 读取入口。固件/EEPROM/bootloader 等有限关键词检查没有在已查业务目录形成新的具体读取调用链；反编译错误、原生库和其他未检查分支的限制仍保留，不作全应用排除。
