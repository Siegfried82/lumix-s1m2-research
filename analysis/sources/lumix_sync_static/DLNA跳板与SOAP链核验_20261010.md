# DLNA 跳板与 SOAP 链核验

2026-10-10，只读静态解析 ELF，不运行共享库。

JNI 浏览函数的全部此前未命名直接 BL 跳板已由 AArch64 ADRP/LDR 解码到 GOT，再与 ELF RELA 重定位对应：malloc、free、__stack_chk_fail，以及 dmpBrowseForExtensionTags / dmpBrowseForExtensionTags2。这关闭了前一报告中未命名 PLT 缺口，不代表完整控制流覆盖。

进一步解析两个真实浏览函数：地址 0x8c6ec（440 字节）及 0x8c8a4（544 字节）。直接调用对应 DM_DMP_SoapHandlerNew/Delete、DM_DMP_SetSoapActionNamespace、DM_DMP_Browse、DM_DMP_BrowseForExtensionTag、IMAEXT_DMP_BrowseWithExtensionTag2/3；包括第二函数尾跳到第一函数的 B 跳板。由实际重定位支持其为 SOAP/DLNA 浏览调用链，不能只从未知调用地址推断固件解码。

结合先前 Java DIDL-Lite 输出消费链，没有程序或任意地址数据输出的证据。当前没有深入所有 SOAP 内部函数、间接 JNI 调用、网络运行行为，不作全库能力排除。

证据 dlna_plt_resolved.json、dlna_browse_implementation_branches.json、dlna_implementation_plt.json。audit_dlna_plt.py 与两个 implementation 脚本保留复现。系统执行的仅为自己的读取脚本，不执行 APK/固件。

该浏览支线已形成明确协议证据，直接固件收益仍未出现。后续优先实际只读对象枚举、同款维修导出/程序样本，或带明确解码入口的新客户端材料，避免无边界地遍历通用媒体栈。
