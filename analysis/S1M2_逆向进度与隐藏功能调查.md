# S1M2 逆向进度与隐藏功能调查

更新：2026-10-07。输入为项目中的 S1m2_V14.bin。已完成封装验证、编码假设试验和官方开源组件调查；继续工作新增了官方包逐字节哈希核对、V1.3/V1.4 对比，以及从 PTool 静态还原并成功验证的旧 GH2 AES 解码流程。**S1M2 专有程序仍未解密，完整逆向工程尚未完成。** 新一轮具体证据和脚本见 [解码突破记录](S1M2_解码突破记录.md)。

## 目前的结论

**松下确实有已经实现、但需要额外条件才开放的功能。S1M2 的确定例子是 ARRI LogC3 授权启用；目前没有证据证明机械快门摇摇乐、完整输入 RAW 导出或多曝光 HDR 合成已经写好、仅被隐藏。**

不要把三个层次混在一起：某个功能的名称存在；功能代码确实存在；该机型能在预期条件下执行并产出正确文件。判定“可以解锁”至少需要后两项的证据，并确认阻挡它的条件。

## 封装层的新验证

`inventory.json` 登记 62 个目录项。第四字段为 2 的 13 项，其原始 SHA-256 全部匹配目录散列；第四字段为 3 的 49 项全部不匹配。原始副本中可直接验证的非空项均为全 00 或全 FF 填充区。

本次确定外层 CRC32 的覆盖范围：

```text
存储位置：0x40，little-endian uint32
覆盖范围：[0x200, 文件末尾)
存储值：0x5d6f7ff7
计算值：0x5d6f7ff7
```

这证明该字段是本文件的 CRC32 校验。它不能证明包没有额外的数字签名或授权校验，也不能证明改完 CRC32 就能刷入。

目录项的后 32 字节实际呈现为 16 字节非零数据加 16 字节零。49 个受编码组件均未发现重复的对齐 16 字节块；相同目录散列的组件可以有不同的原始数据及不同的 16 字节字段。以上与随机化加密相容，但未确定此字段是 IV、封装密钥、认证字段还是其他数据。

特别有价值的对应关系：目录项 8（postboot2_r）、10（postboot4_r）、61（mbr_dummy_d）大小同为 128 KiB，目录散列相同；第 61 项原始内容是全 FF，散列已验证。由此可以提出并检验前两项解码后也是全 FF 的假设。尚未解码，因此该解释保留为假设。

编码探测保存于 `encoding_probes.json`：包含逐 64 KiB 熵、重复块统计、同散列组件分组。对字段为 3 的组件，整段 XOR FF 与 XOR 80 均未得到目录散列。

`metadata_key_probes.json` 记录一次有限试验：1100 个去重的候选密钥（头部对齐字段、零/FF、公有型号字符串的简单构造），对第 8、10 项测试 AES 的 CBC/CFB/OFB/CTR/ECB，以目录的 16 字节字段作为相应 IV，共 11000 次试验，未命中。成功判据是先匹配 32 字节全 FF，再验证整段 SHA-256。这仅排除该候选集合及指定 IV/模式组合，**不是 AES 已被确认或破解，也不是证明保护不可突破**。

## 官方开源组件的实际调查

从松下列明 DC-S1M2ES/DC-S1M2 的官方页面下载了 U-Boot、Linux 4.19.124 和版权包；URL、长度、SHA-256 保存在 `sources/download_manifest.json`，下载后只做静态读取。

- U-Boot 包有 16884 个目录成员，版本字段为 2019.07，含 Milbeaut/SC2006A 支持和通用 AES-128-CBC 命令。通用 AES 命令从调用者提供的内存地址读取 key/IV，本文件没有提供 S1M2 更新包密钥。没有找到 MC8243、S1M2、hr_c_prog、eep_act 或所查询的 UPD 专用标识。
- Linux 包有 66156 个目录成员，含松下修改过的 Milbeaut 驱动、PVC 缓冲区驱动、DM 内存驱动，以及标注 MC8241 的板级配置。
- 板级源码有 RTOS 共享内存头、IPCU 消息缓冲区与同步区、MOVIE/AUDIO 区地址描述；还有 Linux–RTOS 文件系统及 DSP IPCU 源码。这是通信边界和缓冲区研究的真实入口。
- `fs/ipcufs.h` 定义挂载、查找、读页、写页、打开和关闭请求，以及包含物理地址与长度数组的传输结构；`include/uapi/linux/ipcu_userland.h` 定义消息发送、接收、确认及通道开关 ioctl。已经能读到通信层接口，但尚未定位任何 RAW 帧保存或 HDR 合成的业务命令。
- **对应边界：源码板级标识 MC8241，本包头部标识 MC8243。** 官方发布页面将这些源包列在 S1M2 下，但不能直接认为其中某个旧配置就是本机最终构建配置，也不能把地址直接用于实机。
- 从源码看出平台通信结构，不等于已经拿到了专有的曝光、快门、传感器位移或 HDR 融合程序。没有在本次精确型号/更新标识扫描中找到专用解码实现。

## 后续完整逆向的依赖顺序

1. **取得可验证的解码方法。** 研究头部保护、16 字节字段角色、加载器处理流程；利用全 FF 候选与散列作客观判据。另一个官方版本可用于比较目录散列与随机化字段，但比较本身不提供密钥。
2. **识别每个处理器的程序。** 解码后根据可执行头、复位入口、指令与交叉引用确认架构、加载地址和程序/数据边界；不能把所有 DSP 模块直接按 ARM 反汇编。
3. **找出门控的实现与调用关系。** 菜单资源 → 功能 ID → 支持表 → 模式状态机 → 真正的硬件/算法入口。区分区域限制、授权限制、模式互斥、未编译代码与硬件限制。
4. **优先追踪三个目标。** 机械快门/位移/读出时序；全部输入 RAW 的存储生命周期；包围曝光与机内融合器的数据格式和状态机。分别判定“完整实现但被挡住”“可复用部分”“需要新增算法/流程”。
5. **提出可审查的修改后，再谈验证。** 先给出原始逻辑、拟改逻辑、校验及恢复条件。此项目当前仍只授权离线分析；不连接或修改机身，不生成可刷写补丁假装成功。

目前最关键的缺口是专有组件的明文与可信解码流程。现有公开源码能推进平台分析，尚不能越过该缺口去判断目标功能是否已经实现。

在项目目录运行：

```sh
python3 analysis/inspect_firmware.py
python3 analysis/probe_encoding.py
python3 analysis/inspect_oss_sources.py
<LOCAL_USER>/.cache/codex-runtimes/codex-primary-runtime/dependencies/python/bin/python3 analysis/probe_metadata_keys.py
```

第三条仅读取已下载的官方 Linux 源码包，提取相关普通文件并登记来源；每次扫描限单文件 4 MB，未执行源码或构建脚本。第四条使用环境已有的 cryptography，不下载运行第三方破解程序。
